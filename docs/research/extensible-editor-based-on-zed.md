# Fyx: fork Zed, keep the UI API separate

The best path is neither to write a new editor on GPUI nor to wait for upstream. The best option is to **fork Zed following the Brave/VSCodium model**. The fork is pinned to a stable tag. All new code (the UI extension host, its own WIT world, the agent change-approval panel, demo extensions) lives in separate crates, and upstream crates are changed only at a few thin hook points. The reasoning is as follows. **Zed has no UI API for extensions at all**: WIT v0.8.0 can only return commands and configs for LSP/DAP/MCP. In May 2026 a maintainer called a visual API "significant work that we're unlikely to get to in the near future". At the same time, the entire editor core (rope, editor, workspace, agent_ui) is distributed under the GPL and is tightly coupled. So "your own editor on GPUI" means years of rewriting what a fork gets for free, including a ready-made ACP integration with the registry's agents (39 in the August snapshot). A fork has its price: GPL-3.0 for the whole product, a mandatory new name and a weekly race against upstream. Every known fork is losing that race (Zedless, Gram, Superzent have dozens of stars and constant merge conflicts), and none of them has added a general extension API. Technically, the API should be declarative. The extension sends a serialized component tree and patches to it, and the host draws it with native GPUI elements in the current theme. Complex surfaces (diff view, change approval, inline widgets) should be host components that the extension merely parameterizes. There must be no WASM call in the render path. In 1–2 days a swarm of 6–8 agents can realistically deliver a narrow vertical slice: one WIT world, 5–7 primitives, a dock panel, 1–2 demo extensions and basic approval of agent changes. A stable and secure API, which the author of the relevant RFC estimates at "a few months", will not exist in that time. The speed limit will not be the token limit but disk and CPU: a single Rust target directory takes 2–28 GB.

## Zed 1.30: 1.8 million lines of GPL code that change every week

Zed 1.0 was released on **April 29, 2026**. The release post mentions over a million lines of code, "hundreds of thousands" of daily users, macOS, Windows and Linux, and the intention to keep shipping releases weekly. 1.0 already includes Git, SSH remoting, a debugger, parallel agents and ACP with Claude Agent, Codex, OpenCode and Cursor ([Zed blog: Zed is 1.0](https://zed.dev/blog/zed-1-0)). The promise of weekly releases has been kept. As of November 17, 2026, `crates/zed/Cargo.toml` on main has `version = "1.30.0"`, the stable branch is at 1.28.x, preview at 1.29.x, and the repository has **1,395 `v*` tags** in total ([Zed repo tags](https://github.com/zed-industries/zed/tags)). The code itself has **253 crates and 1,821,540 lines of Rust**. The largest parts are: `editor` with about 192k lines, `project` 125k, `gpui` 107k, `agent_ui` 103k, `agent` 94k, `workspace` 57k. `extension_host` itself is small, about 14.5k lines ([Zed repo](https://github.com/zed-industries/zed)). For a fork this means a target that went from 1.0 to 1.28 in ~29 weeks, with every week bringing internal breaking changes.

The build requires the pinned **Rust 1.98.1** toolchain (edition 2024) with the `wasm32-wasip2` target for extensions, `wasm32-unknown-unknown` for "gpui on the web" and musl for the remote server ([Zed repo: rust-toolchain.toml](https://github.com/zed-industries/zed/blob/main/rust-toolchain.toml)). On macOS you need Xcode, CLT and `cmake`, which the `wasmtime-c-api` dependency requires. A release bundle via `script/bundle-mac` requires the **macOS 26 SDK, i.e. Xcode 26+** ([Zed docs: Building for macOS](https://zed.dev/docs/development/macos)). On Windows you need MSVC with the Spectre libraries and CMake ([Zed docs: Building for Windows](https://zed.dev/docs/development/windows.md)). There are no official build-time figures. A third-party measurement gives **16 min 52 s for `cargo build --release`**, but on an older and smaller repository ([cargo-slicer](https://yijunyu.github.io/cargo-slicer/blog/part1.html)). The author of one fork reports roughly **20 min for a full build and about an hour for a release build** ([Discussion #53403](https://github.com/zed-industries/zed/discussions/53403)).

### Licensing: GPUI is free, the editor is not

The README puts it briefly: the code is "mostly GPL-3.0-or-later, with Apache-2.0 components where marked" ([Zed repo README](https://github.com/zed-industries/zed)). In current main, **208 crates are GPL-3.0-or-later, 37 are Apache-2.0**, and another 8 utility crates without a license field contain `LICENSE-GPL`. Under Apache-2.0 are the whole GPUI family (`gpui`, `gpui_macros`, `gpui_platform`, the platform backends, including `gpui_web` and `gpui_ios`) and infrastructure: `sum_tree`, `collections`, `util`, `refineable`, `scheduler`, `http_client`, as well as `extension_api`, i.e. the WIT and the extension guest SDK. **Everything that makes Zed an editor is under the GPL**: `rope`, `text`, `language`, `lsp`, `multi_buffer`, `editor`, `project`, `workspace`, `ui`, `theme`, `terminal`, `extension_host`, `acp_thread`, `agent`, `agent_ui`, `agent_servers` ([Zed repo](https://github.com/zed-industries/zed)). The server side of collab, which used to be AGPL, has been relicensed to GPL. The stated reason was corporate "AGPL-phobia" ([AlphaSignal](https://alphasignal.ai/news/zed-drops-agpl-to-unblock-enterprise-developers-banned-from-using-it)), and the current `crates/collab/Cargo.toml` confirms this. So there is no longer a network clause that would require disclosing the code of a modified server.

The layers in the code go from the bottom up. At the very bottom is `gpui`, then `sum_tree` → `rope` → `text` (a CRDT buffer with anchors), above it `language` (Tree-sitter) and `lsp`, then `project`, `multi_buffer` → `editor`, `workspace`, feature crates and finally the `zed` binary that ties it all together. In practice only the bottom can be reused. `gpui` depends only on Apache crates ([Zed repo: crates/gpui/Cargo.toml](https://github.com/zed-industries/zed/blob/main/crates/gpui/Cargo.toml)). From `language` upward, crates pull in settings, fs, client and project, so taking `editor` effectively means taking almost all of Zed. Using GPUI on its own is also awkward. On crates.io `gpui` is at version **0.2.2 from October 2025**, i.e. more than a year behind main. `gpui_platform`, from which the README recommends launching applications, is not published on crates.io at all, and the README itself calls GPUI "pre-1.0" with frequent breaking changes ([crates.io gpui](https://crates.io/crates/gpui)). There is an ecosystem around GPUI. Longbridge's component library (GPUI Kit, 75+ components, Apache-2.0, ~18.7k stars) is used in a commercial trading application ([GitHub longbridge/gpui-component](https://github.com/longbridge/gpui-component)). The `gpui-component` package is at version 0.10.0, updated November 16, 2026 ([crates.io](https://crates.io/crates/gpui-component)). There is also a community fork, `gpui-ce` ([crates.io gpui-ce](https://crates.io/crates/gpui-ce)). Of interest to a mobile developer: the tree already contains `gpui_ios` and `gpui_web`, although this research found no official announcement of these backends.

### Where exactly the UI plugs in and what will have to be cut

In Zed all UI composition happens in Rust at compile time. A panel implements the `Panel` trait (`crates/workspace/src/dock.rs:36`, positions Left/Bottom/Right, sizes, icon, toggle action). Tab content implements `Item` (`item.rs:170`, title, dirty/save, split, navigation). There are also `ToolbarItemView`, `StatusItemView` and `ModalView`. They are registered via calls to `Workspace::add_panel` (workspace.rs:2921), `register_project_item` and `register_action`. Most important for the fork: `crates/zed/src/zed.rs` (lines 780–864) **loads all panels statically**: ProjectPanel, Outline, Terminal, Git, Collab, Debug, Agent ([Zed repo](https://github.com/zed-industries/zed)). So the natural hook point is this: a host adapter `ExtensionPanel`/`ExtensionItem` implements these traits on behalf of an extension and is registered dynamically from the extension host rather than in `zed.rs`.

Zed's cloud part can be separated, but it is woven in deeply. Telemetry is on by default with opt-out, is disabled via `"telemetry": {"diagnostics": false, "metrics": false}` and goes to Sentry, Snowflake, Hex and Amplitude ([Zed docs: Telemetry](https://zed.dev/docs/telemetry)). `crates/client` reads `ZED_SERVER_URL`. Scattered through the code are dozens of hard-coded `https://zed.dev`, 6 occurrences of `cloud.zed.dev` and 8 occurrences of `zed.dev/releases` for auto-update. Separately there are the crates `telemetry`, `crashes`, `auto_update*`, `collab_ui`, `call`, `channel`, `livekit_*`, `cloud_llm_client`, `edit_prediction*`, `onboarding` ([Zed repo](https://github.com/zed-industries/zed)). A minimal "de-clouding" of the fork consists of these steps: turn telemetry off by default and stub out the uploads, point `server_url` at your own server or nowhere, remove zed.dev sign-in and the collab panels, replace the update feed, keep BYO-key providers and ACP agents. Removing `client` entirely is hard, because `project` and `workspace` reference it for collab. A stub is more reliable.

## Zed extensions don't draw a single pixel, and upstream doesn't promise they will

Zed extensions are compiled into WASM components and run in wasmtime. The `zed:extension` contract is versioned by snapshots `since_v0.0.1` … `since_v0.8.0` (there is no v0.7.0 directory). For each version the host keeps a separate bindings module, so old extensions keep working ([zed repo: extension_api/wit](https://github.com/zed-industries/zed/tree/main/crates/extension_api/wit)). A subtle point: **the stable and preview channels accept the API only up to v0.6.0, and v0.8.0 is available only on nightly** ([wasm_host/wit.rs](https://github.com/zed-industries/zed/blob/main/crates/extension_host/src/wasm_host/wit.rs)). The v0.8.0 world has about 680 lines of WIT. An extension can call `get-settings`, `download-file`, the `worktree` resources (reading files, `which`, shell env), `project` and a key-value store. The editor calls into the extension for language server commands and configs, `labels-for-completions`/`labels-for-symbols`, context servers (MCP), DAP and documentation indexing ([extension.wit v0.8.0](https://github.com/zed-industries/zed/blob/main/crates/extension_api/wit/since_v0.8.0/extension.wit)). **The only "presentation" an extension controls is `code-label`**, a line of code with highlighted spans. The model is entirely pull-based: the host asks, the extension answers. There is no `subscribe`, no buffer or editor resources, no extension-initiated updates.

The runtime determines what any UI API can be. A single global `wasmtime::Engine` is used with the component model, incremental compilation and **epoch interruption every 100 ms**. According to a comment in the code, this is a "rough upper bound" on how long an extension can block `Future::poll`. The compilation cache is limited to 32 MB; one extension takes about 512 KB of it. Each extension gets its own `Store` and **a single serialized message loop on a tokio task**. A call from the editor is passed as a boxed closure through an mpsc channel, and the response comes back through a oneshot. Host functions that need application state hop over to the main thread ([wasm_host.rs](https://github.com/zed-industries/zed/blob/main/crates/extension_host/src/wasm_host.rs)). The WASI sandbox exposes only the extension's working directory. Side effects are limited by exactly three capabilities: `process:exec`, `download_file` and `npm:install`. The user narrows them with the `granted_extension_capabilities` setting ([crates/extension/src/capabilities.rs](https://github.com/zed-industries/zed/blob/main/crates/extension/src/capabilities.rs); [docs: capabilities](https://zed.dev/docs/extensions/capabilities)). The main engineering constraint follows from this: GPUI rendering is synchronous and called every frame, while an extension call is asynchronous, cross-thread and serialized. Therefore **extension UI can only be retained**: the host draws the last stored tree, and updates arrive asynchronously.

In 2026 the extension surface **shrank rather than grew**. Slash commands from extensions were removed in favour of MCP servers ([docs: slash-commands](https://zed.dev/docs/extensions/slash-commands)). ACP extensions were deprecated as of v1.5.0 in favour of the ACP Registry ([docs: agent-servers](https://zed.dev/docs/extensions/agent-servers)). The publishing policy explicitly forbids "using the extension API in unintended ways to work around its current limitations" ([docs: publishing prerequisites](https://zed.dev/docs/extensions/publishing/prerequisites)). That is, tricks such as fake diagnostics that imitate UI may simply not get into the registry.

### Roadmap: an RFC exists, commitments don't

Back in March 2025 a Zed collaborator wrote that extensions are "*extremely* limited", that integrating with the Markdown renderer is impossible, and that a webview would be a "*huge* additional dependency" ([Discussion #27163](https://github.com/zed-industries/zed/discussions/27163)). On the public roadmap the only extensions item is "Open Webview via Extensions #21208" with **Triage** status, i.e. no commitment ([zed.dev/roadmap](https://zed.dev/roadmap)). The most concrete design document is the community **RFC "Visual Extension API" (#53403, April 8, 2026, draft)**. It proposes a new `extension-ui` crate of 2–3k lines and a WIT sketch: a `panel-handle` with `update(element-tree)`, an `element` variant (container, text, button, text-input, table, list, icon) with flex properties, a `callback-registry` keyed by string IDs, and a status bar with priorities. Its phases are: status bar 1–2 weeks, read-only panels 3–4, interactive panels 6–8, charts and custom renderers 2–3 months. Webview was rejected; rendering via GPUI was chosen. The RFC itself admits that its event model, layout and permissions are undefined ([Discussion #53403](https://github.com/zed-industries/zed/discussions/53403)). On May 21, 2026, maintainer macraig replied that the work is tied to the extensions roadmap and has to be done by the Zed team, and that it is "significant work that we're unlikely to get to in the near future", although it is "very much on our radar". Since May no staff have posted, and the community complains that "the focus is still on AI" ([Discussion #53403](https://github.com/zed-industries/zed/discussions/53403)).

The same thread has two valuable practical signals. User nakajimayoshi noted that a mandatory `build_ui` would break all existing extensions, so a separate trait or world is needed. He also stressed that simply injecting GPUI code into the main process would "destroy Zed's entire security model". User mentenaz built six native panels in his own fork: a DB, a node-based workflow editor, package managers, a system monitor, a dashboard and a GitHub client. From that experience he derived requirements: a canvas/graph primitive with zoom/pan (GPUI doesn't have one), automatic inheritance of theme tokens, access to workspace context, an explicit permission model, and background async work with loading and error states. He was also honest about the cost: syncing with upstream is painful ([Discussion #53403](https://github.com/zed-industries/zed/discussions/53403)). That list of requirements is effectively a ready-made backlog for your API.

## Forks only cut or hard-code, competitors are slow or very well funded

All the Zed forks found are small, and **none has added a general extension API**. They fall into two groups. The first group cuts features. Zedless ("privacy, local-first") has 64 stars, and its HN launch got 556 points. The author admitted that it lags upstream because of constant conflicts and is experimenting with patches at the tree-sitter AST level. A commenter counted ~20 own commits versus ~30,000 upstream ones ([relatedrepos](https://relatedrepos.com/gh/zedless-editor/zedless); [HN mirror](https://frontpage-app.vercel.app/news/44964916)). Gram (March 2026) removed AI, collab, telemetry and accounts, and had no binaries at launch ([The Register](https://www.theregister.com/2026/03/04/gram_cut_down_zed/)). Zen (Codeberg) promises syncing once a month ([programming.dev mirror](https://deddit.petersanchez.com/g/programming@programming.dev/p/62M9cp239HS8w9p6j2-Zen-A-distractionfree-code-editor-based-on-Zed)). The second group bakes agent UI directly into Rust. The author of a fork on dev.to, who doesn't know Rust, used AI to write **~800 lines of a Claude Code panel as a thin shell over a CLI process**, because extensions can't provide native UI ([dev.to](https://dev.to/tunadev0/zed-is-amazing-i-hate-it-5aob)). Superzent (an agent workspace with git worktrees and ACP tabs in the center pane) has 10 stars and still uses the upstream extension marketplace ([ecosyste.ms](https://awesome.ecosyste.ms/projects/github.com%2Fcurrybab%2Fsuperzent)). ZedX has 0 stars and a "periodic rebase" ([GitHub it-baron/zedx](https://github.com/it-baron/zedx)). Meanwhile upstream is quickly absorbing the agent niche. Claude Code via ACP went into beta on September 3, 2025 in response to a request with 238 votes ([GitHub #25498](https://github.com/zed-industries/zed/discussions/25498)), and Terminal Threads and Parallel Agents already work ([Digital Applied](https://www.digitalapplied.com/blog/ai-coding-ide-landscape-may-2026-10-tools)). The conclusion is harsh: **a fork whose only difference is a "Claude panel" loses its point with every Zed release**. Only what upstream deliberately doesn't do has long-term value, i.e. a general UI API.

Among new editors, the closest analogue to your thesis is **Rune IDE**, whose source code was opened on September 12, 2026. The application is GPLv3+, the extension SDK Apache-2.0. Rune is written in Go with native GPU rendering, and extensions talk to the editor through an **explicit out-of-process gRPC API**. Rune's agent is itself an extension on the same boundary as third-party ones. It runs only on macOS and Linux, and language coverage is narrow ([aicybr](https://aicybr.com/blog/rune-ide-open-source-gplv3-architecture-agent); [pkg.go.dev rune-go-sdk](https://pkg.go.dev/github.com/unstablebuild/rune-go-sdk)). Sources disagree on whether there is a Python SDK in addition to Go ([Linuxiac](https://linuxiac.com/rune-keyboard-driven-ide-is-now-open-source-under-gplv3/)). There are no popularity metrics for Rune. Rune's weak spots (no Windows, few languages) are exactly what a Zed fork gets at the start, along with ~1,000 extensions ([falcao.org](https://falcao.org/posts/zed-1-0/)). Lapce has over 38k stars, but its last release, v0.4.6, came out in January 2026 ([EveryDev](https://www.everydev.ai/tools/lapce)). Its WASI plugins have only `handle_request`/`handle_notification` and no panel API at all ([lapce-plugin](https://docs.rs/crate/lapce-plugin/0.1.2/source/src/lib.rs)), so the ecosystem has remained wrappers over LSP. Helix's Steel-based plugin system still lives in draft PR #8675 after hundreds of comments and commits, and depends on a separate PR with an event system ([helix PR #8675](https://github.com/helix-editor/helix/pull/8675)). Fresh (a Rust TUI with TypeScript plugins via Deno) is praised for smoothness but criticized for a 400 MB binary and code that is "mostly AI-generated" ([HN mirror](https://hn.nuxt.dev/item/46135067)).

Funded players win through compatibility with the VS Code ecosystem. Cursor reportedly has $2 billion ARR ([Digital Applied](https://www.digitalapplied.com/blog/ai-coding-ide-landscape-may-2026-10-tools)). Yet even it sits on a VS Code 1.105 base that is "about five months old", and extensions break because of the old API host ([Cursor forum](https://forum.cursor.com/t/urgent-the-1-105-vs-code-base-is-now-5-months-old-we-need-a-modern-upstream-sync/164204)). Void, with ~28k stars, stalled without a funding model ([CodeMySpec](https://codemyspec.com/blog/dead-ai-coding-tools-supermaven-aide-void)). The Xi retrospective offers three lessons worth writing into the architectural principles. Splitting the frontend and core into separate processes "was not a good idea". Asynchrony "made everything more complicated". The plugin interface became "too specialized for syntax highlighting" ([xi retrospective](https://raphlinus.github.io/xi/2020/06/27/xi-retrospective.html)). In practice this means: keep the UI and core in one process, as GPUI already does. Put the plugin boundary where latency is tolerable. Design the API to be general from the start (panels, commands, decorations, agent tools), not for a single feature.

## The best UI extensions describe the interface rather than draw it

A survey of other systems gives an almost unambiguous answer on design. VS Code has two levels: many native declarative surfaces and an escape hatch in the form of webviews. The documentation explicitly warns that webviews have a **high memory cost**, so they should be used sparingly, and TreeView or QuickPick should be chosen for simple UIs ([Mintlify mirror VS Code Webview guide](https://www.mintlify.com/Microsoft/vscode/api/guides/webview)). Webviews also get in the way of agent products because they "cannot modify the editor directly" and go through an event bus with a separate process ([tianpan.co](https://tianpan.co/blog/2026-05-02-ide-plugin-is-the-product-coding-agent-outgrows-editor-api)). Compatibility with VS Code extensions the Theia way is real, but it means years of work on a Node host and a `vscode.*` shim ([Theia FAQ](https://theia-ide.org/docs/faq/)), which fits poorly with a WASM-first design. On top of that, it means inheriting an attacked supply chain: **72+ malicious extensions in Open VSX since January 31, 2026**, abusing `extensionPack`/`extensionDependencies` ([The Hacker News](https://thehackernews.com/2026/03/glassworm-supply-chain-attack-abuses-72.html)), and ~$500k lost to a fake Solidity extension ([The New Stack](https://thenewstack.io/agentic-coding-and-the-weakness-of-extensions-for-ides/)).

The most relevant precedent for "WASM extensions with UI in any language" is **Zellij**. A plugin sends serialized built-in components (Text, Table, Ribbon, NestedList, Button, TextInput, Dropdown) via a private DCS sequence. Styles are given as **semantic theme indices** (0–3 accents, 4 dim, 6 error, 7 success) instead of raw colours, and the host remembers component positions to route clicks ([Zellij: Rendering a UI](https://zellij.dev/documentation/plugin-ui-rendering)). A re-render happens only when `update`/`pipe` returns `true` ([Zellij plugin lifecycle](https://zellij.dev/documentation/plugin-lifecycle.html)). Permissions consist of 17 types and are requested from the user via `request_permission` ([Zellij permissions](https://zellij.dev/documentation/plugin-api-permissions)). Raycast shows the same idea at large scale. A React reconciler produces a JSON tree, the diff is sent as JSON Patch (no patches means no native work), the transport is JSON-RPC, and Swift builds AppKit from it. Raycast gave up on a runtime sandbox and relies on open-source review, which the author himself calls "not a bulletproof solution at all" ([Raycast blog](https://raycast.com/blog/how-raycast-api-extensions-work)). WASM gives you what Raycast didn't have: native UI and a real sandbox at the same time. Figma adds two numbers worth remembering. The first attempt to copy the document into the plugin took **14 seconds of serialization**, and a message across the boundary costs about **0.1 ms per round-trip** ([Figma blog](https://www.figma.com/blog/how-we-built-the-figma-plugin-system/)). The lesson: the heavy model (buffers, syntax trees) should be exposed through handles, not copies, and only the UI layer should cross the boundary. The MCP world, meanwhile, has standardized the opposite pole. **MCP Apps (SEP-1865, status Final)** are pre-declared `ui://` resources with HTML in a mandatorily sandboxed iframe that talk to the host via MCP JSON-RPC. HTML was chosen deliberately as an MVP decision ([SEP-1865](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp)).

Neovim shows how far you can go with primitives (extmarks, virtual text, floats) ([jdhao](https://jdhao.github.io/2021/09/09/nvim_use_virtual_text/)), and where it breaks. avante.nvim builds agent diff review on conflict markers and the `co`/`ct`/`ca` keys, but has to temporarily change `timeoutlen` so that `c` doesn't enter operator-pending mode ([avante docs](https://www.mintlify.com/yetone/avante.nvim/features/diff-management)). The takeaway for the API: the host itself must own key routing in temporary "review modes". Agent products need exactly the surfaces that classic plugin APIs deliberately withhold: hunk-by-hunk approval of changes, multi-pane layouts, streaming of the plan and tool calls, reading the terminal, and policy hooks that must "fire in-process" and cannot be disabled by removing an extension ([tianpan.co](https://tianpan.co/blog/2026-05-02-ide-plugin-is-the-product-coding-agent-outgrows-editor-api)).

### What your API should look like

This adds up to a concrete six-layer architecture. The first three are the core of the sprint; the rest comes later.

| Layer | What it gives the extension | Who renders | Capability |
|---|---|---|---|
| 1. Containers | Dock panel, tab, status bar item, modal | `ExtensionPanel`/`ExtensionItem` in the host | `ui:panel`, `ui:status-bar` |
| 2. Declarative tree | text, button, list (virtualized), table, input, icon, flex container; colours only as theme tokens | Mapping to GPUI elements | (included in layer 1) |
| 3. Host components | `diff-view(old,new,lang)`, `editor-view(buffer)`, `markdown`, accept/reject panel | Zed's existing editor/diff/markdown | `workspace:read-buffers` |
| 4. Buffer decorations | Blocks, inlays, gutter, code-lens actions, anchored to CRDT anchors | The editor's existing block/inlay system | `ui:editor-decorations` |
| 5. Proposed-edits model | Hunks, apply/reject/comment, events from ACP `session/request_permission` | Host; policy and consent also live in the host | `agent:review` |
| 6. Later | Out-of-process sidecar via JSON-RPC with the same schema; opt-in web surface for MCP Apps | The same renderer / sandboxed webview | `process:sidecar`, `ui:web` |

Several decisions here are fundamental. First: **your own WIT package and a separate world** (for example, `fyx:ui@0.1.0`) that only UI extensions implement. That way you don't break existing extensions (nakajimayoshi's argument) and don't conflict with a future official Zed API. Second: the tree is sent as a flat `list<node>` with parent indices, followed by patches (`set-props`, `insert`, `remove`). Virtualized lists request rows in pages (`list-rows(range)`), modelled on `uniform_list` in GPUI. That WIT variants cannot be directly recursive is flagged in the research notes as background knowledge, so verify it against the current component model specification as the very first task of the sprint. Third: **zero WASM calls in `render()`**, no more than one call per input event, debouncing for scroll, hover and text input, a node limit per patch, and auto-disabling slow extensions based on a time budget, as the RFC proposes. Fourth: the UI interface needs its own `Store` or a priority queue. Otherwise a slow `download-file` in the same extension will block click handling, because the loop is serialized. It is also worth shortening the epoch for UI calls, because 100 ms is too much for interactivity. Keep in mind a known wasmtime regression as well: with the `component-model-async` feature, every `call_async` slowed down by **120–150%** on a nop benchmark ([Bytecode Alliance Zulip](https://bytecodealliance.github.io/zulip-archive/stream/225357-git-wasmtime/topic/wasmtime.20.2F.20issue.20.2311209.20.60call_async.60.20performance.20regressi.2E.2E.2E.html)). Fifth: the tree schema should be transport-independent. Then the same tree can come both from a WASM component and from a sidecar process via JSON-RPC, as in Rune. Such a sidecar gives you "any language" without risk: Python, TypeScript or Go can be plugged in even where component model tooling for the language is still immature (the notes did not verify that tooling).

For agent integration the fork gets a ready-made foundation. `agent_servers` launches external ACP agents, `acp_thread` models the conversation and tool calls, `agent_ui` renders the panel, and Zed uses the Rust SDK `agent-client-protocol` 5.3.0 with the `unstable` and `unstable_protocol_v2` features ([crates.io agent-client-protocol](https://crates.io/crates/agent-client-protocol)). The ACP Registry, launched on January 28, 2026 together with JetBrains, works on the "implement once, works everywhere" principle ([Zed blog: ACP Registry](https://zed.dev/blog/acp-registry)). The registry snapshot from August 28 contains **39 agents**: Claude Agent, Codex, Gemini CLI, Cursor, GitHub Copilot, Junie, goose, OpenCode and others ([ACP registry JSON](https://cdn.agentclientprotocol.com/registry/v1/v2026.08.28-e9b1b2d/registry.json)). So your novelty lies not in "supporting agents" but in the fact that **UI extensions can subscribe to agent session events and render their own review, trace and plan**, while a permission request from the agent goes through the host's proposed-edits model. Policy and consent stay in the host. The `unstable_protocol_v2` feature hints that the protocol will still change, so bind to the SDK, not to raw JSON.

### Adapter for VS Code extensions (added after discussion)

Full VS Code compatibility is unrealistic: it is a Node host and a shim for hundreds of `vscode.*` functions (the Theia path, years of work), Microsoft's proprietary extensions (Live Share, Remote Development, etc.) are licensed only for VS Code, the official Marketplace is available only to Microsoft products, and Open VSX has received 72+ malicious extensions since January 31, 2026. A partial adapter, on the other hand, gives decent coverage at a low cost. It has three levels:

1. **A converter for declarative content.** Themes, icons, snippets and keybindings from VS Code extensions are automatically converted into Fyx formats (Zed already has an importer for themes). Language extensions are mostly wrappers over LSP/DAP, which the fork already supports natively.
2. **A sidecar host with a partial API.** A separate Node process runs real `.vsix` files unchanged, but implements only a subset of `vscode.*`: commands, settings, the workspace file system, reading and editing documents, diagnostics, formatting, the status bar, QuickPick, Output, decorations and TreeView. Calls go through the same JSON-RPC tree schema as layer 6, and TreeView maps almost directly onto the declarative tree. Unimplemented APIs return an explicit error. The process runs with minimal privileges; whether Node's permission model is sufficient for that needs to be checked.
3. **Webview — only later and opt-in**, through the same surface as MCP Apps.

In the sprint the adapter is a separate workstream, W8, which doesn't block the main line (see the workstream table).

## Three paths, one winner: a fork following the Brave pattern

| Criterion | Zed fork | New editor on GPUI | Upstream-first |
|---|---|---|---|
| What you get for free | The whole editor, LSP, git, terminal, debugger, ACP + registry, ~1,000 extensions, Windows | GPUI, `sum_tree`, utilities, `extension_api` (WIT/SDK) | Everything, if merged |
| What has to be written | UI host + WIT + hooks | Rope/buffer, editor, multi_buffer, project, LSP client, workspace/dock, UI kit, agent panel | The same as in the fork, but by Zed's rules |
| Product license | GPL-3.0 (commercial use OK, proprietary not) | Any, as long as GPL code isn't copied | GPL + CLA in Zed's favour |
| Control over the API | Full | Full | None: the work "has to be done by the team" |
| Time to demo | Hours–days | Weeks–months | Undetermined |
| Main risk | Drift from weekly upstream | Getting stuck like Lapce/Xi | Merge rejection |

Upstream-first doesn't work as the main path. Zed requires a CLA and merges "about half" of PRs. Among the things usually rejected are explicitly named giant refactors, non-trivial changes without tests and "anything that looks entirely AI-generated" ([Zed CONTRIBUTING.md (mirror)](https://git.secluded.site/zed/blob/main/CONTRIBUTING.md?source=1)). The maintainer has already said that the visual API should be led by the team. The CLA grants Zed Industries an irrevocable license **with the right to sublicense**, and counts even feedback and tracker posts as a "contribution". Employees need their employer's permission or a corporate CLA ([Zed CLA](https://zed.dev/cla)). If you work on this during working hours or under contract, take that into account. The "from scratch on GPUI" path gives licensing freedom, but at the cost of rewriting everything above `sum_tree`. Moreover, GPL code can only be studied as a source of ideas, because a close translation risks becoming a derivative work. For a solo developer directing agents, that is a repeat of the Xi and Lapce scenario. **The recommendation is a hybrid**. Fork now. Later, small, tested, human-reviewed PRs with hooks go upstream (for example, dynamic panel registration instead of the static one in `zed.rs`), shrinking the fork's diff. If Zed ever ships an official API, your separate WIT namespace will let you migrate without breakage.

### How not to become a second Cursor

Long-lived forks of fast-moving projects survive when the diff is small and mechanical. Brave keeps its code in a separate `src/brave` tree, pins the Chromium branch in `package.json` and applies `.patch` files during `sync` with `--force` and `--init` modes ([brave-core README](https://cdn.jsdelivr.net/gh/brave/brave-core@master/README.md)). VSCodium patches upstream at build time, pins the tag and commit in `upstream/stable.json`, and moves divergences into config. `product.json` changes `updateUrl`, telemetry endpoints are replaced with `0.0.0.0`, and the marketplace is redirected to Open VSX ([DeepWiki: VSCodium](https://deepwiki.com/VSCodium/vscodium/1.2-key-features-and-differences-from-vs-code)). LibreWolf builds "settings + source" in CI with the same kind of patching ([LibreWolf source-doc](https://ark.sudovanilla.org/Korbs/LibreWolf/raw/branch/main/assets/source-doc.md)). The opposite example is Cursor, which fell five months behind. Eclipse puts it this way: "a fork seems fast now, but you pay the debt back with interest" ([Eclipse blog](https://blogs.eclipse.org/post/thomas-froment/why-cursor-windsurf-and-co-fork-vs-code-shouldnt)).

For Zed this translates into five rules. First, pin a **stable tag** (currently the 1.28.x line), not main. Second, put all new code in new crates (`crates/ui_ext`, `crates/ui_ext_host`, `crates/ui_ext_sdk`, `crates/agent_review`), and keep edits to upstream crates (`workspace`, `extension_host`, `zed`, the workspace `Cargo.toml`) down to a few lines of hooks, each with a marker comment. Third, do rebranding, URLs and disabling services through default settings, environment variables and feature flags, not scattered edits. Fourth, **rebase on every release while the diff is small**, because every skipped week costs more. Fifth, set up a CI job that tries weekly to apply your stack onto the newest tag and opens an issue on conflict. License the guest SDK under Apache-2.0, as Zed does with `extension_api` and Rune does with its SDK. Then extension authors, including proprietary ones, don't fall under the GPL.

### Name, trademark and distribution

Zed's licenses **grant no rights to trademarks, names or logos** ([Zed Software Overview](https://zed.dev/software-overview)). The brand guidelines forbid any use that "may falsely suggest an official affiliation" or cause confusion ([The Zed Brand](https://zed.dev/brand)). The US application for the "ZED" mark, according to a third-party aggregator, has pending/suspended status rather than registered ([Gleanmark](https://gleanmark.com/trademark/uspto-97583804)). However, there are no specific rules for wording like "based on Zed", so it is safer not to use "Zed" in the name at all. The practical checklist: a new name and icons; a new bundle ID, data and config directories and a URL scheme instead of `zed://`, so the fork doesn't conflict with an installed Zed (the VSCodium pattern with `~/.vscode-oss`); license headers stay in every file; license notices are generated via `cargo-about`, as in Gram ([Gram on Codeberg](https://codeberg.org/mosen/gram)); the complete corresponding source is published for every binary. If the build contacts Zed's services, Zed's ToS apply to them even for a build from source ([Zed Software Overview](https://zed.dev/software-overview)). So the decision whether to use their extension registry has to be a conscious one. macOS requires an Apple Developer account, signing and notarization via `script/bundle-mac`; Windows requires a signing certificate. The author of Gram hasn't tried building on a machine with less than 16 GB of RAM ([Gram on Codeberg](https://codeberg.org/mosen/gram)). Postpone notarization for the sprint: ad-hoc signing is enough for your own machines.

**Chosen name: Fyx** (pronounced "fix", a pun on "fix": an editor you fix up to suit yourself). Brand decisions:

- **Terminal command:** `fyx .` — no conflicts with known CLIs found.
- **Packages:** `fyx` is free on crates.io and PyPI; on npm there is only an empty placeholder from 2022, so JS packages are published under the `@fyx/...` scope. Guest SDK: `fyx-sdk` (Apache-2.0).
- **WIT namespace:** `fyx:ui@0.1.0`.
- **Bundle ID, directories, URL scheme:** `dev.fyx.Fyx`, `~/.config/fyx`, `fyx://`, so as not to conflict with an installed Zed.
- **Check manually before starting:** github.com/fyx (fallbacks `fyx-editor`, `fyxdev`, `getfyx`) and the domains fyx.dev, fyx.sh, getfyx.com.
- **Trademarks:** in the US there are several FYX marks, including in software classes 9 and 42 (Trac Interstar LLC, a truck repair service; FYX Gaming). The markets are different, so the risk for an open-source editor is low, but before any commercialization a consultation with a trademark lawyer is needed.
- **Rejected options and reasons** are collected in the table "Names for the editor: vetted candidates". In particular: Tersa (Hayden Bleasel's AI workflow), Graft (NanoNets), Trellis, Kern, the "X Code" format (crowded with AI agents), LF Code ("LF" = line feed and Linux Foundation), Lex Code (Lex.page, Unix `lex`), LX Code and LXE (hard to pronounce).

## A 36-hour sprint: eight workstreams and one narrow slice

Two large public experiments converge on one point: a swarm's throughput comes from **many independent tasks and a nearly perfect automated verifier**. Anthropic built a C compiler of ~100k lines of Rust with **16 parallel agents in ~2 weeks for a little under $20k**. Each agent worked in its own container and claimed tasks with lock files. When new features started breaking old ones, strict CI was the saviour. Parallelism collapsed where the task was monolithic: all 16 agents hit the same bug and overwrote each other's fixes ([Anthropic Engineering](https://anthropic.com/engineering/building-c-compiler)). Cursor found that a shared file with locks gives 20 agents the productivity of 2–3. The scheme that worked best was "planners → workers → a judge per cycle" with fresh restarts, while a separate integrator became a bottleneck. The key thesis: "prompts matter more than the harness" ([Cursor blog](https://cursor.com/blog/scaling-agents)). The tools for this already exist in Claude Code. `claude --worktree <name>` creates an isolated worktree. For subagents there is `isolation: worktree`. `worktree.baseRef: "head"` lets you branch off unmerged work, `.worktreeinclude` copies gitignored files, and `WorktreeCreate` hooks let you place worktrees on another disk ([Claude Code docs: worktrees](https://code.claude.com/docs/en/worktrees.md)).

Rust's main physical constraint is disk and locking. **Every `cargo build` creates 2–10 GB of intermediate files**, and one project with 26 worktrees grew to 105 GB (5.9–28 GB per directory). A shared `target/` serializes builds and can corrupt `.rmeta`/`.rlib` ([rust-lang/cargo #16804 (mirror)](https://github-users.yhajoa.workers.dev/rust-lang/cargo/issues/16804)). So each worktree needs its own `CARGO_TARGET_DIR`, ideally sccache and mold on Linux, and `cargo check` for iterations. `Cargo.lock` remains a file at elevated risk of conflicts ([Claudio: Rust development](https://iron-ham.github.io/claudio/tutorials/rust-development)). Zed specifics: don't open the Zed repository in a dev build, because it will start rebuilding the root crates, and on "Too many open files" in tests switch to `cargo-nextest` ([Zed docs: Building for macOS](https://zed.dev/docs/development/macos.md)). Hence the realistic figure: **6–8 compiling agents on one workstation** plus as many non-compiling agents as you like. It is the latter that let you use the limit to the full without killing the disk. There is no public data on sprints specifically on the Zed codebase, so this estimate is an extrapolation.

A base config worth putting into the fork in the very first hour (`.cargo/config.toml` on Linux; on macOS remove the mold line):

```toml
[build]
rustc-wrapper = "sccache"
[target.x86_64-unknown-linux-gnu]
rustflags = ["-C", "link-arg=-fuse-ld=mold"]
[profile.dev]
debug = "line-tables-only"
```

### Schedule and workstream allocation

**Phase 0 (hours 0–2): interface freeze.** You and a planner agent clone Zed at the stable tag, do one "warm" build in the main checkout and prepare copies of the target directory for the worktrees (reflink or `cp -c`, so as not to start from a cold build). The planner writes `PLAN.md`, `ARCHITECTURE.md`, a `tasks/` task directory, **the frozen WIT file of the UI world** and empty crate skeletons already added to the workspace. After that, only the integrator may edit the workspace `Cargo.toml`, `Cargo.lock` and the WIT. The reason is that changing shared interfaces is exactly the "monolithic task" that serializes the swarm. **Phase 1 (hours 2–14)** — parallel workers. **Phase 2 (hours 14–20)** — first integration, launching the app, a judge pass, fresh restarts of drifting agents. **Phase 3 (hours 20–30)** — second wave: agent change review, decorations, polish. **Phase 4 (last 6–8 hours)** — integration only, manual testing in the running editor and your review pass.

| Workstream | Owns (directories) | Deliverable | Depends on |
|---|---|---|---|
| W0 Integrator/CI (lead + you) | `Cargo.toml`, `Cargo.lock`, WIT, `integration` branch, `script/gate.sh` | Gate: `cargo check` + `clippy` + `nextest -p` on changed crates; full `zed` build on a schedule; red doesn't get merged | — |
| W1 Rebranding and de-clouding | `crates/zed` (brand/paths only), default settings, `client` (URL stub) | New name, bundle ID, data directories, URL scheme; telemetry off; collab/sign-in hidden; auto-update off | W0 |
| W2 WIT and host bindings | `crates/ui_ext` (types, tree model, patches), a module in `extension_host` | The `fyx:ui@0.1.0` world, bindings, its own queue or Store for UI, version gating without the nightly restriction | Frozen WIT |
| W3 Renderer and containers | `crates/ui_ext_host` | `ExtensionPanel: Panel`, mapping of 5–7 primitives to GPUI, theme tokens, event routing by ID, one registration hook in `workspace` | W2 (types) |
| W4 Guest SDK and demos | `crates/ui_ext_sdk`, `extensions/demo_*` | Rust SDK (Apache-2.0); demo 1: counter/list; demo 2: workspace TODO aggregator; build to `wasm32-wasip2` | WIT |
| W5 Agent change review | `crates/agent_review` + a thin hook in `acp_thread`/`agent_ui` | Host proposed-edits model; diff view on the existing editor/diff; hunk-by-hunk accept/reject; invoked from ACP `request_permission` | W3 (container) |
| W6 Decorations (stretch) | a module in `ui_ext_host` + a hook in `editor` | A block decoration or inlay, anchored, from extension data | W3 |
| W7 Judge/reviewer/docs (non-compiling) | `docs/`, `tasks/`, PR review | Checking WIT conformance, finding duplication, updating `PLAN.md`, manual test scenarios, checking recursion in WIT | — |
| W8 VS Code adapter (parallel, non-blocking) | `tools/vsix-convert`, `sidecars/vscode-host` (Node/TS) | Converter for themes/snippets/keybindings; Node host with a shim for the 15–20 most used `vscode.*` APIs; a run of 10–20 simple extensions from Open VSX and a coverage report | Tree schema (W2), the JSON-RPC transport can be mocked |

To use up the limit before the reset, it pays most to scale the workstreams that don't compile, or compile little: W7, a component model spec researcher, demo extension authors (guest crates are small and build to WASM quickly), an agent writing tests for `ui_ext` without GPUI, and also workstream W8: its Node part doesn't touch the Rust build at all. Run the heavy workers W3, W5 and W6 only with `cargo check -p <crate>`, and let only W0 do the full `zed` build. Each agent keeps a progress file and writes a short log with "ERROR" on the same line, because Anthropic's agents, starting from scratch every time, lived on exactly such files. The reference for agents, the analogue of the "GCC oracle", is Zed's existing panels: `ProjectPanel` and `AgentPanel` show how to implement `Panel` correctly.

### What can realistically be done and what will break

The realistic result of two days is: your own WIT world and bindings, a crate that maps the declarative tree to GPUI, a dock panel showing 1–2 demo extensions, a "click → WASM callback → new patch → repaint" event loop, a rebranded build without the cloud, and basic hunk-by-hunk approval of changes from an ACP agent. All of it behind a feature flag and tested on one OS. In parallel, from workstream W8: a converter for VS Code themes and snippets, a Node host prototype with a partial API, and a report on which of the 10–20 tested extensions work. Out of scope for the sprint: a security model with permission prompts, ABI stability, frame budgets, the sidecar transport, a second SDK language (possible as a stretch, but not promised), Windows/Linux builds, notarization and a marketplace. The things most likely to break are these. First, re-entrancy and borrow errors when updating GPUI entities from async WASM callbacks. Second, version mismatches of wasmtime and WIT with the ones pinned in Zed. Third, the dev extension loading path. Fourth, concurrent edits to `Cargo.lock` or the WIT. Fifth, and most insidious, the "tests are green but the feature doesn't work" situation: Anthropic explicitly warns that green tests rarely mean readiness ([Anthropic Engineering](https://anthropic.com/engineering/building-c-compiler)). A separate reputational risk: AI-written forks and editors already meet community scepticism about quality, and Zed upstream rejects PRs that "look entirely AI-generated". So everything that goes public must pass your manual review.

## Conclusion

The most valuable thing this research shows: **the market gap and the technical difficulty coincide at one point**. Zed deliberately routes agents through ACP rather than through UI extensions, and is shrinking the extension surface. Forks only cut features or bake in their own panels. Rune put the agent on the extension boundary, but via gRPC and only in Go. No one has yet built a native, themed, sandboxed UI API in which agent review is a first-class host object. That is what becomes the product, not "yet another Claude panel" that upstream will absorb anyway. It follows that the fork should be measured not by the number of features but by the size of the diff outside its own crates. As long as that is a few dozen lines of hooks, the weekly rebase stays a routine that can be handed to an agent. As soon as hooks spread across `editor` and `workspace`, you repeat the fate of Zedless and Cursor.

The second practical conclusion concerns the sprint: the constraint is not tokens but the physics of Rust. So the most effective way to "burn" the limit usefully is to freeze the interfaces in two hours, and then distribute the work so that most agents write specs, SDKs, demos, tests and reviews, while only a few compile. If in two days you have one panel rendering a WASM tree and one hunk-by-hunk approval of agent changes, you will have more than any public Zed fork has today, and enough to decide whether it is worth building further.
