# Worktree і паралельні агенти у Fyx: дослідження (2026-11-19)

Питання: чи варто робити нативну роботу з git worktree, де видно, який агент у якому worktree, з
зручним перемиканням і переглядом. Якщо так, то як зробити це добре й під контролем.

> **Оновлення:** розділ 8 (оцінка доцільності) звужує план із розділів 5–6. Чинний висновок — у розділі 8.

**Коротко (перше дослідження):** робити варто, але не з нуля. Zed 1.29.2 (наша база) уже має worktree, бічну панель
тредів і перемикання. Бракує трьох речей: старту агента «одразу в новому worktree», огляду всіх
worktree з їхнім станом і циклу «переглянути → злити → прибрати». Цей цикл — пряме продовження нашого
`agent_review`, і тут Fyx може бути кращим за Zed, а не копією.

## 2. Чого бракує (код + скарги в issue Zed)

1. **Немає «новий тред у новому worktree» одним кроком.** Зараз треба спершу створити worktree (меню
   «+» → Create New Worktree), а тоді почати тред. Налаштування на кшталт «нові треди завжди
   ізольовані» немає. У Claude Desktop, Codex і VS Code для цього є перемикач під полем вводу.
2. **Завжди detached HEAD.** Гілку треба створювати вручну, а база — лише поточна або гілка за
   замовчуванням ([#65586](https://github.com/zed-industries/zed/discussions/65586)). На рівні git
   `CreateWorktreeTarget::NewBranch { branch_name, base_sha }` уже є (`crates/git/src/repository.rs:310`),
   але інтерфейс його не використовує.
3. **Немає копіювання gitignored-файлів** (`.env`, локальні конфіги)
   ([#59453](https://github.com/zed-industries/zed/issues/59453)). Галузевий стандарт —
   `.worktreeinclude` (Claude Code, Codex, Conductor, VS Code).
4. **Немає огляду worktree.** Бічна панель групує за проєктом, а не за worktree
   ([#59141](https://github.com/zed-industries/zed/discussions/59141)). Не видно ahead/behind, брудних
   файлів, розміру на диску, PR. Треди в закритих workspace не мають живого статусу.
5. **Немає циклу «переглянути → злити → PR».** Є `git::DiffBranch` (diff від merge-base), але
   немає «злити назад» і «створити PR». Найпопулярніший запит у Zed — коментарі до diff, які йдуть
   назад агенту ([#59157](https://github.com/zed-industries/zed/issues/59157), 169 реакцій).
6. **Прибирання надто агресивне або його немає.** Архівування видаляє worktree, а користувачі хочуть
   довгоживучі ([#56758](https://github.com/zed-industries/zed/discussions/56758)). Worktree, створені
   поза Zed (наприклад, `.claude/worktrees/` від Claude Code), ніколи не прибираються. Немає ліміту
   кількості й немає `git worktree lock`, поки агент працює.
7. **Дрібниці:** шлях подвоює назву проєкту `worktrees/fyx/<rand>/fyx`
   ([#58055](https://github.com/zed-industries/zed/issues/58055)), що боляче для MAX_PATH на Windows;
   `NextThread`/`PreviousThread` не мають клавіш; git panel ламається в не-main worktree
   ([#33764](https://github.com/zed-industries/zed/issues/33764)).
8. **Немає поняття «хто власник».** Реєстр `created_worktrees` знає тільки «створив Zed». Користувач,
   агент і зовнішній CLI не розрізняються.

Висновок ринку: створити worktree вже вміють усі. Відрізняються **огляд**, **повернення змін** і
**керована політика прибирання**.

## 4. Чи варто це робити у Fyx

**За:**
- Це прямо підсилює головну фішку Fyx — `agent_review`. Worktree дає агенту ізоляцію, а review
  вирішує, що з неї повертається в основну гілку.
- Більша частина механіки вже є в upstream, тож нам лишається тонкий шар зверху.
- Ми самі живемо в цьому сценарії: рій W0–W10 — це саме «багато агентів у багатьох worktree».

**Проти / ризики:**
- Zed дуже активно розвиває цю зону (0.233 → 1.29 за пів року). Якщо патчити `sidebar.rs` чи
  `agent_panel.rs`, кожен rebase болітиме. Тому: власний crate, мінімальні хуки `fyx:`.
- Частина пунктів (detached HEAD, подвоєний шлях, гілка в git panel) — це баги, які краще виправити
  в upstream. Але PR у zed-industries/zed — рішення тільки ваше.
- Rust-проєкти в worktree — це холодний `target/` (у нас 27 ГБ) і переіндексація rust-analyzer. Без
  продуманого setup (sccache, свій `CARGO_TARGET_DIR`, підігрітий кеш) зручність закінчиться на
  першій збірці.

**Рішення:** робити поетапно, починаючи з дешевого, і вбудувати в review-цикл.

## 5. Як зробити: дизайн

### 5.1 Принципи
- **Worktree — першокласний об'єкт поряд із тредом.** Модель: `репо → worktree → (гілка, треди,
  термінали, review, PR)`. Сьогодні в Zed головні треди, а worktree — лише чип.
- **Нічого не губиться.** Перед будь-яким видаленням — знімок (механізм Zed уже є). Брудні,
  незапушені, закріплені й чужі worktree автоматично не видаляються ніколи.
- **Агент не виходить зі свого worktree.** Запис за межі кореня треду блокується через `fyx_guard`,
  так само як зараз блокуються приватні файли. Зміни в main checkout — тільки через review/merge.
- **Явний власник.** Кожен worktree має мітку: `user`, `agent:<thread>`, `external` (створив CLI
  поза Fyx), `unmanaged`. Від мітки залежить, що Fyx можна робити автоматично.
- **Політика в репо, вибір у користувача.** `.fyx/worktrees.toml` (setup, include, порти, база,
  префікс гілки) комітиться; ліміти й авто-прибирання — у налаштуваннях користувача.

### 5.2 Що бачить користувач
1. **Перемикач під полем вводу агента:** `Local | New worktree ▾` (база: поточна / default / будь-яка
   гілка). Налаштування `agent.new_thread_isolation: "local" | "worktree" | "ask"`.
2. **Панель Worktrees** (док, поруч із бічною панеллю тредів). Один рядок на worktree:
   - назва + гілка + база, власник (іконка: людина / агент / зовнішній);
   - агенти в ньому зі статусом (виконується / чекає дозволу / готовий до review / помилка);
   - `+12 −3 файли`, ahead/behind відносно бази, брудний чи ні, розмір на диску, стан PR/CI;
   - дії: Відкрити, Review, Merge…, PR, Pin, Архівувати, Видалити.
   - групування: за worktree (за замовчуванням) або за статусом (простий kanban: Працює / Чекає мене
     / Готово до review / Злито).
3. **Перемикання:** клік або `ctrl-tab` (як зараз), плюс `alt-1..9` по закріплених worktree, плюс
   дефолтні клавіші для `NextThread/PreviousThread`. Стан кожного workspace живе (MultiWorkspace),
   тому перемикання миттєве.
4. **Review & Merge** (з `agent_review`): diff worktree проти merge-base, прийняття/відхилення
   hunk'ів, коментарі до рядків, які йдуть агенту новим повідомленням (#59157). Потім
   `Squash into <base>` / `Merge` / `Rebase` / `Create PR` (через `gh`). Pre-commit хуки не
   пропускаються. Після merge — пропозиція (або політика) архівувати.
5. **Сповіщення:** «агент у `brave-otter` чекає дозволу» з кнопкою переходу; лічильник «чекають мене»
   у статус-барі.

### 5.3 Під капотом
- **Новий crate `fyx_worktrees`** (GPL, Fyx-owned). Він:
  - тримає власний реєстр: власник, pin, політика, порти, PR (поверх `created_worktrees` Zed, не
    замість нього);
  - створює worktree через `GitStore` з `CreateWorktreeTarget::NewBranch` (`fyx/<name>` від свіжого
    `origin/<base>`), копіює файли з `.worktreeinclude`, виділяє блок портів (`FYX_PORT`..`+9`),
    запускає setup (наявний хук `create_worktree` + `.fyx/worktrees.toml`);
  - ставить `git worktree lock` на час роботи агента й знімає застарілі lock;
  - проводить прибирання: ліміт N, вік, «злитий → архів», знімок перед видаленням, ніколи не чіпає
    `external/unmanaged`, брудні та закріплені;
  - малює панель Worktrees (нативний GPUI-`Panel`, як `ProjectPanel`).
- **Хуки в upstream (`fyx:`), орієнтовно 4–6 місць:**
  - перемикач `Local | New worktree` у полі вводу агента (`agent_ui`);
  - реєстрація панелі (`zed.rs`);
  - виклик `fyx_worktrees` на створенні/архівуванні (`worktree_service.rs`, `thread_worktree_archive.rs`);
  - перевірка «запис лише в межах worktree треду» (`fyx_guard`/`agent_review`).
- **Для Rust-репо** (і самого Fyx) — setup за замовчуванням: `CARGO_TARGET_DIR` поза worktree, але
  свій на кожен, опційний «теплий старт» копією `target/` (як у нашому PLAN), sccache. Явне
  попередження про розмір. Симлінк спільного `target/` не робимо: блокування Cargo й змішування
  build-script.
- **Windows:** корінь коротший і без подвоєння (`D:\wt\fyx\brave-otter`), перевірка довжини шляху до
  створення; при видаленні junction видаляється тільки сам лінк.
- **API для розширень (пізніше, WIT 0.2):** `workspace:worktrees` (лише читання: список, статус,
  diff-stat; події) — щоб extension міг зробити свій kanban чи дашборд. Зміни WIT — тільки W0.

### 5.4 Контроль і безпека
- Агентське створення worktree (`create_thread` tool) вмикаємо Fyx-налаштуванням, а не staff-прапорцем,
  і тільки з підтвердженням: картка «агент хоче створити 3 worktree для best-of-n» → Дозволити.
- Ліміти: максимум worktree на репо, максимум одночасних агентів, бюджет диска (попередження).
- Trust: новий worktree успадковує довіру джерела (Zed так і робить); `.fyx/worktrees.toml` з
  setup-командами виконується лише в довіреному репо й показує команди перед першим запуском.
- Worktree — це ізоляція файлів, а не безпека. Мережу й процеси обмежує окремий шар (W9), про що
  чесно сказано в UI.

## 8. Чи реально доцільно (друге дослідження, 2026-11-19)

**Вердикт: повноцінний менеджер worktree в ядрі робити не варто. Варто зробити вузький шар із трьох
частин:**
1. огляд усіх worktree, разом із чужими, і того, який агент де працює;
2. review і merge гілки worktree через `agent_review`;
3. облік вартості для Rust (диск, `target/`).

Плюс дешеві виправлення у файлах, які в upstream міняються рідко.

### 8.1 Факти «проти» повного менеджера
- **Основа вже є і стала стандартом.** Створення, перемикання, бічна панель, архів зі знімком є в Zed
  з квітня 2026, а також у Claude Code, Codex, VS Code, JetBrains і Cursor. Повторно це будувати —
  нуль переваги.
- **Попит вузький.** Телеметрія Jellyfish (≈19 млн рядків активного часу Claude Code, березень 2026):
  у 84% користувачів пік — 1–2 агенти одночасно, лише 6,1% активних хвилин припадає на більше ніж
  одного агента. Опитування Stack Overflow (травень 2026): 69% працюють з одним агентом.
  ([Jellyfish](https://jellyfishresearch.substack.com/p/measuring-ai-agent-concurrency),
  [SO](https://stackoverflow.blog/2026/05/27/agents-on-a-leash-agentic-ai-remains-mostly-monitored-at-work))
- **Продуктивність паралельності не доведена.** METR (лютий 2026) прямо пише, що не може коректно
  виміряти людей із кількома агентами одночасно. Практики та опитування BCG/HBR сходяться на стелі в
  2–4 агенти через втому від нагляду. ([METR](https://metr.org/blog/2026-02-24-uplift-update/))
- **Агенти власника живуть поза Fyx.** З 13 worktree цього репо 11 створив Claude desktop
  (`.claude/worktrees/`), жоден не створив редактор. Він сам створює й прибирає свої worktree.
  Перемикач «New worktree» в агенті Fyx нашому реальному процесу нічого не дає.
- **Найдорожчі для хуків файли — найгарячіші в upstream.** Комітів за 6 місяців до v1.29.2:
  `agent_panel.rs` — 96, `git_store.rs` — 72, `sidebar.rs` — 62, `title_bar.rs` — 27,
  `multi_workspace.rs` — 20. Zed випускає реліз щотижня, тож кожен хук там — регулярний конфлікт при
  rebase. Водночас `worktree_service.rs` — 6, `worktree_picker.rs` — 9, `thread_worktree_archive.rs` — 4:
  їх чіпати дешево.
- **Частина прогалин закривається в upstream і без нас** (відкриті community PR, ще не переглянуті):
  групування тредів за worktree ([#65988](https://github.com/zed-industries/zed/pull/65988)),
  довільна папка worktree ([#64384](https://github.com/zed-industries/zed/pull/64384)), локальна
  default-гілка як база ([#66670](https://github.com/zed-industries/zed/pull/66670)). Їх не будуємо;
  якщо зіллють, отримаємо безкоштовно.

### 8.2 Факти «за» вузький шар
- **Ніхто не показує чужих агентів.** Zed бачить лише свої треди й CLI-агентів у своєму терміналі.
  Claude Code desktop, запущений окремо, для нього невидимий. При цьому прив'язка є на диску:
  `~/.claude/projects/<шлях-worktree-з-дефісами>/<session>.jsonl` (час зміни = активність), у Codex —
  `cwd` у метаданих сесії. Рядок «`fyx-w3-renderer` · Claude Code · активний 2 хв тому · +340/−12 ·
  15 ГБ target» — саме те, що просив власник, і такого немає ні в кого.
- **Вузьке місце — review, а не створення.** Faros: час review +91% (2025) і медіана в review +441%
  (2026, ще не перевірено). Найпопулярніший запит у Zed — коментарі до diff, які йдуть назад агенту
  (#59157, 169 реакцій). Це головна фішка Fyx (`agent_review`), тож тут ми природно сильніші.
- **Для Rust ціна worktree — це диск і холодна збірка.** У нас кожен робочий `target/` сягає 1–15 ГБ
  (`D:\fyx-targets\w2c` 15 ГБ), основний — 27 ГБ. sccache між worktree для Rust майже не влучає, бо
  в ключах абсолютні шляхи. Ніхто з конкурентів цього не показує. Показати розмір, `CARGO_TARGET_DIR`
  і дати «очистити target» — дешево й корисно.

### 8.3 Що робимо і чого ні

| | Що | Де | Оцінка |
|---|---|---|---|
| ✅ | **Панель Worktrees, лише читання.** Усі `git worktree list` відкритих репо; власник: Fyx / Claude Code / Codex / вручну; активність зовнішньої сесії; брудний/ahead/behind; розмір worktree і його `target/`; дії Відкрити (наявний `SwitchWorktree`) і «Diff від бази» (наявний `DiffBranch`) | новий crate `fyx_worktrees`, один хук реєстрації в `zed.rs` | 3–5 днів |
| ✅ | **Review & merge гілки worktree:** hunk'и через `agent_review`, коментарі (у свого агента — повідомленням; для зовнішнього — файлом/буфером обміну), squash/merge у базу, хуки pre-commit не пропускаються | `fyx_worktrees` + `agent_review` | 1–2 тижні |
| ✅ | **Дешеві виправлення в холодних файлах:** гілка `fyx/<name>` замість detached, `.worktreeinclude`, без подвоєння назви в шляху | `worktree_service.rs`, `git_store.rs` (шлях) — 2–3 хуки `fyx:` | 1–2 дні |
| ⏸ | Перемикач `Local / New worktree` в агенті, kanban, best-of-n, агент сам створює worktree | `agent_panel.rs` (найгарячіший) | лише якщо власник почне запускати агентів усередині Fyx |
| ❌ | Групування бічної панелі за worktree, власна політика автоприбирання, lock, порти | дублює upstream/Claude Code | ні |

**Чому не розширення `fyx:ui`:** у WIT 0.4 немає списку worktree, перемикання workspace і статусу
сесій. До того ж читання `~/.claude` — це доступ поза worktree, якого розширенням давати не можна.
Тому дані й дії — у host-crate. Інтерфейс можна пізніше віддати розширенню через read-only
`workspace:worktrees`, коли дійде до WIT 0.5.

### 8.4 Як перевірити, перш ніж вкладатися
1. Тиждень користуватися тим, що вже є (`shift-alt-w`, `ctrl-tab`, Changes since branch) і записувати,
   чого бракує. Якщо бракує лише «бачити Claude-сесії й розміри» — робимо тільки першу частину.
2. Прототип першої частини (панель, лише читання) — найдешевша гіпотеза, яку легко викинути: один хук,
   власний crate, upstream майже не зачіпається.
3. Review & merge беремо, тільки якщо після прототипу review гілок справді йде через Fyx, а не через
   GitHub чи Claude desktop.
