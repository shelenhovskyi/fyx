# Writing a Fyx UI extension

This guide is for authors of Fyx UI extensions: WASM components that add native, themed panels and
status bar items to Fyx through the `fyx:ui@0.1.0` API. The whole workflow runs through one tool,
`fyx-ext`: create, build, run in Fyx, check, test and package. The guide also covers the
manifest, the mental model, and a complete counter walkthrough.

Related pages:

- [SDK reference](sdk-reference.md): the Rust SDK `ui_ext_sdk`, item by item, with the host rule
  each one enforces.
- Generated API reference, regenerated by `script/fyx-api-docs` and checked for drift by a test:
  [the `fyx:ui` WIT world](api/fyx-ui-0.1.0.md), [every public `ui_ext_sdk` item](api/ui_ext_sdk.md),
  and [the test harness `fyx_ext_harness`](api/fyx_ext_harness.md). The script also builds the
  rustdoc of both crates.
- [Limits and gotchas](limits-and-gotchas.md): time budget, caps, rows, inputs, icons, versions,
  and what is planned for 0.2.

> **Status: prototype.** `fyx:ui@0.1.0` is frozen, but it is not a stable API, and 0.2 is
> being implemented. Extensions are written in Rust; TypeScript is deferred until after 1.0. UI
> extensions load from dev folders, `.fyxext` packages installed from disk and an environment
> variable (see "Installing as a dev extension"); there is no public registry yet. The SDK and
> `fyx-ext` are not published to crates.io, so they come from a Fyx checkout, and `diff-view` is
> a placeholder. These docs describe what the code on the
> `integration` branch does, limits included.

Rule sources are cited in HTML comments as `file:line`, so you can check every claim against the
code.

## What a UI extension is

A UI extension is a WebAssembly component (target `wasm32-wasip2`) that implements the
`fyx:ui/ui-extension` world in `crates/ui_ext/wit/fyx-ui.wit`. It contributes **surfaces**:

- **Panels** in the left, right or bottom dock, each with a dock icon and a default size.
- **Status items** on the left or right of the status bar.

<!-- crates/ui_ext/wit/fyx-ui.wit:134-159 -->

The extension never draws. It describes each surface as a tree of **nodes** (flex containers,
text, buttons, inputs, virtualized lists and tables, icons, markdown, and a diff view). Fyx keeps
that tree and renders it with its own GPUI components, coloured by the active theme. When the user
clicks or types, Fyx calls the extension once, and the extension answers with **patches** to the
tree.

<!-- crates/ui_ext/wit/fyx-ui.wit:81-118, 175-190 -->

A UI extension is separate from a Zed-style extension (`zed:extension`). It runs in its own
wasmtime `Store` with its own call queue, on its own engine. A slow call in the same extension's
`zed:extension` component therefore never delays click handling. The `[fyx_ui]` manifest table is
ignored by upstream Zed's manifest parser, so one directory can hold both kinds.

<!-- crates/ui_ext_wasm/src/ui_ext_wasm.rs:3-9, 137-138 -->

The sandbox: the component gets WASI p2, all of it linked (Rust's std imports parts of it), with
stderr inherited and nothing else granted. It has no preopened directories, no environment
variables and no arguments, and no network: TCP, UDP and name lookup are denied, so `connect`
fails with "access denied". It cannot read the worktree or buffers yet. Its store is capped (256 MiB
of memory; see "Limits" in `limits-and-gotchas.md`). Besides WASI, the host functions are
`push-update` and `log`.

## Quick start: `fyx-ext`

`fyx-ext` is a command-line tool in this repository (`crates/fyx_ext`). Install it from a Fyx
checkout. The checkout's `.cargo/config.toml` asks for `sccache`; the empty `RUSTC_WRAPPER`
installs without it:

```bash
RUSTC_WRAPPER= cargo install --path crates/fyx_ext
```

The first install fetches every git dependency of the Fyx workspace, which takes a few minutes.

Then create an extension, and run it in Fyx with rebuilds on every change:

```bash
fyx-ext new my-panel --out ~/src
```

```bash
cd ~/src/my_panel && fyx-ext dev --fyx /path/to/fyx
```

`new` creates `~/src/my_panel/`. The crate name is the name with `-` as `_`; the extension id and
the surface id are the name with `_` as `-`:

```
my_panel/
├── Cargo.toml           # cdylib, its own empty [workspace], ui_ext_sdk + the test harness
├── extension.toml       # id "my-panel" + [fyx_ui] with capabilities = ["ui:panel"]
├── rust-toolchain.toml  # the toolchain Fyx pins, plus the wasm32-wasip2 target
├── README.md            # the fyx-ext commands for this crate
├── .gitignore           # /target, /fyx_ui.wasm, /*.fyxext
├── src/
│   └── my_panel.rs      # a right-dock panel with a button that patches a label, and a unit test
└── tests/
    └── headless.rs      # mounts the built component and clicks the button (see Testing)
```

`new` takes these options:

| Option | Effect |
|---|---|
| `--out <dir>` | Parent directory of the new crate, default the current directory. `<dir>/<crate>` must not exist or must be empty. |
| `--sdk-path <checkout>` | Path dependencies on `<checkout>/crates/ui_ext_sdk` and `fyx_ext_harness`. The default is the checkout `fyx-ext` was built from, written as an absolute path. |
| `--sdk-git <url>` | Git dependencies instead, at `--sdk-branch <branch>` (default `integration`) or `--sdk-rev <rev>`. Cargo then clones the whole Fyx repository on the first build. |

The name must be lower-case letters and digits, separated by single `-` or `_`, and start with a
letter. The empty `[workspace]` table lets the crate build inside a Fyx checkout too (for example
`--out extensions`) without becoming a member of the Fyx workspace. Inside a Fyx checkout, build
with `RUSTC_WRAPPER=` if you do not have sccache (see [Building](#building)).
`script/fyx-new-extension` still works; it runs `fyx-ext new` with the same options.

The generated panel is the walkthrough below in miniature: one `SurfaceTree`, node ids stored on
every mount, and a `set-props` patch in reply to a click. The rest of this guide explains each
piece.

## The `fyx-ext` commands

Every command takes `--path <extension dir>` (default: the current directory).

| Command | What it does |
|---|---|
| `fyx-ext new <name>` | Creates the crate above. |
| `fyx-ext build [--release] [-- <cargo args>]` | Runs `cargo build --target wasm32-wasip2`, copies the component to the path `[fyx_ui].component` names, then runs `check`. |
| `fyx-ext dev [--fyx <binary>] [--no-launch] [--no-watch] [-- <fyx args>]` | Builds and checks, starts Fyx with the extension directory prepended to `FYX_UI_DEV_EXTENSIONS`, then rebuilds whenever a source file, `Cargo.toml` or `extension.toml` changes, until Fyx exits. The Fyx binary is `--fyx`, then `FYX_BIN`, then `fyx` on `PATH`. |
| `fyx-ext check [--deny-warnings]` | Checks `extension.toml` and the built component the way Fyx does when it loads them (below). Exits with 1 on an error, or on a warning with `--deny-warnings`. |
| `fyx-ext test [-- <cargo test args>]` | Builds, checks, runs every surface headless, then runs the crate's `cargo test` with the built component (see [Testing](#testing)). |
| `fyx-ext package [--out <dir>] [--no-build]` | A release build, then `check`, then `<id>-<version>.fyxext` (see [Packaging](#packaging)). |

What `check` reports, as errors unless marked:

- **Manifest:** the rules of the [`[fyx_ui]` table](#extensiontoml), the id (lower-case letters
  and digits joined by single `-`, at most 64 characters), a semantic `version`, and known
  capability names (a typo is an error). Each world takes its own capabilities, as the host's
  `UiManifest::check_world` does:
  - **0.1** takes `ui:panel` and `ui:status-bar`, plus `ui:modal` and `ui:editor-decorations`
    unused (a warning), so a manifest can declare them before its component moves to 0.2.
  - **0.2** adds `ui:modal`, `ui:editor-decorations` and `ui:notifications`.
  - **0.3** adds `ui:images`, `ui:canvas` and the T2 capabilities (`network:fetch`,
    `process:spawn`, `workspace:edit`, `agent:observe`).
  - Anything else is an error. That includes what is planned for 0.4 (`ui:picker`, `ui:hover`,
    `ui:code-lens`, `ui:virtual-documents`, `ui:commands` and the T1 `workspace:*` reads), at any
    version. The 0.3 tables (`[fyx_ui.network]`, `[[fyx_ui.processes]]`, `[fyx_ui.process]`) are
    errors in a manifest that targets 0.1 or 0.2.

  A missing `name` or a `schema_version` other than 1 is a warning.
- **Component:** it must be a valid component (not a core module) and at most 32 MiB. It must
  carry exactly one `fyx:ui-api-version` section, equal to `api_version` (no section is a
  warning), and export `surfaces`, `mount`, `handle-event` and `list-rows`.
- **Capabilities, declared against used:** an import that needs a capability the manifest does
  not declare is an error, and a declared capability that nothing uses is a warning. An import
  Fyx does not provide is an error, because the component would fail to load. Importing
  `wasi:filesystem`, `wasi:sockets` or `wasi:http` is a warning: they are linked, but every call
  fails.
- **Loading:** `check` loads the component in the test harness, as Fyx would. A component that
  fails to load is an error. Every surface `surfaces()` declares needs the capability of its
  kind (`ui:panel`, `ui:status-bar`, and `ui:modal` in 0.2), as on the host. An unused surface
  capability, or no surfaces at all, is a warning.
- **Running guest code:** `check`, `test`, `dev` and `package` instantiate the component and call
  `surfaces()`; `test` also mounts every surface. The harness applies Fyx's limits: the time
  budgets, 256 MiB of memory, and a WASI with stderr only. Still, run these commands on an
  untrusted extension, such as one under review in registry CI, inside a sandbox, as for any build
  of someone else's code.

## Testing

There are two levels, and `fyx-ext test` runs both.

- **Unit tests** run your extension's Rust code on your machine, not in WASM. The SDK works off
  WASM: `log` prints to stderr, and every other host function (`push_update`, ticks, surfaces,
  decorations) succeeds and is recorded for `take_host_effects()`; `take_pushed_updates()` takes
  only the pushes. Plain `cargo test` runs them. See [Step 8](#step-8-test-it).
- **Headless tests** run the *built component* in wasmtime with `fyx_ext_harness`, the way Fyx
  runs it, without the editor. Trees, patches and their limits are validated with Fyx's own tree
  model, and the call contract matches the host's: time budgets, the push cap, pushes before the
  reply, rows in range, and typed text written into the input before the event. A test in the
  host runtime compares the two on every call, so they cannot drift apart.

`fyx-ext test`:

1. builds and checks the extension;
2. mounts every surface and fetches the first 50 rows of every list and table, reporting what
   the host would reject, and reporting `log` errors as warnings;
3. runs `cargo test` on the crate with `FYX_EXT_COMPONENT` set to the built component and
   `FYX_EXT_PACKAGE` to the extension folder.

`Harness::from_env()` reads those variables (the folder first), so headless tests skip under a
plain `cargo test`. `Harness::load_package(dir)` loads a folder as Fyx installs it: the
`[fyx_ui]` component and capabilities of its `extension.toml`, and its `assets/` for image nodes.
The harness API: `mount`, `event`, `click(surface, label)`, `rows`, `nodes`, `props`, `text`,
`find`, `find_text` and `find_button`, plus `effects()`, `logs()` and `disabled()` for
assertions. The full list is in the [harness reference](api/fyx_ext_harness.md).

The harness runs `fyx:ui` 0.1, 0.2 and 0.3 components. Its methods show the newest model
(`ui_ext::v0_2`, which also holds 0.3's image nodes), into which older data converts without
loss: tooltips, `secret`, input labels, `selected`, `indent`, `invalidate-rows` and images.
`event`, `click`, `tick` and `dismiss` return an `Outcome` with the call's effects. The same
methods with a `_v0_1` suffix (`event_v0_1`, `click_v0_1`, `rows_v0_1`, `mount_v0_1`,
`tree_v0_1`, `find_v0_1`, `surfaces_v0_1`, `pushed_v0_1`, `handle_event_raw_v0_1`) show the 0.1
model, as the host's 0.1 view does.

> **Renamed (decision D5, pre-1.0).** Before plan 4.12 the unsuffixed methods showed the 0.1
> model and the newest one had a `_v0_2` suffix. Tests written then need `_v0_1` on the old
> unsuffixed calls and no suffix on the `_v0_2` ones; `mount` now returns the nodes instead of
> a `Tree`. The `_v0_2` names still work for now and will be removed.

On top of these:
- `tick(surface)` runs a pending tick; `pending_tick(surface)` shows its delay, since the harness
  has no clock.
- `dismiss(modal, reason)` closes a shown modal as the user would; `is_shown(modal)` says whether
  one is open.
- `decoration(id)` and `decorations()` list placed decorations; `nodes(id)` holds their trees.
- `effects()` records every host call's effect.
- Notifications and progress (0.2, section M) run with the host's checks and caps.
  `notifications()` and `progresses()` show what is open or running. A test plays the user with
  `notification_action(id, action)`, `close_notification(id, reason)` and `cancel_progress(id)`,
  which send the owner its event. The harness has no clock, so a notification closes only when
  a test says so.
- `Harness::load_with_capabilities` loads with a manifest's capabilities instead of all of them.
- `image_failures()` (0.3) lists the image nodes the renderer would draw as alt text: an asset
  that is missing, outside the package, over 2 MiB or not a valid PNG or SVG, a freed generated
  image, and `tint` on a PNG. Each is also a `warn` log line, and `fyx-ext test` reports them as
  warnings. Assets are only checked in a harness made by `load_package` (or `fyx-ext test`).
- Canvases (0.3) are checked as the host checks them:
  - the caps, finite coordinates, and panels only;
  - none in list rows;
  - at most 16 per surface.

  `canvas(surface, id)` returns a canvas's draw list. `canvas_click(surface, id, x, y)` clicks
  it as the renderer would. It fails without a call on a canvas that is not clickable, or at a
  point outside the box.
- `network:fetch` (0.3) runs the host's import checks: the capability, the domain list
  (`[fyx_ui.network]`, or `with_network_domains`), `check_request`, and the in-flight and
  per-minute caps.
  - With no broker, `fetch` is `denied`, as in a host where the user has not allowed it.
  - `set_broker(TestBroker::granted(respond))` lets requests reach a closure that answers them.
    `TestBroker::asking(answer, respond)` prompts on the first delivery, and
    `TestBroker::denied()` refuses at the import.
  - Accepted requests wait in `pending_fetches()` until `deliver_io()` delivers each outcome
    through `handle-io`. A cancelled request ends `cancelled`, and a call that traps drops its
    requests.
- `process:spawn` (0.3) runs the host's import checks too: the capability, the programs
  (`[[fyx_ui.processes]]`, or `with_processes`), `check_spawn`, the worktree, and the 4-process
  cap. The broker decides as for `fetch`.
  - Real programs never run. `fake_program(name, |request, stdin| FakeRun::ok(..))` stands in for
    one, and `deliver_io()` delivers its output and exit once its stdin is closed.
  - A kill ends with `killed`, and a declared program with no fake ends `spawn-failed`
    (`not-found`).
  - `set_worktree(None)` or `set_worktree(Some(false))` tests the unavailable and untrusted
    cases.
- `workspace:edit` and `agent:observe` (0.3) follow the host too: the capability and the
  broker, then `check_edit` and the in-flight cap. When an edit is applied, `check_targets`
  refuses protected paths and overlaps.
  - Allowed edits apply unless `set_edit_answer` says otherwise, and `applied_edits()` lists
    them.
  - `set_agent_reviews(Some(reviews))` is the snapshot `start` sends; `None` makes `start`
    unavailable.
  - `agent_event(event)` feeds a running feed with the host's ids, and the harness maps them to
    opaque ones as the host does.
  - `deliver_io()` delivers `edit-done` and the agent events.
- `permissions` (0.3) follows the host:
  - `query` answers `unavailable` for an undeclared capability, otherwise the broker's state,
    fixed for the call by its first query;
  - `request` needs a click and uses it up, and prompts only from `ask`, once per capability per
    call. The broker answers after the call, and `deliver_io()` delivers the answer as
    `permission-changed`;
  - `TestBroker::granted` starts granted, and `TestBroker::asking(answer, …)` starts at `ask`.
    The broker's state is the state of every T2 capability.
- In 0.3, picker surfaces are refused as not supported yet, and the 0.3 interfaces the host does
  not implement yet (`decorations` included) trap when called.

The host's 0.2 rules apply: each import is checked when it is called, and its effect applies after
the call. Showing a modal needs a click or Enter, a modal mounts when it is shown, and three failed
ticks in a row stop a surface's ticks until the next event on it.

## Packaging

```bash
fyx-ext package
```

This writes `<id>-<version>.fyxext`, a zip of `extension.toml`, the component, and the
`assets/` directory if there is one. Packaging refuses an extension that fails `check`. The
package may be at most 50 MiB and the component at most 32 MiB. Registry packages also carry a
`signature.json`, which the registry's CI adds; authors never sign or upload binaries themselves.

## Project layout

A UI extension is one directory holding the manifest and the built component, plus the Rust crate
that produces the component:

```
my_counter/
├── Cargo.toml          # cdylib crate depending on ui_ext_sdk
├── extension.toml      # id, name, version + the [fyx_ui] table
├── fyx_ui.wasm         # the built component, copied here by fyx-ext build (not committed)
├── src/
│   └── lib.rs          # implements ui_ext_sdk::Extension, ends with register_extension!
└── tests/
    └── headless.rs     # optional: tests on the built component with fyx_ext_harness
```

The demo extensions in this repository (`extensions/fyx_demo_*`) have this layout, except that
they are members of the Fyx workspace and name their crate root `src/<crate>.rs`. Each one also
has a `.gitignore` that ignores `/fyx_ui.wasm`.

`Cargo.toml` of a standalone extension:

```toml
[package]
name = "my_counter"
version = "0.1.0"
edition = "2024"
publish = false

[lib]
crate-type = ["cdylib"]

[dependencies]
# The SDK is not on crates.io yet: point at a Fyx checkout.
ui_ext_sdk = { path = "../fyx/crates/ui_ext_sdk" }

[dev-dependencies]
# Only for tests/headless.rs; it builds wasmtime, so the first `cargo test` takes a few minutes.
fyx_ext_harness = { path = "../fyx/crates/fyx_ext_harness" }
```

- `crate-type = ["cdylib"]` is required. On `wasm32-wasip2`, cargo then emits a component.
- `ui_ext_sdk` is a path dependency because the crate is not published yet (it is planned as
  `fyx-sdk`). It inherits its edition and lints from the Fyx workspace, so a full Fyx checkout
  must exist at that path. Its external dependencies are `wit-bindgen` 0.41 and, through
  `ui_ext`, `serde` and `thiserror`.
- If your crate sits *inside* the Fyx checkout but is not a workspace member, add an empty
  `[workspace]` table to its `Cargo.toml`. Without it, cargo refuses to build a package that is
  inside a workspace but not a member of it. The host's test fixture `probe` does the same.

The SDK is built and tested with the toolchain pinned in `rust-toolchain.toml` (1.98.1, which has

## `extension.toml`

```toml
id = "my-counter"
name = "My counter"
description = "A counter panel."
version = "0.1.0"
schema_version = 1
authors = ["You"]

[fyx_ui]
api_version = "0.1.0"
component = "fyx_ui.wasm"
capabilities = ["ui:panel"]
```

Fyx reads `id` and the `[fyx_ui]` table. It ignores the other top-level keys, but keep them: they
are what upstream Zed's manifest parser expects.

<!-- crates/ui_ext_wasm/src/ui_ext_wasm.rs:151-155 (ExtensionToml { id, fyx_ui }) -->

`[fyx_ui]` accepts these keys, plus the `[fyx_ui.network]` table for `network:fetch` (0.3; see
the [SDK reference](sdk-reference.md)). Unknown keys are an error (`deny_unknown_fields`).

| Key | Rule |
|---|---|
| `api_version` | A semver string. It must be a version this build supports, and it must equal the version the component itself declares (see [Versions](limits-and-gotchas.md#versions)). Releases run `0.1.0` to `0.4.0`: all four are frozen (0.4 since 2026-11-20). A newer version is staged: only dev builds load it, and `fyx-ext check` warns. |
| `component` | A path inside the extension directory. It must be non-empty and relative, with only normal path segments: `fyx_ui.wasm` and `bin/fyx_ui.wasm` pass, but `./fyx_ui.wasm`, `../x.wasm` and absolute paths are rejected. |
| `capabilities` | A list of strings, empty by default. Every panel surface needs `"ui:panel"` and every status item needs `"ui:status-bar"`, or loading fails. Each `api_version` takes its own capabilities (see [the `fyx-ext` commands](#the-fyx-ext-commands)); a capability the world does not take fails the load with `<capability> needs fyx:ui 0.3; this extension targets <version>`. |

<!-- crates/ui_ext_wasm/src/ui_ext_wasm.rs:139-149 (UiManifest, deny_unknown_fields, capabilities default), 171-183 (version supported, component path: all components Normal), 188-203 (check_surfaces), 551-557 (manifest version == component version, check_surfaces) -->

The capability check runs only when Fyx loads the extension from its directory. A bare `.wasm`
loaded for quick iteration (below) skips it. `fyx-ext check` applies all of these rules before
Fyx does.

`fyx-ext check` also looks at the PNG and SVG files in `assets/`, which `image` nodes can show
(0.3). A file over 2 MiB is an error. These are warnings, because Fyx draws the image's alt text
instead and does not fail the update:

- a file that is not a valid PNG or SVG (a compressed `.svgz` is not one);
- a PNG over 2048 px on a side;
- an SVG that declares XML entities;
- an SVG that Fyx's scan before parsing refuses (`ui_ext::image::prescan_svg`): `url(…)` inside
  `<style>`, references that expand past the caps or form a cycle, nesting past 256;
- a name an image node cannot use.

An SVG with `<image>`, `<script>` or `<foreignObject>` is also a warning, since Fyx drops those
parts.

## Building

```bash
fyx-ext build --release
```

This runs `cargo build --target wasm32-wasip2 --release`, copies the component to the path
`[fyx_ui].component` names, and checks it. The output is already a component, with no separate
`wasm-tools component new` step. `register_extension!` embeds the custom section
`fyx:ui-api-version` that tells Fyx which API version the component targets. Release builds with
`strip = true` keep that section.

<!-- crates/ui_ext_sdk/src/ui_ext_sdk.rs:210-215, crates/fyx_ext/src/build.rs -->

For the demos in this repository, `script/fyx-build-demos` builds all of them, copies each
`<crate>.wasm` to `extensions/<crate>/fyx_ui.wasm`, and prints a ready `FYX_UI_DEV_EXTENSIONS=...`
line (`;`-separated on Windows, `:` elsewhere). `fyx-ext check --path extensions/<crate>` and
`fyx-ext test --path extensions/<crate>` work on them too.

```bash
script/fyx-build-demos --release
```

`script/fyx-build-demos --fyx-ui-0-2` builds every demo's `fyx:ui` 0.2 world instead, for a dev
build whose host runs 0.2. It leaves the repository alone: each demo goes to
`<target>/fyx-demos-v0_2/<demo>/`, with a copy of its `extension.toml` set to
`api_version = "0.2.0"` and of its `assets/` folder, and the printed `FYX_UI_DEV_EXTENSIONS` line
points there. `--fyx-ui-0-3` does the same for the 0.3 world in
`<target>/fyx-demos-v0_3/`.

A demo whose newer build needs capabilities that 0.1 refuses keeps the 0.1 list in
`extension.toml` and adds a comment line for the newer world. In the copy for that world, the
script uses it in place of the `capabilities` line:

```toml
capabilities = ["ui:panel", "ui:status-bar", "ui:modal"]
# fyx-ui-0-2: capabilities = ["ui:panel", "ui:status-bar", "ui:modal", "ui:notifications"]
```

## Installing as a dev extension

`fyx-ext dev` covers the common case: it starts Fyx with your extension directory in
`FYX_UI_DEV_EXTENSIONS` and rebuilds it as you edit. The rest of this section is what happens
underneath, and the other ways to load an extension.

UI extensions load from `fyx.extensions.dev_paths`, from the install store (see "Installing a
package"), from Zed's installed-extensions directory, and from the environment variable
`FYX_UI_DEV_EXTENSIONS`.

- **`fyx_ui: install dev UI extension`** asks for a folder, shows the capabilities its
  `extension.toml` asks for, and adds the folder to `fyx.extensions.dev_paths` in your user
  settings. Fyx loads it now and on every start, and reloads it when its component is rebuilt;
  the folder stays where it is. **`fyx_ui: remove dev UI extension`** takes it off the list (or
  edit the setting).

  ```json
  { "fyx": { "extensions": { "dev_paths": ["C:/src/my_counter"] } } }
  ```
- **A folder added to `dev_paths` by hand, or anything else in the installed-extensions
  directory** (a folder copied there, or linked by upstream's "Install Dev Extension") waits for
  consent: Fyx shows a notification with the
  capabilities it asks for and loads it only after **Enable**. The answer is kept in
  `<data dir>/fyx-ui-consent.json`, for those capabilities (for a linked folder, for that
  folder). Asking for more T1 or T2 capabilities asks again on the next start. A new build of the
  component, or more T0 capabilities, does not: the consent is not tied to the component's hash
  (decided, integration-6 R9).
- **`FYX_UI_DEV_EXTENSIONS`**, read once at startup, needs no consent: setting it is the opt-in.
  It works in dev builds only (ignored, with a log line, in Preview and Stable), and every window
  shows a banner while it is set. Fyx's own builds are on the Dev channel (`crates/zed/RELEASE_CHANNEL`
  is `dev`), so the variable works on Dev and Nightly builds. For an older
  Stable-channel build, set `ZED_RELEASE_CHANNEL=dev` at runtime.

### Extension Inspector

Dev builds, and release builds with `"fyx": { "extensions": { "developer_mode": true } }` (new
windows), have an **Extension Inspector** panel (`fyx_ui: toggle extension inspector`). For the
surface you pick it shows the live tree, the recent events and updates (a rejected update is
marked), every call with its duration against its budget and its push count, the capability
checks and denials, and your `log` output. It reads what Fyx records anyway and never calls the
extension.

### Capabilities and permissions

Every capability in `[fyx_ui].capabilities` has a tier:

| Tier | Capabilities | Granted |
|---|---|---|
| T0 | `ui:panel`, `ui:status-bar` (and the 0.2+ UI ones: `ui:modal`, `ui:notifications`, …) | no prompt; listed in the install dialog and on the extension's chips |
| T1 | `workspace:read-buffers`, `workspace:read-files`, `workspace:diagnostics` | once, in the install dialog; `fyx_ui: revoke UI extension permission` takes it back |
| T2 | `network:fetch`, `process:spawn`, `workspace:edit`, `agent:observe` | 0.3 only: the first use asks, and the extensions page changes the answer; a manifest for 0.1 or 0.2 that asks for one is refused. **(0.4)** T2 is accepted at install, one checkbox per item, unticked by default; the first-use prompt stays only for dev installs without a dialog |
| T3 | `terminal:read`, `terminal:write` | **(0.4)** at the moment of action, on one terminal; see [Terminals and CLI integrations](#terminals-and-cli-integrations-fyxui-04) |

An unknown capability is refused at load, with its name in the error. An update that adds only
T0 capabilities (or only changes the component) loads silently; one that adds a T1 capability is
held: the old version keeps running and Fyx asks you to **Approve** it. A revoked T1 capability is
denied from the extension's next call and asked for again on its next load. `fyx:ui@0.1.0` has no
T1 host imports yet, so today T1 only matters for what the dialogs show and hold.

### Installing a package

A `.fyxext` package is a zip of `extension.toml` (with `id`, a semver `version` and the
`[fyx_ui]` table), the component it names, and optional `assets/` and `signature.json`.
**`fyx_ui: install UI extension from file`** shows its id, version and capabilities, marks it
"Unsigned, not from the registry", and installs it into `<data dir>/extensions/fyx/<id>/<version>/`.
Installing another version of the same id is an update: the replaced version is kept for
**`fyx_ui: roll back UI extension`**, and older ones are deleted. **`fyx_ui: toggle pin UI
extension`** keeps an id on its version (an install of another version is refused until it is
unpinned); **`fyx_ui: uninstall UI extension`** removes every version.

A package is refused when it is over 50 MiB, its component is over 32 MiB, it unpacks to more
than 128 MiB or 1024 entries, or an entry name is not a plain relative path (no `..`, drive,
root, backslash or `:`). On first load Fyx precompiles the component next to the version folder
(`<id>/<version>-<key>.cwasm`), so later starts skip compiling; the file is Fyx's own, and one
inside a package is never loaded.

## The mental model

These rules shape everything else. The SDK handles most of the bookkeeping, but you need them to
understand what you get back.

**1. The host retains the tree; the extension never renders.** `mount` returns a surface's whole
tree once. Fyx keeps it and redraws from its copy every frame, and it never calls into WASM from
`render()`. In the current host, `mount` runs once when the extension loads, not when the panel
first opens. It runs again only to resync after Fyx rejects an update (rule 5). Reopening a panel
does not remount it.

<!-- crates/ui_ext/wit/fyx-ui.wit:183-184; crates/ui_ext_host/src/registry.rs:86-88 (SurfaceState::new on register) → crates/ui_ext_host/src/surface.rs:92 (mount in new), 327-341 (remount on invalid update) -->

**2. Flat tree, parents first.** WIT types cannot be recursive, so a tree travels as a flat
`list<node>` in which every node names its parent's id. A parent must come before its children,
and siblings keep list order. Several nodes may have no parent: a surface is a forest of roots.

<!-- crates/ui_ext/wit/fyx-ui.wit:93-99; crates/ui_ext/src/tree.rs:72, 260-268 (UnknownParent) -->

**3. Only `flex` nodes have children.** Lists and tables get their rows from `list-rows`, not
from child nodes. A child under any other kind of node is rejected.

<!-- crates/ui_ext/src/types.rs:136-139; crates/ui_ext/src/tree.rs:241-246, 269-274 -->

**4. Node ids are yours, and they are forever.** You choose every `node-id` (a `u32`). An id must
be unique within the surface and must never be reused for a different node while the surface
lives. Fyx routes events and patches by id. The SDK's `IdAllocator` only counts up, and
`SurfaceTree` keeps counting across remounts.

<!-- crates/ui_ext/wit/fyx-ui.wit:5-7; crates/ui_ext_sdk/src/ui_ext_sdk.rs:241-267, 601-604 -->

**5. Changes are patches, applied atomically.** `handle-event` answers `unchanged`, a full
`replace`, or a list of `set-props`, `insert` and `remove` patches. Fyx applies a batch all or
nothing. If one patch breaks a rule (unknown id, child under a non-flex node, a `before` that is
not a sibling, a duplicate id, a cap), Fyx keeps the old tree, shows the error in the panel
footer, and calls `mount` again to resync. The extension is not told why, so the SDK's
`SurfaceTree` checks the same rules *before* queueing an edit.

<!-- crates/ui_ext/wit/fyx-ui.wit:101-118; crates/ui_ext/src/tree.rs:188-207; crates/ui_ext_host/src/surface.rs:287-343; crates/ui_ext_sdk/src/ui_ext_sdk.rs:568-573 -->

**6. One call per input event, one call at a time.** A click is one `handle-event` call. Typing is
debounced (150 ms), and a newer queued `input-changed` for the same input replaces the older one.
Enter sends `input-submitted` with the text. Events reach the extension one at a time, in order,
and each reply is applied before the next event goes out. An event whose node has left the tree
is dropped. There are no hover, scroll or focus events in 0.1. Scrolling a list makes `list-rows`
calls, not events.

<!-- crates/ui_ext/wit/fyx-ui.wit:126-132, 186-187; crates/ui_ext_host/src/surface.rs:170-219; crates/ui_ext_host/src/view.rs:30, 216-252 -->

**7. No calls from render, and none outside a host call.** Your code runs only while Fyx is
calling it: `surfaces`, `mount`, `handle-event` or `list-rows`. `push-update` therefore only works
*during* one of those calls. It cannot drive a timer (see
[Limits](limits-and-gotchas.md#push-update-only-during-a-call)).

**8. Theme tokens only.** There are no raw colours and no font choices. Colours are the nine
`color-token` values (`text`, `text-muted`, `text-accent`, `error`, `warning`, `success`, `border`,
`surface`, `elevated-surface`), mapped to the active theme. Your UI follows theme changes with no
work on your side.

<!-- crates/ui_ext/wit/fyx-ui.wit:9-21; crates/ui_ext_host/src/view.rs:763-794 -->

**9. Slow or crashing extensions are stopped.** Each call has a 200 ms budget (2 s for
instantiation, `surfaces` and the first `mount` of each surface). A call that runs past it, traps
or panics stops the extension: its surfaces show the reason and **Restart extension**, which loads
it again on a fresh instance, and a dev extension restarts by itself on its next build. Returning
`Err(String)` is different: it is shown to the user and the extension keeps running.

## Walkthrough: a counter in 60 lines

The extension below is a right-dock panel with a bold label, an **Add** button and a **Reset**
button that is disabled at zero. The file is 68 lines, 59 of them code, and builds as-is for
`wasm32-wasip2`. It was verified with `cargo build --target wasm32-wasip2 --release` and
`cargo test` against the SDK on `integration`.

### Step 1: the crate

Create `my_counter/` with the `Cargo.toml` and `extension.toml` from
[Project layout](#project-layout) and [`extension.toml`](#extensiontoml).

### Step 2: state and props

```rust
use ui_ext_sdk::*;

const SURFACE_ID: &str = "my-counter";

#[derive(Default)]
struct Counter {
    count: u32,
    tree: SurfaceTree,
    label: NodeId,
    add: NodeId,
    reset: NodeId,
}

impl Counter {
    fn label(&self) -> TextProps {
        TextProps::new(format!("Count: {}", self.count)).bold()
    }

    fn reset(&self) -> ButtonProps {
        ButtonProps::new("Reset").disabled(self.count == 0)
    }
}
```

`use ui_ext_sdk::*` brings in the WIT types (`Node`, `NodeId`, `UiEvent`, `Update`, the props
records), their builders, `SurfaceTree` and the `Extension` trait.

`SurfaceTree` is your copy of what Fyx shows. It hands out node ids and turns your edits into
patches.

The node id fields start at 0. The SDK never hands out 0 (ids start at 1), so before `mount` no
real event can match them.

Writing each node's props as a function of the state is the pattern the demos use. You call the
same function in `mount` and after every change, and `SurfaceTree` only sends what actually
changed.

```rust
        let panel = Surface::panel(SURFACE_ID, "My counter", DockPosition::Right, Icon::Hash, 280);

```

### Step 4: build the tree in `mount`

```rust
    fn mount(&mut self, surface_id: &str) -> Result<Vec<Node>, String> {
        if surface_id != SURFACE_ID {
            return Err(format!("unknown surface {surface_id:?}"));
        }
        let (label, reset) = (self.label(), self.reset());
        let mut ids = (0, 0, 0);
        let nodes = self.tree.mount(|tree| {
            tree.flex(FlexProps::column().gap(8).padding(8), |tree| {
                ids.0 = tree.text(label);
                tree.row(|tree| {
                    ids.1 = tree.button(ButtonProps::new("Add").icon(Icon::Plus));
                    ids.2 = tree.button(reset);
                });
            });
        })?;
        (self.label, self.add, self.reset) = ids;
        Ok(nodes)
    }
```

- `SurfaceTree::mount` runs your closure with a `TreeBuilder`. A flex node's closure adds its
  children, and every builder call returns the new node's id.
- The props are computed *before* `self.tree.mount` because the closure cannot borrow `self`
  while `self.tree` is mutably borrowed.
- The ids are stored on every mount, not just the first. `mount` can be called again (rule 1),
  and the new tree gets new ids. The count lives in `self.count`, so it survives a remount.
- `?` works because `TreeError` converts into `String`.

On the first mount, the flat list this returns is five nodes, parents first: column (1), text (2), row (3), Add (4),
Reset (5).

<!-- crates/ui_ext_sdk/src/ui_ext_sdk.rs:313-329, 549-553, 601-618 -->

### Step 5: answer events with patches

```rust
    fn handle_event(&mut self, surface_id: &str, event: UiEvent) -> Result<Update, String> {
        if surface_id != SURFACE_ID {
            return Err(format!("unknown surface {surface_id:?}"));
        }
        match event {
            UiEvent::Click(id) if id == self.add => self.count = self.count.saturating_add(1),
            UiEvent::Click(id) if id == self.reset => self.count = 0,
            _ => return Ok(Update::Unchanged),
        }
        self.tree.set_props(self.label, self.label())?;
        self.tree.set_props(self.reset, self.reset())?;
        Ok(self.tree.take_update())
    }
}
```

- `set_props` records the new props and queues a `set-props` patch, but only if they differ from
  what Fyx already shows. The first Add from 0 changes the label and enables Reset (two patches),
  while the next Add only changes the label (one patch).
- `take_update` hands the queued patches to Fyx: `patches` if there are any, `unchanged`
  otherwise.
- Use `saturating_add` rather than `+= 1`: a panic aborts the call, and a trapped call disables
  the extension.

### A virtualized list

A list node only declares its row count and a fixed row height. Fyx asks for rows as they scroll
into view, and you build each row as a small subtree with `ui_ext_sdk::list_rows`:

```rust
// in mount, inside a flex node:
//     self.list = tree.list(ListProps::new(self.count, 24));

fn list_rows(&mut self, _surface_id: &str, list_node: NodeId, start: u32, count: u32) -> Vec<ListRow> {
    if list_node != self.list {
        return Vec::new();
    }
    let total = self.count;
    list_rows(start, count, total, |index, tree| {
        tree.row(|tree| {
            tree.text(format!("Row {} of {total}", index + 1));
        });
    })
}
```

- `list_rows` clamps the requested range to `total`. It builds each row with ids starting at
  `ROW_NODE_ID_BASE`, and it leaves out (and logs) any row Fyx would reject.
- Each row needs exactly one root node. Ids inside a row are row-local, and a click anywhere in a
  row arrives as `row-click(list, index)`.
- Fyx requests the visible rows again when the list node's props change. Read
  [Rows](limits-and-gotchas.md#rows-row-local-ids-row-click-and-refresh) before relying on that.

`extensions/fyx_demo_counter` is the complete version of this example.

### An input

```rust
fn filter_input(text: &str) -> InputProps {
    InputProps::new(text).placeholder("Filter")
}

// in mount:
//     self.filter = tree.input(filter_input(&self.query));

// in handle_event:
match event {
    UiEvent::InputChanged((id, text)) if id == self.filter => {
        // Record what the user typed without echoing it back.
        self.tree.set_props_from_host(id, filter_input(&text))?;
        self.query = text;
        // ...set the props of the nodes that depend on the query, then:
        Ok(self.tree.take_update())
    }
    UiEvent::InputSubmitted((id, text)) if id == self.filter => {
        // Record the submitted text first, or clearing would look like "no change".
        self.tree.set_props_from_host(id, filter_input(&text))?;
        self.tree.set_props(id, filter_input(""))?;
        self.query.clear();
        Ok(self.tree.take_update())
    }
    _ => Ok(Update::Unchanged),
}
```

The user owns an input's text while typing, which is why the first arm uses
`set_props_from_host`. See [Input text ownership](limits-and-gotchas.md#input-text-ownership) for
the details.

Note the double parentheses in `UiEvent::InputChanged((id, text))`: a WIT tuple payload becomes one
Rust tuple field.

## Newer worlds: `fyx:ui` 0.2 and 0.3

Releases of Fyx run `fyx:ui` 0.1 to 0.4, all frozen. The 0.4 world (terminals and CLI
integrations) has its own section,
[Terminals and CLI integrations](#terminals-and-cli-integrations-fyxui-04), at the end.
Every snippet below is taken from a demo in `extensions/` that builds and is tested.

### Choosing a world

The SDK's types are 0.2's by default. The crate feature `fyx-ui-0-3` switches them to the
0.3 world. `register_extension!` exports the world you name, and it converts down where it can:

```toml
[features]
fyx-ui-0-2 = []
fyx-ui-0-3 = ["ui_ext_sdk/fyx-ui-0-3"]
```

```rust
#[cfg(not(any(feature = "fyx-ui-0-2", feature = "fyx-ui-0-3")))]
register_extension!(MyPanel, v0_1);
#[cfg(all(feature = "fyx-ui-0-2", not(feature = "fyx-ui-0-3")))]
register_extension!(MyPanel, v0_2);
#[cfg(feature = "fyx-ui-0-3")]
register_extension!(MyPanel);
```

- **What a lower world does with newer features:** a host function returns `unavailable`
  ("needs fyx:ui 0.3"), and a node that the world cannot hold makes the call return `Err`.
- **The manifest's `api_version`** must match the world the component exports.
  `script/fyx-build-demos --fyx-ui-0-2` and `--fyx-ui-0-3` set it in the copies they write to
  the target directory.
- **Tests for each world:** the demos keep one panel for 0.1 that says what is missing, and gate
  their newer code and tests with `#[cfg(feature = "fyx-ui-0-3")]`.

### Notifications and progress (0.2)

Declare `ui:notifications`. The events come to the owner's `handle_event`.

```rust
// in handle_event, on a button click:
let notification = Notification::new(MAIN, NotificationLevel::Info, "Saved").action("undo", "Undo");
let id = notify(&notification)?;

let options = ProgressOptions::new(MAIN, "Indexing", ProgressLocation::Panel).cancellable();
let job = progress_start(&options)?;
progress_update(job, ProgressValue::Percent(10), Some("1 of 10"))?;

// later, in handle_event:
match event {
    UiEvent::NotificationAction(action) => { /* action.notification, action.action == "undo" */ }
    UiEvent::ProgressCancelRequested(job) => progress_end(job),
    _ => {}
}
```

The caps are 3 open notifications and 5 per minute, and 4 running progresses. Past a cap, the
call returns `limit-exceeded` and the title goes to the log. (From
`crates/fyx_ext_harness/fixtures/v0_2`.)

### Images (0.3)

Declare `ui:images`. Put files in the package's `assets/` folder; `fyx-ext package` ships it.

```rust
tree.image(ImageProps::asset("assets/logo.svg", "The Fyx logo").size(48, 48));
tree.image(
    ImageProps::asset("assets/logo.svg", "The Fyx logo in the accent colour")
        .size(48, 48)
        .tint(ColorToken::TextAccent), // SVG only; ignored with a warning on a PNG
);
tree.image(ImageProps::asset("assets/sample.png", "A photo").size(96, 96).fit(ImageFit::Cover));

// An image made at run time: register it, show it, free the old one.
let chart = add_image(ImageFormat::Svg, chart_svg(&bars).as_bytes())?;
self.panel.set_props(node, ImageProps::generated(chart, "A bar chart").size(240, 96))?;
remove_image(old_chart);
```

- **Where they go:** panels and panel list rows only.
- **A bad image is not an update error:** a missing or broken asset, or a freed handle, draws the
  alt text and logs a warning. `fyx-ext check` reports assets over 2 MiB, invalid files, and SVGs
  whose parts Fyx drops.
- **SVGs that Fyx refuses** (it draws the alt text instead):
  - `url(…)` inside `<style>`: set `fill` or `style` on the element instead;
  - compressed `.svgz` files;
  - XML entity declarations;
  - `<use>` and `url(#…)` references that expand past 100 000 nodes or 16 levels, or form a cycle;
  - elements nested over 256 deep.

  Fyx checks these before it parses, for assets and for `add_image` bytes alike.
- **The demo:** `extensions/fyx_demo_images`.

### Canvases (0.3)

Declare `ui:canvas`. A canvas holds a draw list. The whole list is sent again with every
`set_props`, so redraw from your state.

```rust
pub fn bar_chart(selected: Option<usize>) -> (CanvasProps, CanvasHits<usize>) {
    let mut draw = DrawList::new();
    let mut hits = CanvasHits::new();
    for day in 0..DAYS.len() {
        let stroke = (selected == Some(day))
            .then(|| Stroke::new(Paint::token(ColorToken::TextAccent), 2.0));
        draw.rect(bar(day), Some(Paint::data(DataColor::cycle(day))), stroke);
        hits.add(Rect::new(day as f32 * SLOT, 0.0, SLOT, BAR_BOTTOM), day);
    }
    let canvas = CanvasProps::new(280, 140, "Commits per day this week")
        .draw(draw)
        .clickable()
        .fit(CanvasFit::ScaleDown);
    (canvas, hits)
}

// in handle_event: a click arrives in canvas coordinates; hit-testing is yours.
UiEvent::CanvasClick(click) if Some(click.canvas) == self.chart_node() => {
    self.selected = self.hits.at(click.x, click.y).copied();
    // ...set_props the chart and the label, then take_update()
}
```

- **Colours:** `Paint::data(DataColor::…)` gives eight chart colours that stay readable in every
  theme; `Paint::token` gives the theme's own.
- **Limits:**
  - canvases are for panels only, not list rows, at most 16 per surface;
  - 16384 ops per canvas;
  - every number must be finite.

  `SurfaceTree` rejects a canvas the host would refuse, with a `TreeError`.
- **Animation:** only through ticks, as in the demo's sparkline.
- **The demo:** `extensions/fyx_demo_charts`.

### Fetching (0.3)

Declare `network:fetch` and the hosts. The first fetch asks the user.

```toml
[fyx_ui]
api_version = "0.3.0"
capabilities = ["ui:panel", "network:fetch"]

[fyx_ui.network]
domains = ["api.example.com", "localhost:8080"]
```

```rust
let id = fetch(&HttpRequest::get("https://api.example.com/items").header("accept", "application/json"))?;

// Outcomes are not tied to a surface: they come to handle_io, and you push updates yourself.
fn handle_io(&mut self, event: IoEvent) -> Result<(), String> {
    if let IoEvent::FetchDone((id, result)) = event {
        let line = match result {
            Ok(response) if response.is_success() => response.text().unwrap_or("").to_string(),
            Ok(response) => format!("HTTP {}", response.status),
            Err(error) => error.to_string(), // "network access was denied", …
        };
        self.panel.set_props(self.status, TextProps::new(line))?;
        self.panel.push(PANEL).map_err(|error| error.message)?;
    }
    Ok(())
}
```

Only `https://` URLs on the listed hosts are allowed, plus `http://` to a listed `localhost` with
its port. The caps are 8 requests in flight and 120 per minute.

### Running programs (0.3)

Declare `process:spawn`, the programs, and the environment names you pass:

```toml
[[fyx_ui.processes]]
name = "git"
args = ["status", "**"]

[fyx_ui.process]
env = ["NO_COLOR"]
```

```rust
let id = spawn(&SpawnRequest::new("git").args(["status", "--short"]))?;

fn handle_io(&mut self, event: IoEvent) -> Result<(), String> {
    match event {
        IoEvent::ProcessOutput(output) => self.log.push_str(&output.text()),
        IoEvent::ProcessExited(exit) => { /* exit.code, exit.killed */ }
        IoEvent::SpawnFailed((id, error)) => { /* error.to_string() */ }
        _ => {}
    }
    Ok(())
}
```

- **Permissions:** the first spawn asks the user, and it needs an open, trusted worktree.
- **Limits:**
  - at most 4 processes;
  - the arguments must fit the declared patterns: one per position, a literal, `*` inside one
    for any text, or `**` last for any rest;
  - a program without `args` runs with no arguments only. Any arguments need `args = ["**"]`,
    which the consent prompt shows. `fyx-ext check` warns about a program without `args`;
  - only the declared environment names, and only names from Fyx's allowlist: `LANG`,
    `LANGUAGE`, `LC_*`, `TZ`, `TERM`, `COLORTERM`, `NO_COLOR`, `FORCE_COLOR`, `CLICOLOR`,
    `CLICOLOR_FORCE`, `COLUMNS`, `LINES`, `CI`, `RUST_LOG`, `RUST_BACKTRACE`, `NODE_ENV`,
    `PYTHONUNBUFFERED`, `PYTHONIOENCODING` and `PYTHONUTF8` (`ui_ext::process::ALLOWED_ENV_NAMES`).
    The manifest check and the call refuse any other name, such as `HOME`, `LD_*`,
    `NODE_OPTIONS`, `GIT_DIR`, `CARGO_*` or `PATH`.
- **Stdin:** `.stdin()` keeps it open for `write_stdin` until `close_stdin`.

### Editing files and watching agent reviews (0.3)

Declare `workspace:edit` and `agent:observe`. Both ask the user on first use.

```rust
let edit = WorkspaceEdit::new("Sort imports").file(
    FileEdit::path("src/main.rs")
        .replace(TextRange::new(Position::new(0, 0), Position::new(2, 0)), "use a;\nuse b;\n"),
);
let id = apply_edit(&edit)?;
start_observing()?;

fn handle_io(&mut self, event: IoEvent) -> Result<(), String> {
    match event {
        IoEvent::EditDone((id, Err(error))) => { /* error.to_string(): "the file changed: …" */ }
        IoEvent::Agent(AgentEvent::Snapshot(reviews)) => { /* the open reviews */ }
        IoEvent::Agent(AgentEvent::Opened(review)) => { /* review.file, review.hunks */ }
        _ => {}
    }
    Ok(())
}
```

An edit applies all its files or none, as one undo step per buffer, and nothing is saved.
Protected paths such as `.git/` are refused. The agent feed is read-only.

### Testing 0.3 features headless

`Harness::load_package(dir)` loads the folder as Fyx installs it: the manifest's capabilities,
domains and programs, and the assets. Nothing reaches the network or runs a program. The test
plays the user and the outside world:

```rust
let mut harness = Harness::load_package(package)?;
harness.mount("charts")?;
harness.canvas_click("charts", chart, 100.0, 60.0)?; // fails outside the box
assert!(harness.find_text("charts", "Wed: 42 commits").is_some());

harness.set_broker(TestBroker::granted(Box::new(|request| {
    Ok(FetchResponse { status: 200, headers: vec![], body: b"[]".to_vec(), url: request.url.clone() })
})));
harness.fake_program("git", |_request, _stdin| FakeRun::ok(" M src/main.rs\n"));
harness.click("main", "Refresh")?;
harness.deliver_io()?; // fetch-done, process output and exit, through handle_io
```

- **Without a broker:** every T2 capability is denied, as in a host where the user has not
  allowed it.
- **Images:** `image_failures()` lists the images Fyx would draw as alt text.
- **Comparison with the host:** `ui_ext_wasm`'s `harness_conformance*` tests run the same
  components in the host and the harness and compare every effect, so the harness cannot drift.

## Terminals and CLI integrations: `fyx:ui` 0.4

`fyx:ui` 0.4 lets an extension be a terminal of its own, and lets anyone build a full integration
for a command-line tool (Claude Code, Gemini CLI, Codex, OpenCode, …). Fyx has no tool-specific
code for this: it offers generic primitives, and each tool is an extension. The design, with every
limit and the reasons, is [wit-0.4/design.md](wit-0.4/design.md); this section is the author's
route through it.

**Status.** 0.4 is frozen (2026-11-20): Stable, Preview and Dev builds load it. The WIT is
`crates/ui_ext/wit/since_v0.4.0/fyx-ui.wit`. The SDK's `fyx-ui-0-4` feature has the `terminals`,
`listeners`, `context`, `review` and `relay` modules, the harness fakes them, and the demos
`fyx_demo_pseudo_terminal`, `fyx_demo_terminal_profiles`, `fyx_claude_code` and `fyx_gemini_cli`
use them. Snippets here are manifest TOML or WIT calls; the demos show the Rust side.

### What you can build

- **A terminal of your own** (requirement 1): a *pseudo-terminal* is a tab or a panel area whose
  backend is your code (SSH, a serial port, tmux control mode, a container, a TUI written in
  WASM). Fyx draws it with its native terminal view: you send bytes, you get input and resizes.
  There is no terminal emulator in WASM.
- **An integration for any CLI tool** (requirement 2): a profile in the "+" menu that starts the
  tool, environment for it, a loopback server it connects to (MCP), a discovery file that tells
  it where to connect, command hooks that reach you, proposed edits that go through Fyx's agent
  review, editor context, and approval cards for the tool's own permission prompts.
- **Powerful things the user accepts by hand** (requirement 3): everything that runs code or
  reaches outside Fyx is a T2 item the user ticks at install, one checkbox each.

Fyx never gives you the byte stream of every terminal, never a write into the user's shell without
the user's say-so, and never a write into `~`.

### Choosing 0.4

Set `api_version = "0.4.0"` in `[fyx_ui]`. The 0.4 tables and capabilities are errors for a lower
world, so the install dialog never asks consent for something the world cannot use:

```text
[[fyx_ui.listeners]] needs fyx:ui 0.4; this extension targets 0.3.0
```

Everything 0.3 has works unchanged in 0.4.

### Capabilities and tiers

| Tier | New in 0.4 | When the user agrees |
|---|---|---|
| T0 | `package:files`, `ui:approvals` | never asked; shown on the extension page |
| T1 | `terminal:profiles`, `terminal:pseudo`, `terminal:status`, `context:editor`, `workspace:open`, `review:propose` | listed in the install dialog; installing is the consent |
| T2 | `terminal:create`, `terminal:env`, `terminal:observe`, `network:listen`, `fs:discovery-file`, `relay:hooks` (and 0.3's `network:fetch`, `process:spawn`, `workspace:edit`, `agent:observe`) | **one checkbox per item** in the install dialog, unticked by default |
| T3 | `terminal:read`, `terminal:write` | **at the moment of action**, on one terminal, after a gesture |

Until the T3 model is in the host (plan 5.6 and 5.18), a manifest that declares a T3 capability is
refused.

### What the user's consent means for your code

- **T2 at install, per item.** Every T2 item in your manifest needs `reason = "…"`: one line of
  plain text, at most 200 bytes. The install dialog shows it under the item as "The author says:
  …". Write it for the person ticking the box. A missing or longer reason fails the load.
- **An unticked item is `denied`.** Your extension still loads. Check what you are allowed to do,
  and say what you cannot do instead of failing: a panel that explains "ticking *Create
  terminals* on the extension page turns this on" is a normal extension.
- **The user can turn items on later** on the extension page (one more confirmation with the same
  text), and off at any time.
- **Revocation stops everything at once.** Terminals you created and their process trees are
  killed, listeners close, discovery files are removed, relay channels answer their `on_failure`,
  and the env leaves new terminals. You get `io-event::permission-changed`.
- **Updates show a diff.** A new version that adds or widens a T1 or T2 item (a capability, a
  program or its argument patterns, a domain, an env name or value, a listener, a discovery path,
  a relay channel, `scope = "all-new"`) is held. The old version keeps running until the user
  approves. Removals and T0 additions install silently. The registry's PR comment shows you the
  same diff, so check it before you ask for a review.
- **T3 is not requested in advance.** You ask at the moment you need it, from a gesture in your own
  UI. The user's answer is "Once" or "This terminal until it closes". "Always allow" exists, but
  only the user can turn it on from a card or the extension page, with a warning in plain words,
  and it resets when your component changes. Do not design around it.
- **Never in an untrusted worktree.** Created terminals are unavailable there
  (`untrusted-worktree`), and T3 never applies.
- **A journal** on the extension page records what you did (programs started, listeners opened,
  discovery files written, relay requests, proposals, consent changes). Terminal reads are
  recorded without their content. It is the user's view of you: keep your behaviour explainable.

### Terminal profiles (`terminal:profiles`, T1)

A profile is a recipe. It shows in the terminal panel's "+" menu as "Name — Extension", and the
user starts it. The terminal belongs to the user: you may set its status, give it env and paste
into it; reading or writing it is T3.

```toml
[[fyx_ui.terminal_profiles]]
id = "claude"                 # [a-z0-9-]{1,32}, unique in the extension
name = "Claude Code"
icon = "ai-claude"            # a frozen icon name; extension SVGs are not host chrome
program = "claude"            # resolved like [[fyx_ui.processes]]: PATH outside worktrees
args = ["--ide"]              # literal; may contain ${package} and ${relay}
cwd = "worktree"              # "worktree" or "home"
account_tool = "claude"       # optional: the user picks an account profile for it
resume_flag = "--resume"      # optional: --[a-z][a-z0-9-]{0,31}, resumes a session (below)
```

The menu shows the full command line on hover, and marks a shell or interpreter "runs any command
you type". At most 16 profiles, and `args` of at most 64 items of 1 KiB.

Fyx reopens a profile's terminals when their project opens again, with the same account
(`fyx.terminal.restore_profile_terminals`). With `resume_flag`, it starts the program with
`<resume_flag> <session id>` instead, the id being the last top-level `session_id` that the
terminal's hooks sent through `fyx-relay` (Claude Code's hook input has one). Fyx passes only an
id of 1 to 128 `[A-Za-z0-9_-]` that does not start with `-`, and the user can turn resuming off
(`fyx.terminal.resume_profile_sessions`).

### Pseudo-terminals and the `terminal` node (`terminal:pseudo`, T1)

```text
terminals.open-pseudo({ title, cols?, rows?, in-panel })  -> terminal-handle
terminals.write-output(handle, bytes)     # at most 64 KiB per call, 4 MiB/s per terminal
io-event::terminal-input(handle, bytes)   # coalesced to 30 per second
io-event::terminal-resized(handle, cols, rows)   # the last size only
```

- `in-panel = true`, or a `terminal` node (`node-kind::terminal({ handle })`) in your panel, draws
  the native terminal inside your UI, so you can build tabs, blocks or side panels around a real
  terminal. One node per handle.
- Fyx **removes** these from your output before the terminal sees it: OSC 52 (clipboard), OSC 8
  (hyperlinks), OSC 1337, OSC 7501, and every sequence the terminal would answer (DA, DSR/CPR,
  DECRQSS, XTGETTCAP, colour queries). The terminal never writes a reply built from your output.
  Above the rate limit `write-output` fails with `rate-limited`.
- The tab says which extension owns it.

### Created terminals (`terminal:create`, T2)

`terminals.create({ program, args, cwd?, title? })` runs a **declared** program in a real pty as
your own terminal. You read its raw output and write its input.

```toml
[[fyx_ui.terminal_programs]]
name = "codex"
args = ["-c", "notify=*", "**"]     # argument patterns, as [[fyx_ui.processes]]
reason = "Starts Codex in a terminal tab so you can use it inside Fyx."
```

```text
io-event::terminal-output(handle, bytes, dropped)   # at most 30 per second, 64 KiB each
io-event::terminal-exited(handle, exit-code?)
terminals.send-input(handle, bytes)                 # at most 64 KiB per call
```

Output beyond the rate is buffered up to 1 MiB; then the oldest is dropped and the next event says
how much. The tab says "started by <extension>". At most 8 per extension; each is killed with its
process tree on reload, disable, uninstall and revocation. Programs in `RUNS_ANY_CODE` (shells,
interpreters) are marked in the dialog, as in 0.3.

### Environment for terminals (`terminal:env`, T2)

```toml
[fyx_ui.terminal_env]
vars = { ENABLE_IDE_INTEGRATION = "true", CLAUDE_CODE_PLUGIN_DIRS = "${package}/claude-plugin" }
scope = "profiles"                  # or "all-new"
reason = "Tells Claude Code to connect to this extension and load its plugin."
```

- **Scope.** `profiles` (default) puts the vars in your own terminals only (profiles and created
  terminals). `all-new` also puts them in every new terminal the user opens, which is a second,
  stronger checkbox, unticked by default. If it is unticked you get `profiles`. Terminals already
  open show "Restart to apply" when the scope widens.
- **Values** are literals or templates: `${package}` (your installed folder, read-only),
  `${listen.<name>.port}`, `${relay}` and `${account.<tool>}`. The host fills the templates; you
  never see an account's path or a listener's token. `${listen.<name>.token}` is allowed only for
  a listener with `token_in_env = true`. At most 32 names, 4 KiB per value, no NUL or newline.
- **Refused at load**, in any letter case: code loaders and redirections (`LD_*`, `DYLD_*`,
  `NODE_OPTIONS`, `PYTHONPATH`, `BASH_ENV`, `PROMPT_COMMAND`, `GIT_*` editors, `RUSTC_WRAPPER`, …),
  `PATH`, `PATHEXT`, `COMSPEC`, `HOME`, `USERPROFILE`, `XDG_*`, `ZDOTDIR`, `SHELL`, `TERM*`,
  `FYX_*`, `ZED_*`, and the credential and config-dir names of
  [Accounts](#accounts-and-what-an-extension-cannot-do) below. A `*_TOKEN` name is allowed in one
  case: its value is exactly `${listen.<name>.token}` of one `token_in_env` listener. That token is
  Fyx's own, not a credential.
- The install checkbox lists every name and value. A value that points into your package shows as
  "files from this extension".

### Status, observing, pasting

- `terminals.set-status(handle, status?)`: a state (`idle`, `working`, `blocked`, `done`,
  `error`), a label (at most 64 bytes), optional detail and progress, and `attention`. On your own
  terminals it needs no capability; on any other terminal it needs `terminal:status` (T1), and
  the handle comes from `terminal:observe` or a relay request. The tab always shows who set it
  ("from extension X"), at most 4 updates per second.
- `terminal:observe` (T2): `terminals.list()` and `terminal-created`, `terminal-closed` and
  `terminal-status-changed` events, with title, cwd, origin, status and the account profile's
  **name**. Command lines in titles are redacted (`•••`) unless the user has shared the terminal
  with you (T3).
- `terminals.paste(handle, text)` pastes into your profile or own terminal, after a gesture in your
  UI, and only while the program has bracketed paste on. Fyx strips control characters, wraps the
  text in the paste markers and caps it at 16 KiB.

### Loopback listeners and MCP (`network:listen`, T2)

The host listens on `127.0.0.1:0` and checks everything first; you handle messages.

```toml
[[fyx_ui.listeners]]
name = "ide"
protocol = "mcp-websocket"          # "mcp-websocket", "mcp-streamable-http", "websocket", "http"
auth = { header = "x-claude-code-ide-authorization" }   # or { bearer = true } or { query = "auth" }
token_in_env = false
reason = "Lets Claude Code in your terminal talk to Fyx about your open files."
```

- Fyx refuses, before you see anything: a wrong or missing token (128 random bits, new each run),
  any `Origin` header, a `Host` that is not `127.0.0.1:<port>` or `localhost:<port>`, more than 16
  connections, messages over 4 MiB and more than 100 messages a second per connection. At most 4
  listeners.
- **MCP:** the host speaks JSON-RPC and MCP. You register tools with
  `listeners.register-tools(listener, tools)`, answer `io-event::mcp-call` with
  `listeners.respond(call-id, outcome)` (a call may stay open until you answer, which a blocking
  `openDiff` needs; it is cancelled when its connection closes: `io-event::mcp-cancelled`), and
  send notifications with `listeners.notify`.
- **`websocket` and `http`:** raw frames or requests arrive as `listener-message` and
  `listener-request`; you answer with `listeners.send` and `listeners.reply`.
- Your code never sees the token. It travels in a discovery file or, with `token_in_env`, in a
  terminal's env.

### Discovery files (`fs:discovery-file`, T2)

CLI tools find an IDE through a file at a known path. The host writes it from your template.

```toml
[[fyx_ui.discovery_files]]
listener = "ide"
dir = "${account.claude}/ide"       # or "${tmp}/<name>"
default_dir = "~/.claude/ide"       # used when no account profile applies
name = "${port}.lock"
content = { pid = "${pid}", workspaceFolders = "${worktrees}", ideName = "Fyx",
            transport = "ws", authToken = "${token}" }
reason = "Lets Claude Code find this window. Claude Code will run what this extension tells it."
```

- Placeholders: `${port}`, `${token}`, `${pid}`, `${worktrees}`, `${uid}`, `${tmp}`.
- The `name` must contain `${port}` or `${pid}` and end in `.lock` or `.json`, so a discovery file
  can never replace a tool's settings. No `..`, no symlink anywhere in the path. The file is
  `0600` in a `0700` directory (an ACL for the user on Windows), written atomically.
- It is removed on listener close, exit, revoke and uninstall; stale files from a crash are
  removed at the next start. With several account profiles, one file goes into each account's
  directory.
- The dialog says what it means, because a discovery file counts as running code in that tool.
  At most 8 files.

### Command hooks through `fyx-relay` (`relay:hooks`, T2)

Most tools' hooks can only run a command. `fyx-relay` ships next to the `fyx` CLI.

```toml
[[fyx_ui.relay_channels]]
name = "pre-tool"
timeout_ms = 30000                  # at most 600000
on_failure = { exit = 0 }           # what the hook gets when Fyx or you do not answer
reason = "Receives Claude Code's tool hooks so Fyx can show what it is about to do."
```

A hook runs `"$FYX_RELAY" --channel <extension-id>/pre-tool`; `FYX_RELAY` is in every Fyx terminal
and `${relay}` gives the path to profile args. You get `io-event::relay-request(id, channel,
terminal?, argv, stdin)` (stdin at most 1 MiB) and answer with
`relay.respond(id, exit-code, stdout, stderr)`. **A relay hook fails open by default**: with Fyx
closed, no token, an unknown channel, a revoked capability or a timeout, it exits 0 with no output,
so your channel never blocks the user's tool. Declare `on_failure = { exit = 2 }` to fail closed;
the install checkbox shows it. At most 16 channels and 8 requests in flight.

### Proposed edits (`review:propose`, T1)

```text
review.propose({ path, change: new-content(text) | unified-diff(text), title, session, apply })  -> id
io-event::review-decided(id, result<{ decision, final-content }, error>)
review.begin-turn(session) / review.end-turn(session, changed-paths)
```

The user reviews the edit hunk by hunk in Fyx's agent review, and `final-content` is the text after
their choices. A blocking protocol (Claude's `openDiff`) keeps its MCP call open until then; a
notifying one (Gemini's `ide/diffAccepted`) sends a notification. `apply = false` (default) writes
nothing: the tool writes the file itself. `apply = true` applies the accepted hunks as one
undoable edit and never saves. Reviewing is the consent, so this needs no `workspace:edit`.
Protected and private paths are refused; at most 64 open proposals and 8 MiB per file. You cannot
answer a review: accepting and rejecting stay the user's.

### Editor context, opening files, approval cards

- `context:editor` (T1): `context.watch(on)` gives `io-event::context-changed` with the active
  file, open files, cursor and selection (up to 64 KiB, debounced to 300 ms). Private files show as
  "a private file" with no text. Combined with `network:*`, terminal writes or `relay:hooks`, the
  dialog warns "It can pass what you select to <tool>".
- `workspace:open` (T1): `context.open(path, range?, focus)` opens a worktree file. `focus = true`
  needs the user's gesture, or a recent request from a terminal that has focus; otherwise the file
  opens in the background and never steals typing.
- `ui:approvals` (T0): `approvals.ask(title, detail, options)` shows a tool's permission question as
  a Fyx card with "Allow once", "Always allow" and "Deny" (you choose which, at least one). The
  card is drawn by the host with your name and a note that the tool's name is "as the extension
  says". It has a 1 s click guard, no keyboard answer and grants nothing in Fyx. The answer comes
  back as `io-event::approval-answered`; you pass it to the tool. At most 4 open.

### Reading and writing the user's terminals (T3)

`terminals.request-read(handle, scope, lines)` and `terminals.request-write(handle, text, submit)`
need a gesture in your UI and show a host-drawn card. A read returns plain text without ANSI (the
last command block, or the last N ≤ 500 lines) as `io-event::terminal-read-done`; a write shows
the exact text for confirmation **every time**, takes printable text and tab only (no control keys,
no ESC), and `submit` adds Enter after the confirmation. The tab shows "typed by <extension>" for
5 s. The user's terminals stay the user's: pseudo and created terminals are yours; everything else
needs T3.

### Accounts, and what an extension cannot do

People run several accounts of one tool (a personal and a work Claude, for example). Fyx's
**account profiles** hold that choice, and the rules around them bind extensions too:

- You never see an account's directory or credentials. `account_tool` on a profile, and the
  `${account.<tool>}` template, let the *host* put the user's chosen account into a terminal or a
  discovery path. You see only the account's name (in `terminal-info`).
- These names are refused for `terminal:env` and `process:spawn`, in any case: config
  directories (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `GEMINI_CLI_HOME`, `COPILOT_HOME`,
  `OPENCODE_CONFIG_DIR`, `OPENCODE_CONFIG`, `OPENCODE_CONFIG_CONTENT`, `QWEN_CODE_HOME`,
  `AMP_HOME`, and every name an account preset uses) and credentials (`CLAUDE_CODE_OAUTH_TOKEN`,
  `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `OPENAI_API_KEY`, `GEMINI_API_KEY`,
  `GOOGLE_API_KEY`, `GOOGLE_APPLICATION_CREDENTIALS`, `GH_TOKEN`, `GITHUB_TOKEN`,
  `COPILOT_GITHUB_TOKEN`, and any name ending in `_API_KEY`, `_TOKEN`, `_SECRET`, `_PASSWORD` or
  `_CREDENTIALS`, except the listener-token case above). Account directories are protected paths,
  like `.claude/`.
- **The registry does not accept** an extension that rotates accounts, switches them when a limit
  is reached, spreads load over accounts, carries a session to another account to continue on its
  limit, shares or resells access, or handles tokens. It is blocked if found later. Fyx itself
  never does these things: there is no automatic switch and no "continue with another account"
  button, and a limit message is shown as it is. See
  [Accounts and limits](platform/registry-repo.md#accounts-and-limits-what-is-not-accepted).

### Publishing a 0.4 extension to the registry

- **Tier.** The registry rates a release by its highest capability, and **T3 counts as T2**, so
  an extension with `terminal:read` or any T2 capability needs the owner's approval for every
  version and never auto-merges. A T1-only integration (profiles, pseudo-terminals, status,
  context, review proposals) follows the T0 and T1 rules. The registry does not accept T2
  entries until `fyx-ext` reads `network_domains` and `processes`
  ([registry-repo.md](platform/registry-repo.md#the-entry)); a 0.4 T2 extension can run as a
  dev extension in the meantime.
- **The diff in the PR comment.** For a new version, the comment lists what you add (each item
  with its tier) and remove, the same text clients show before an update installs. Put a plain
  `reason` on every T2 item, since a reviewer reads it next to the diff.
