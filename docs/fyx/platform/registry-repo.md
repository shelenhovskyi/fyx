# Registry repository: `shelenhovskyi/fyx-extensions`

Status: **design for platform plan task 3.1** (and the CI of 3.2). Nothing exists yet: the
repository is created in task 3.1. This document says what goes in it, who can merge what, what CI
does, how the signing keys are handled and how an extension gets blocked.

It builds on:

- [spec.md](spec.md) decisions 12–21: the package, the entry, CI from source, signatures, the
  block list and the capability tiers;
- [registry-format.md](registry-format.md): `index.json`, `blocklist.json`, keys and the
  `fyx-registry` CI tool, as `crates/fyx_registry` implements them. That file is on
  `claude/fyx-registry-core` until it merges.

**Decided (owner, 2026-11-18; recorded in spec decisions 16 and 18):**

- **T0 and T1 merge by themselves.** An entry whose release is tier T0 or T1 merges when CI is
  green. A new T0–T1 extension needs no review.
- **Owners of the entry.** A new version needs one of the entry's own owners. An owner change
  needs an existing owner.
- **T2 needs the owner.** The owner of the registry approves every T2 version, not only the first
  one.
- **`urgent` needs the owner.** The owner approves every `urgent = true`.
- **Separate keys.** Releases and the block list are signed by separate keys, held apart. The
  client verifies each against its own keyset, so a stolen release key cannot forge a block list.

See [Review rules](#review-rules) and [Keys](#keys).

## Goals

- **Built from source.** An author never uploads a binary. Every package is built by the
  registry's CI from a public commit, in a pinned image.
- **Small trust boundary.** Untrusted code (an extension's build scripts and tests) never runs
  where a signing key or a write token exists.
- **No human queue for low-risk changes.** A T0–T1 extension and its updates need nobody's review.
  T2 (network, processes, editing files, observing agents) always needs the owner.
- **Releases are permanent.** A published version is never replaced or deleted. A bad one is
  blocked.

## Layout

```text
fyx-extensions/
├── extensions/
│   └── <id>.toml              # one entry per extension (decision 14)
├── blocklist/
│   └── blocklist.toml         # the block list source; CI signs it into blocklist.json
├── keys/
│   ├── releases.json          # public keys only: release key + its rotation key
│   └── blocklist.json         # public keys only: block-list key + its rotation key
├── policy/
│   ├── builder.toml           # pinned builder image digest and fyx-ext version
│   └── reserved-ids.txt       # ids nobody may register (fyx, fyx-*, zed, …)
├── builder/
│   └── Dockerfile             # the builder image's source
├── .github/
│   ├── CODEOWNERS
│   ├── ISSUE_TEMPLATE/report-extension.yml
│   └── workflows/
│       ├── pr.yml             # untrusted: build, check, test, classify
│       ├── publish.yml        # trusted: rebuild, sign, publish (push to main)
│       └── blocklist.yml      # trusted: sign and publish the block list
├── CONTRIBUTING.md            # how to add or update an entry
└── README.md
```

Nothing in the repository is generated by CI: `index.json` and `blocklist.json` live only as
release assets (see [Publishing](#publishing)). So no CI job needs to push to `main`.

## The entry

`extensions/<id>.toml`, as decision 14 says: where the source is, and who owns it. Everything else
comes from the extension's own `extension.toml` at that commit.

```toml
# extensions/todo.toml
id     = "todo"                                   # equals the file name and extension.toml's id
owners = ["alice", "bob"]                         # GitHub logins; at least one

[source]
repository = "https://github.com/alice/todo"
commit     = "0123456789abcdef0123456789abcdef01234567"
path       = "."                                  # the extension's folder in that repository

# Optional. Skips the 24 h age gate; only the owner may set it (see Review rules).
urgent = false
```

Rules, checked by CI in the `entry` step:

- **Unknown keys are an error**, like every Fyx format.
- **`id`** follows the registry's id rules (`a-z`, `0-9`, `-`, starting with a letter, at most
  64 characters). It must equal the file name and the `id` in `extension.toml`, and must not be
  listed in `policy/reserved-ids.txt`.
- **`owners`**: 1 to 8 GitHub logins.
- **`source.repository`** is an `https://github.com/<owner>/<repo>` URL. Other hosts come later.
- **`source.commit`** is a full 40-digit lowercase SHA. Branches and tags are refused, because
  they move.
- **`source.path`** is relative, without `..`.

How the release fields of [registry-format.md](registry-format.md#indexjson) are filled:

| Release field | From |
|---|---|
| `id`, `owners`, `source.*` | the entry |
| `version`, `name`, `description` | `extension.toml` at `source.commit` |
| `capabilities` | `[fyx_ui] capabilities` in `extension.toml` |
| `network_domains`, `processes` | the manifest fields that come with T2 (decisions 23, 24). Until `fyx-ext` knows them, CI refuses an entry that declares a T2 capability. |
| `tier` | computed by CI: the highest tier among the capabilities (decision 21) |
| `package.url`, `.sha256`, `.size` | the package CI built, and its release asset URL |
| `published_at` | the time the publish job signs the release |
| `urgent` | the entry |

To publish a new version, the author bumps `version` in `extension.toml`, pushes the commit, and
opens a PR that changes `source.commit`. If the version is already in the index, CI refuses the
PR: a published version is never replaced (`fyx-registry index add` refuses it too).

## Review rules

GitHub settings on `main`:

- Pull requests only. No direct pushes, no force pushes, no deletion, for admins too.
- **Required status checks:** `entry`, `build`, `policy`.
- **Require review from Code Owners** is on. GitHub asks for a code owner only when a PR touches a
  file that CODEOWNERS assigns, so it does not apply to `extensions/`.
- No other required reviews, so a PR whose checks are green can merge.
- Auto-merge is allowed. A bot enables it on PRs that `policy` marks auto-mergeable.

`.github/CODEOWNERS`:

```text
# Everything that decides trust is the owner's.
/.github/            @shelenhovskyi
/policy/             @shelenhovskyi
/builder/            @shelenhovskyi
/keys/               @shelenhovskyi
/blocklist/          @shelenhovskyi
/README.md           @shelenhovskyi
/CONTRIBUTING.md     @shelenhovskyi
# /extensions/ has no code owner: the policy check decides who must approve.
```

### The `policy` check

The tier rule depends on what the built component declares, not on which files changed, so
CODEOWNERS cannot express it. The `policy` check enforces it. It runs on every PR push and every
submitted review (`pull_request_review`), so an approval turns it green without a new commit.

The check reads three things: the entry before and after the PR, the release that the `build` job
derived, and the last published release of that id from `index.json`. A PR may change one entry
only.

| Change | Who must approve |
|---|---|
| **New extension, tier T0 or T1** | Nobody. Auto-merges on green CI. |
| **New extension, tier T2** | The owner (`@shelenhovskyi`). |
| **New version of an extension, tier T0 or T1**, no owner change | One of the entry's owners: as the PR's author, or by an approving review. Auto-merges once that holds. |
| **Any PR whose release is T2**: a new version, a new T2 capability, a new network domain or a new process | The owner, for every version. A T2 update changes code that can reach the network or your files. |
| **Owners added or removed** | An existing owner of the entry. |
| **`urgent = true`** | The owner. It skips the 24 h age gate. |
| **Entry deleted** | Refused. Releases are permanent; block the extension instead. |
| **Anything under CODEOWNERS paths** | The owner, through Code Owners review. |

The check also fails, whoever approves, when:

- the id is reserved, or is a near copy of an existing id. It refuses an id at edit distance 1
  from an existing id, and one that equals it after removing `-`.
- the version is not higher than the last published one;
- `extension.toml`'s `id` does not equal the entry's;
- the build, `fyx-ext check` or `fyx-ext test` failed.

The check states its decision in a PR comment: the tier, what changed compared with the last
release (capabilities, domains, processes, owners), and who must approve. This comment is the
reviewer's summary for a T2 PR.

**Why a T0–T1 update still needs an owner of the entry:** without it, anyone could open a PR that
points someone else's extension at a commit in their own fork. The commit must also be reachable
from a branch of `source.repository`, not only from a fork's PR ref.

## CI

Two workflows, split by trust.

### `pr.yml`: untrusted

Triggered by `pull_request` (never `pull_request_target`). The token is read-only and the job has
no secrets: the extension's build scripts and tests run here.

Each changed entry gets its own job, so one extension's `build.rs` cannot touch another's
artifacts.

1. **`entry`**: parse and validate the entry (above).
2. **`build`**, in the pinned image from `policy/builder.toml`
   (`ghcr.io/shelenhovskyi/fyx-ext-builder@sha256:<digest>`). The image has the toolchain that
   `rust-toolchain.toml` pins, the `wasm32-wasip2` target, and a pinned `fyx-ext`.
   1. Fetch `source.repository` at `source.commit` (`git fetch --depth 1 origin <sha>`). Check that
      the commit is on one of the repository's branches.
   2. Require a `Cargo.lock`, then run `cargo fetch --locked`. This is the only step with network
      access.
   3. Run the rest in a container started with `--network none` and `CARGO_NET_OFFLINE=true`:
      - `fyx-ext check --deny-warnings`: the manifest, the component, the declared and used
        capabilities;
      - `fyx-ext test`: the extension's headless tests on `fyx_ext_harness`;
      - `fyx-ext package`: writes `<id>-<version>.fyxext`.
   4. Run `cargo deny check advisories` on the extension's `Cargo.lock`. It reports, and does not
      block, except for an advisory against `wit-bindgen` or the SDK.
   5. Write the unsigned release JSON (the `signed` part of a release, without `published_at`)
      and the package's SHA-256 as artifacts.
3. **`policy`**: the check above.

### `publish.yml`: trusted

Triggered by a push to `main`. It has a `concurrency: publish` group, so publishes run one at a
time and `index add` never races.

1. **Rebuild** each changed entry, in the same image and the same `--network none` steps. Publish
   never takes a package from the PR run.
   - It compares the SHA-256 with the PR build's and reports a mismatch.
   - The mismatch becomes a failure once the builds are shown to be reproducible (open question
     1).
   - This job also has no secrets.
2. **Sign and publish**, in a separate job in the GitHub Environment `release-signing`. Only this
   job can read the release key. It runs no extension code: it receives the package and the
   unsigned release as artifacts.
   1. Set `published_at` to now. Run
      `fyx-registry sign release release.json --package <pkg> --out signed.json`, with the key in
      `FYX_REGISTRY_SIGNING_KEY`.
   2. Run `fyx-registry verify release signed.json --package <pkg> --keyset keys/releases.json`.
   3. Upload the package to the release `<id>-v<version>`, creating it. Do this before the index
      names it.
   4. Download the current `index.json`. Run
      `fyx-registry index add --index index.json --release signed.json --keyset keys/releases.json`,
      then `fyx-registry verify index index.json --keyset keys/releases.json`.
   5. Upload `index.json` to the release `index`, replacing it (`gh release upload --clobber`).

### `blocklist.yml`: trusted

Triggered by a push to `main` that changes `blocklist/`. It runs in its own Environment,
`blocklist-signing`, which holds the block-list key and nothing else. `publish.yml` cannot read
this key, and this workflow cannot read the release key.

1. Convert `blocklist.toml` to the unsigned block list, with `sequence` set to the published
   list's sequence + 1 and `generated_at` set to now.
2. Run `fyx-registry sign blocklist blocklist-unsigned.json --out blocklist.json`, with the
   block-list key in `FYX_REGISTRY_SIGNING_KEY`.
3. Run `fyx-registry verify blocklist blocklist.json --keyset keys/blocklist.json`.
4. Upload `blocklist.json` to the release `index`.

## Publishing

| What | Where |
|---|---|
| Package | release `<id>-v<version>`, asset `<id>-<version>.fyxext` |
| Index | release `index`, asset `index.json` |
| Block list | release `index`, asset `blocklist.json` |

The client reads fixed URLs:
`https://github.com/shelenhovskyi/fyx-extensions/releases/download/index/index.json` and
`…/index/blocklist.json`.

Replacing a release asset is not atomic, so a fetch can fail for a moment. The client keeps its
cached copy when a fetch fails (registry-format.md, "The cached copy"), so a failed fetch costs
nothing. If that turns out to be a problem, GitHub Pages is the fallback for the two documents.

Release tags are protected (a ruleset on `*-v*` and `index`), so only the publish job can create
them.

## Keys

There are four Ed25519 keys: two **keysets** with two keys each (spec decision 18). **No real key
exists yet, and none may ever be written into a repository, an issue, a log, a document or an
agent session.** Every key in this document and in tests is a placeholder or is generated per test
run.

| Keyset | Key | Key id (example) | Where the seed lives | Signs |
|---|---|---|---|---|
| Release | current | `fyx-rel-2026-a` | Secret `FYX_REGISTRY_SIGNING_KEY` in the Environment `release-signing`, plus an offline backup | Every release |
| Release | rotation | `fyx-rel-2026-b` | Offline only | Nothing, until it replaces the current key |
| Block list | current | `fyx-bl-2026-a` | Secret `FYX_REGISTRY_SIGNING_KEY` in the Environment `blocklist-signing`, plus an offline backup | Every block list |
| Block list | rotation | `fyx-bl-2026-b` | Offline only | Nothing, until it replaces the current key |

- **Offline** means the owner's password manager plus a paper or hardware backup. An offline key
  is never stored in GitHub.
- **Where the public keys go.** The release keys are in `keys/releases.json` and the block-list
  keys in `keys/blocklist.json`. Both keysets are compiled into the client.
- **Each document has its own keyset.** The client checks a release only against the release
  keyset, and the block list only against the block-list keyset. A release key therefore cannot
  sign a block list that a client accepts, and the other way round.
- **No format change.** The documents already carry a domain tag, and every `fyx_registry` verify
  call takes the keyset to check against. The client (plan 3.3, 3.4) passes the right keyset.
  The "Keys" section of registry-format.md describes one keyset and needs this split.
- **The client decides.** Only a client release decides which keys are trusted. Changing a keyset
  file in this repository changes only what CI checks against.

### Creating the keys

The owner does this by hand, on their own machine. An agent never does it and never sees a seed.
For each of the four keys:

1. Generate the seed: `openssl rand -base64 32`. Write it into the key file JSON
   (`{"key_id": "fyx-rel-2026-a", "seed": "…"}`). Use a RAM disk or a folder that is not synced.
2. Run `fyx-registry public-key --key-file key.json`. Add the printed entry to its keyset file
   through a PR, and send it to the Fyx client so it is compiled in.
3. Store the key file's JSON in the password manager. For a current key, also store it as the
   secret of its Environment.
4. Delete the key file.

The two Environments:

| | `release-signing` | `blocklist-signing` |
|---|---|---|
| Used by | `publish.yml` only | `blocklist.yml` only |
| Deployment branches | `main` only | `main` only |
| Required reviewers | none: a reviewer would block T0–T1 auto-merge | the owner: a block-list publish is always the owner's action |

Neither secret is available to forks, and `pr.yml` references neither. The protection of
`release-signing` is that only workflows on `main` run there, and `/.github/` is the owner's.

### Rotation, planned

The same steps apply to each keyset. Old clients know the current and the rotation key, so
documents are always signed with a key that both old and new clients accept.

1. **Promote the rotation key.** Put it into the Environment's secret. It is now the current key.
   - For releases, re-sign every published release with it and publish a new `index.json`.
   - For the block list, sign the next list with it.
2. **Make a new rotation key** offline. Ship a client whose keyset holds the promoted key and the
   new rotation key.
3. **Drop the old key.** Once that client is current, remove the old key from the keyset file.

### Compromise

If a **release key** leaks:

1. Delete the secret. This stops publishing.
2. Promote the release rotation key, and re-sign the index with it.
3. Ship a client release whose release keyset drops the leaked key.
4. Review every release signed since the suspected leak. Block what you cannot vouch for: the
   block-list key is untouched, so the block list still works.

If the **block-list key** leaks, an attacker can block extensions or publish a list with a huge
`sequence`. Clients would then refuse every real list. The attacker cannot ship code.

1. Delete the secret.
2. Promote the block-list rotation key.
3. Ship a client release whose block-list keyset drops the leaked key.
   - The client verifies its cached copy again when it loads it. A forged list signed by the
     dropped key then fails verification and is discarded, so the client starts with no cached
     list.
   - The next real list is accepted whatever its `sequence`.

## Block list

Only the owner can block, through a PR to `blocklist/blocklist.toml` (CODEOWNERS):

```toml
[[entry]]
id       = "todo"
versions = ">=1.2.0, <1.2.3"        # or "*"
reason   = "Uploads open buffers."  # shown to users, 1-300 characters
urgent   = true
```

How a block happens:

1. **Report.** Anyone can open a "Report an extension" issue. For a vulnerability, report it
   privately as a security advisory on the repository. The issue template asks for the id,
   versions, what happens, and how to reproduce it.
2. **Triage** within 24 h of the report. Confirm the report, then tell the extension's owners in
   the issue, unless that would warn an attacker.
3. **Block.** Open a PR with the entry and the owner's approval. `blocklist.yml` signs and
   publishes it. Clients pick it up within 6 h, or at their next start, and disable the blocked
   versions (decision 19). They roll back to a kept previous version that is not blocked.
4. **Fix.** The extension's owners publish a fixed version through a normal PR. The block entry's
   range should end below the fixed version.
   - The fix can be `urgent = true` with the registry owner's approval, so it skips the age gate.
   - Clients then update straight from the blocked version (`ReplacesBlocked` in
     registry-format.md).
5. **Lift** a block by removing the entry. The next sequence no longer has it, and clients stop
   disabling it. The release itself was never deleted.

Malware is blocked with `versions = "*"`. Every later PR for that id fails `policy` until the
owner removes the block.

1. Create the repository and its branch rules, CODEOWNERS, the `policy/` files and a
   CONTRIBUTING.md with an example entry.
2. Add `pr.yml` with `entry` and `policy`. Done when a PR adding a T2 capability cannot merge

1. Add the builder image, and `build` and `publish.yml`.

   signature.

## Open questions

1. **Reproducible builds.** Should a mismatch between the PR build and the publish build fail the
   publish? Proposed: yes, once three demo extensions build bit-for-bit identically twice in the
   pinned image.
2. **New T0–T1 extensions with no human review**, as the owner decided. The CI checks above
   (reserved and near-copy ids, owner identity) cover squatting, not intent: a T0 panel can still
   show misleading text. Is a review after publishing, plus the block list, enough?
3. **Where T2 manifest fields live.** `network_domains` and `processes` need `[fyx_ui]` keys and
   `fyx-ext check` support before any T2 entry can pass `build`.
