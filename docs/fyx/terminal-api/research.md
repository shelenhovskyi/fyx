# Термінали для розширень і нативні інтеграції CLI-інструментів: дослідження

Статус: дослідження, 2026-11-19. Нічого з цього не реалізовано. Документ свідомо не тримається
чинних правил Fyx (заморожений 0.3, «мінімальні upstream-хуки», «a terminal is the user's»,
«T2 при першому використанні»): де пропозиція їх змінює, це сказано в розділі
[Які правила доведеться змінити](#які-правила-доведеться-змінити).

Позначки джерел: **[DOC]** офіційна документація, **[RE]** реверс-інжиніринг сторонніх проєктів,
**[?]** не перевірено.

Вимоги власника:

1. Розширення може бути окремим повноцінним терміналом.
2. Будь-хто може зробити повноцінну інтеграцію не лише для Claude Code CLI, а для будь-якого
   інструмента.
3. Потужні можливості користувач приймає вручну під час встановлення.

## Коротко

1. **Нічого Claude-специфічного в ядрі Fyx.** Ядро дає загальні примітиви («набір для
   інтеграцій»), а Claude Code, Gemini CLI, Codex тощо — це розширення на цих примітивах.
   Перше таке розширення (Claude Code) робимо самі, друге (Gemini CLI, у нього документований
   протокол) — щоб перевірити, що набір справді загальний.
2. **«Розширення-термінал» — так, але малює завжди Fyx.** Розширення визначає, *що* це за
   термінал (програма, бекенд, свій потік байтів, своя панель навколо), а сітку символів,
   ввід, IME, виділення і пошук малює нативний термінал Fyx. Власний емулятор у WASM — ні.
3. **Безкоштовний виграш: протокол OSC 7501.** Claude Code (2.1.295+) уже сам повідомляє стан
   сесії (працює / заблоковано / готово), якщо термінал відповідає на запит підтримки; Codex
   додає це в main [RE]. Якщо Fyx навчиться приймати OSC 7501, статус на вкладці буде без
   жодного розширення і налаштування.
4. **Дозволи: три рівні з прийняттям при встановленні.** Звичайне — видно в списку,
   встановлення = згода. Потужне — окремі галочки при встановленні з точними програмами,
   шляхами, портами і поясненням автора. Дії над *твоїми* терміналами — тільки в момент дії,
   на конкретному терміналі, який ти явно поділив.
5. **Чого не даємо:** глобального потоку всіх байтів з усіх терміналів, сирого VT замість
   структурованих даних, запису в чужий shell без жесту, прямого запису розширенням у `~`.

## 2. Розширення як «окремий термінал»

| Форма | Що робить розширення | Що робить Fyx | Рішення |
|---|---|---|---|
| **Профіль** | Рецепт: програма, args, env, cwd, іконка, назва. З'являється в меню «+» | Запускає pty, малює, все інше | Так. Як профілі VS Code і fragments Windows Terminal |
| **Бекенд (pseudo-terminal, «domain»)** | Дає потік байтів в обидва боки: SSH-клієнт, serial-порт, tmux control mode, контейнер, свій протокол, TUI, написаний у WASM. Отримує `input(bytes)` і `resized(cols, rows)` | Малює через alacritty, санітизує вивід, ріже великі потоки на шматки, щоб флуд не з'їдав бюджет виклику | Так. Як `Pseudoterminal` у VS Code, domains у WezTerm, панелі плагінів Zellij |
| **Керований термінал** | Запускає *оголошену* програму в pty, читає і пише **у свій** термінал | Позначка «запущено розширенням X» на вкладці | Так (потужний дозвіл) |
| **Вузол `terminal` у панелі** | Будує свій інтерфейс навколо терміналу: вкладки, блоки, бічні панелі, палітра команд | Сітку всередині вузла малює нативний `terminal_view` | Так. Саме це дає «окремий повноцінний термінал»; у VS Code такого немає, тому там тягнуть xterm.js у webview |
| **Власний емулятор** (свій VT-парсер і рендер на `canvas`) | Усе | Лише показує картинку | **Ні.** Див. нижче |

Чому не власний емулятор (виміряно на коді):

- `ui-event` не має подій клавіатури і фокусу на canvas (`fyx-ui.wit:478-500`): не набрати
  Ctrl-C, стрілки, Tab.
- Кольори canvas — лише токени теми і 8 data-кольорів (`docs/fyx/wit-0.3/design.md:1125-1131`):
  ANSI 256 і truecolor неможливі.
- Немає метрик шрифту і сітки комірок, немає події зміни розміру: не розкласти сітку, CJK,
  курсор, не повідомити cols/rows програмі.
- `process:spawn` — це pipes без pty (`fyx-ui.wit:819-859`): shell і TUI не працюють інтерактивно.
- 200 мс бюджет фатальний (`docs/fyx/limits-and-gotchas.md:22-47`): `cat` великого файлу в одному
  виклику вимикає розширення.
- Рендер: 16 384 текстових op-ів малюються ~69 мс (`tasks/progress/W3.md:16-20`), tick не частіше
  100 мс (`design.md:1163`), без IME, доступності, виділення, пошуку, посилань.

Щоб це виправити, довелося б перебудувати `terminal_view` всередині API. VT-парсер у WASM працює
нормально (ghostty-web, `libghostty-vt`), але всі такі проєкти малюють назовні справжнім GPU/DOM-стеком.
Якщо колись знадобиться — це вузол `grid`, який годується VT-потоком, тобто та сама форма «бекенд».

Висновки для API:

- **Спільний знаменник** — дві «родини» IDE-протоколів. Родина A: редактор слухає loopback-порт
  (MCP), пише discovery-файл з токеном у певне місце, кладе порт у env терміналу (Claude, Gemini,
  Qwen, Copilot). Родина B: свій WebSocket/IPC (Amp, Codex). Спільної специфікації немає.
- **ACP** — єдиний міжвендорний стандарт, але для іншого режиму: агент живе в панелі редактора,
  а не в терміналі. Fyx його вже має; розширенням треба лише дати змогу зареєструвати ACP-агента
  декларативно.
- **Більшість хуків уміють лише запускати команду** (Gemini, Codex, Cursor, Kiro, Aider). Тому
  Fyx має постачати маленький relay-бінарник, який пересилає JSON від хука до розширення і
  повертає відповідь (allow/deny) з правильним exit code.
- **Перевірка правок** буває двох видів: блокуюча (Claude `openDiff`, Copilot, Codex app-server,
  ACP) і «відправив — отримав сповіщення» (Gemini/Qwen). Примітив має підтримувати обидва і
  повертати фінальний вміст з правками користувача.
- **OSC 7501 «Program Status»** — специфікація rev 0.4 (superlogical.com/rex/docs/build/program-status):
  `ESC ] 7501 ; key=value:... ST`, ключі `state` = idle|working|blocked|done|error, `progress`,
  `kind` = permission|question|auth, `app`, `id`, `title`, `msg` (base64); запит підтримки `OSC 7501 ; ?`.
  Відправники: Claude Code 2.1.295+, Codex у main, кілька інших; приймачі: kitty (master), tuios,
  cmux, Ghostty (лише парсер) [RE, дані про поширення з одного блогу].

Уроки: VS Code не стабілізує глобальний потік байтів через продуктивність і замінив його виводом
однієї команди; nonce в OSC 633 захищає від підробленої «команди користувача»; kitty і Zellij
дають дозволи по діях; Zellij замазує текст команд без дозволу на читання вмісту; JetBrains тричі
міняв API — переживають лише абстракції «процес» і «блок команди»; аудит 2023 року знайшов ~10 CVE,
де відповідь терміналу потрапляла назад у ввід shell.

## 5. Архітектура

```
┌──────────── розширення: fyx_claude_code, fyx_gemini_cli, ssh, serial, ... ────────────┐
└───────────────────────────────────────────┬───────────────────────────────────────────┘
┌──────────────────────── шар C: fyx:ui@0.4, дозволи ───────┴───────────────────────────┐
│ terminal:* · env · package-files · listen · discovery-file · review:propose · context │
└───────────────────────────────────────────┬───────────────────────────────────────────┘
┌────────────────────── шар B: набір для інтеграцій (хост) ─┴───────────────────────────┐
│ loopback-сервер з токеном · MCP-обгортка · fyx-relay · discovery-файли · review-міст  │
└───────────────────────────────────────────┬───────────────────────────────────────────┘
┌────────────────────── шар A: термінальний фундамент ──────┴───────────────────────────┐
│ TerminalId · OSC-тап (7, 9, 9;4, 99, 133, 633, 777, 1337, 7501) · CommandBlock         │
│ TerminalStatus на вкладці · список агентних сесій · pseudo-terminal · вузол terminal  │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

### Шар A: термінальний фундамент

1. **Ідентифікатор і реєстр.** `TerminalId` для кожного терміналу (для розширень — непрозорий
   і свій у кожного). У env: `FYX_TERMINAL_ID`, `FYX_TERMINAL_TOKEN` (секрет терміналу).
   `Project` емітить `TerminalCreated` / `TerminalClosed`.
2. **OSC-тап.** У форку alacritty — колбек на необроблений OSC → `TerminalBackendEvent::Osc`.
   Розбір: OSC 7 (cwd), 9 / 777 / 99 (сповіщення), `9;4` (прогрес), 133 / 633 (блоки команд),
   1337 `SetUserVar`, **7501 (стан програми, з відповіддю на запит підтримки)**. Ліміти розміру
   і частоти — на IO-потоці.
3. **Shell integration** для zsh, bash, fish з nonce → `CommandBlock { command_line, trusted, cwd,
   exit_code, output_range }`.
4. **Статус на вкладці** `TerminalStatus { state, label, detail, progress, attention, source }`.
   Джерело завжди видно («від Claude Code через OSC 7501», «від розширення X»), щоб розширення
   не могло видати себе за інструмент.
5. **Список агентних сесій**: усі термінали зі станом, сортування «потребує уваги» вгору, клік —
   перехід. Сповіщення Fyx на `blocked` і `done`, коли вікно не у фокусі.
6. **Pseudo-terminal** поверх наявних display-only терміналів і **вузол `terminal`** для панелей
   розширень.
7. **Санітизація** виводу з pseudo-terminal: без OSC 52, 8, 1337, запитів з відповіддю; відповіді
   терміналу ніколи не будуються з даних виводу.

Уже після цього шару Claude Code (і Codex, коли випустять) показує стан на вкладці без розширень.

### Шар C: дозволи в `fyx:ui@0.4`

Принцип замість «a terminal is the user's»: **термінали користувача — користувача за
замовчуванням; свої термінали розширення — його.**

Рівні:

- **T0** — без запиту, видно в списку.
- **T1** — у списку при встановленні; встановлення = згода; відкликається.
- **T2** — **окремі галочки при встановленні** в групі «Може запускати код або виходити за межі
  Fyx», з точними програмами, env, шляхами, портами і поясненням автора. Не відмічено → `Denied`,
  можна ввімкнути пізніше на сторінці розширення. Запит при першому використанні лишається
  лише для встановлень без діалогу (dev-шлях через `FYX_UI_DEV_EXTENSIONS`).
- **T3** (новий) — лише в момент дії, на конкретному об'єкті, після жесту користувача. Наперед
  не дозволяється, максимум «на цей термінал до кінця сесії».

| Можливість | Рівень | Примітка |
|---|---|---|
| Статус на своїх терміналах | T0 | на чужих — T1, завжди з підписом джерела |
| `terminal:profiles` | T1 | користувач сам запускає; оболонки й інтерпретатори з `RUNS_ANY_CODE` виділено |
| `terminal:pseudo`, вузол `terminal` | T1 | процесу немає; запис у буфер обміну — окремий T2 |
| `context:selection`, `workspace:diagnostics`, `open` | T1 | попередження про комбінацію з мережею, записом у термінал чи файлами |
| `review:propose` | T1 | сама перевірка — це згода на кожну правку; застосувати без перевірки = `workspace:edit` (T2) |
| `terminal:create` (оголошені програми в pty), читання і запис у свої | T2 | позначка «запущено X»; недоступно в недовіреному worktree |
| `terminal:env` у свої термінали | T2 | `PATH`, `LD_*`, `DYLD_*`, `*_OPTIONS`, `NODE_OPTIONS`, `PYTHON*` позначені як «може запускати будь-що» |
| `terminal:env` у **всі нові** термінали | T2, окрема сильніша галочка | старі термінали з позначкою «перезапустіть, щоб застосувати» |
| `terminal:observe` (список, назви, cwd, стани) | T2 | текст команд замазаний без T3-читання (як у Zellij) |
| `net:listen` (loopback) | T2 | «приймає з'єднання від програм на цьому комп'ютері» |
| `fs:discovery-file` за шаблоном шляху | T2 | файл пише хост; прибирається при відкликанні і видаленні; вважається виконанням коду в тому інструменті |
| `relay` | T2 | канал для хуків інструментів |
| `network:fetch`, `process:spawn`, `workspace:edit`, `agent:observe` | T2 | як у 0.3, але з прийняттям при встановленні |
| Читання вмісту **твого** терміналу | T3 | «Поділитися з X» на вкладці; лише блок команди або останні N рядків без ANSI |
| Запис у **твій** термінал | T3 | лише поділений термінал і підтвердження кожної команди з точним текстом; без керівних клавіш |

**«Завжди дозволяти» для T3.** За замовчуванням T3 питає щоразу, але користувач може свідомо
дозволити розширенню доступ до всіх своїх терміналів назавжди:

- Вмикається лише з картки запиту («Завжди дозволяти X») або на сторінці розширення, не в
  діалозі встановлення, і окремо для читання і для запису.
- Перед увімкненням — помітне попередження з наслідками простими словами: «X зможе бачити все,
  що з'являється у твоїх терміналах, зокрема паролі й токени, і виконувати будь-які команди від
  твого імені». Кнопка підтвердження активна через 1 с (як наявний click guard).
- Поки дозвіл діє, на кожній вкладці терміналу видно постійний значок «X має доступ», а в
  статус-барі — індикатор з посиланням на відкликання одним кліком.
- Кожне читання і запис потрапляють у журнал розширення; запис додатково підсвічує вкладку
  («набрано розширенням X»).
- Дозвіл скидається при оновленні розширення (новий sha256 компонента) і не діє в недовіреному
  worktree.

Загальні правила: грант прив'язаний до sha256 компонента (вже є); оновлення, яке додає або
розширює T2/T3, затримується і показує різницю («нове у 1.3: ...»); відкликання вбиває термінали
розширення, закриває порти і прибирає discovery-файли; журнал використань (запущені процеси,
записи в термінали, файли поза проєктом, порти) видно на сторінці розширення; на вкладці видно
бейдж, коли розширення пише в термінал. Click guard 1 с і «без відповіді з клавіатури» діють для
всіх T3-запитів.

### Перше розширення: `fyx_claude_code`

Як воно лягає на примітиви:

1. Профіль «Claude Code» у меню «+» і (опційно, окрема галочка) env у всі нові термінали.
2. `CLAUDE_CODE_PLUGIN_DIRS` → тека пакета з Claude-плагіном, у якому `http`-хуки шлють події на
   loopback-сервер розширення. Стан і так приходить через OSC 7501; хуки дають деталі (який
   інструмент, текст запиту дозволу, останнє повідомлення) і хід для agent review.
3. `net:listen` + `fs:discovery-file` `~/.claude/ide/{port}.lock` + env `CLAUDE_CODE_SSE_PORT`,
   `ENABLE_IDE_INTEGRATION=true` → IDE-протокол: `selection_changed`, `at_mentioned`,
   `getDiagnostics`, `openFile`, `openDiff` → `review:propose`.
4. Хід агента: `UserPromptSubmit` → початок, `Stop` → кінець; змінені за хід файли — у панелі
   перевірки як «змінено без перевірки», а правки через `openDiff` — по hunk-ах.

Обмеження: у режимах `acceptEdits` / `auto` Claude пише без `openDiff`; IDE-протокол [RE] і може
зламатися з новою версією CLI.

Сценарій: особистий акаунт Claude у `~/.claude`, робочий у `~/.claude-work`; так само для інших
інструментів.

### Що дозволяють самі інструменти

| Інструмент | Як розділити акаунти |
|---|---|
| Claude Code | `CLAUDE_CONFIG_DIR=/abs/path` — уся тека налаштувань, логін, сесії, `ide/` lock-файли [DOC]. Проєктні налаштування цю змінну задати не можуть [DOC] |
| Gemini CLI | `GEMINI_CLI_HOME` [DOC] |
| Codex CLI | `CODEX_HOME` [DOC] |
| Copilot CLI | `COPILOT_HOME` [DOC] |
| OpenCode | `OPENCODE_CONFIG_DIR` [DOC] |

Що каже Anthropic (code.claude.com/docs/en/legal-and-compliance): дозволено, щоб користувач
входив у **незмінений бінарник Claude Code** зі своєю підпискою; заборонено стороннім розробникам
збирати, зберігати чи передавати облікові дані й токени Claude.ai або пускати запити через
підписку від імені інших; ліміти Pro/Max/Ultra розраховані на «звичайне індивідуальне
використання». Окремо про кілька акаунтів однієї людини сторінка не говорить; у новинах є
слова співробітника, що мати кілька акаунтів не заборонено, і звіти про бани за патерни, схожі
на перепродаж [?, вторинні джерела].

### Як це виглядає у Fyx

- **Профілі акаунтів** у налаштуваннях користувача: назва («Особистий», «Робочий»), інструмент,
  тека налаштувань, колір. Fyx лише підставляє змінну теки (`CLAUDE_CONFIG_DIR` тощо) у
  термінал або ACP-агента; входить користувач сам, командою інструмента, всередині цієї теки.
- **Прив'язка до проєкту**: «у цьому проєкті — Робочий». Зберігається в налаштуваннях
  користувача за шляхом проєкту, не в репозиторії: репозиторій не може обрати за тебе акаунт.
  Вибір також є в меню «+» («Claude Code — Робочий») і в agent panel.
- **Акаунт завжди видно**: бейдж і колір на вкладці терміналу, у списку сесій і в agent panel,
  щоб не працювати випадково не з того акаунта.
- Discovery-файли IDE-протоколу пишуться в теку свого профілю (`$CLAUDE_CONFIG_DIR/ide/`), тож
  CLI підключається до правильного вікна.

### Обмеження проти обходу правил і лімітів

Вбудовано в продукт, а не лише в правила реєстру:

1. **Fyx ніколи не торкається облікових даних**: не читає, не копіює, не зберігає токени і не
   передає їх між профілями. Тека профілю для Fyx — непрозорий шлях. Логін робить лише
   офіційний інструмент.
2. **Жодного автоматичного перемикання.** Fyx не змінює акаунт у відповідь на ліміт, помилку
   `rate_limit` чи вичерпану квоту. Повідомлення про ліміт показується як є («ліміт до 15:00»),
   без кнопки «продовжити з іншим акаунтом».
3. **Зміна акаунта = нова сесія.** Fyx не переносить сесію, історію чи контекст між
   акаунтами, щоб продовжити ту саму роботу на чужому ліміті.
4. **Немає розподілу навантаження**: ні «запустити задачу на всіх акаунтах», ні черги, яка
   роздає запити між акаунтами, ні пулу акаунтів.
5. **Розширенням це недоступно.** Змінні тек і автентифікації (`CLAUDE_CONFIG_DIR`,
   `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, `CODEX_HOME`, `GEMINI_CLI_HOME`,
   `COPILOT_HOME`, `OPENCODE_CONFIG_DIR`, `*_API_KEY` тощо) — у списку заборонених для
   `terminal:env` і `process:spawn` (`crates/ui_ext/src/process.rs:65-118`). Теки профілів
   додаються до захищених шляхів, як `.claude/`. Розширення бачить лише назву профілю
   терміналу, не шлях.
6. **Правило реєстру**: розширення, які ротують акаунти, обходять ліміти, діляться або
   перепродують доступ, не приймаються в `fyx-extensions` і потрапляють у block list.

Чесне обмеження: людина вручну в терміналі може зробити що завгодно, і Fyx цьому не завадить.
Мета — не будувати і не відкривати для цього механізмів.

Примітка: agent panel працює з Claude через ACP-адаптер на Agent SDK, а сторінка Anthropic
каже, що продукти на Agent SDK мають використовувати API-ключі. Це функціональність upstream Zed
(`crates/agent_servers` з моменту форку Fyx не змінював), тож рішення власника 2026-11-19 —
лишити як є і стежити за тим, що зробить upstream.

### Профілі Fyx (глобальна мультиакаунтність)

Ідея: профіль Fyx — це окремий «Fyx» зі своїми налаштуваннями, розширеннями, keymap, історією
проєктів і акаунтами агентів. Обираєш «Робочий» при відкритті вікна — і відкривається IDE з
робочими розширеннями і робочим акаунтом Claude.

Що вже є в Zed:

- `--user-data-dir <dir>` переносить у теку *усе*: `config/` (налаштування, keymap, теми),
  дані, розширення, історію, облікові дані (`crates/paths/src/paths.rs:103-135`,
  `crates/cli/src/main.rs:526`). Тека задається при старті процесу, тож один профіль = один
  процес.
- Settings profiles (`profiles` у `settings.json`, `crates/settings_content/src/settings_content.rs:495-506`,
  крейт `settings_profile_selector`) — іменовані набори перевизначень налаштувань в одному
  процесі. Лише налаштування, без розширень і акаунтів.

| Варіант | Як | Плюси | Мінуси |
|---|---|---|---|
| **A. Профіль = окрема тека даних** | Fyx-шар над `--user-data-dir`: менеджер профілів, вибір при запуску, `fyx --profile work` | Повна ізоляція (розширення, налаштування, логіни), майже без змін у коді Zed, уже працює | Кожен профіль — окремий процес (більше пам'яті); вікна різних профілів не об'єднати; спільне (тема, keymap) треба копіювати або синхронізувати |
| **B. Профілі в одному процесі, як у VS Code** | Профіль = налаштування + набір увімкнених розширень + keymap + акаунти, вибір на вікно | Одне вікно поруч з іншим, легше перемикати | Глобальні налаштування і розширення в Zed спільні на весь процес; потрібні великі зміни в settings store і хості розширень |

Рекомендація: **варіант A**, з таким UX:

- **Менеджер профілів**: створити порожній, копію наявного або з шаблону; назва, колір, іконка.
- **Вибір профілю**: при запуску, якщо профілів більше одного (або «завжди відкривати
  останній»); чип з назвою і кольором профілю в заголовку вікна; команда «Відкрити в профілі…»;
  меню Dock; `fyx --profile <назва>`.
- **Проєкт пам'ятає профіль**: відкриваєш робочий репозиторій з особистого профілю — Fyx
  пропонує відкрити його в «Робочому».
- **Акаунти агентів прив'язані до профілю**: у «Робочому» за замовчуванням
  `CLAUDE_CONFIG_DIR=~/.claude-work` тощо (профілі акаунтів вище стають частиною профілю Fyx).
- **Спільне за бажанням**: «підтягнути тему і keymap з Особистого» — пізніше, окремою функцією.

Ті самі обмеження: перемикання профілю — лише дія користувача, ніколи автоматично через ліміт;
розширення не бачать інших профілів і не можуть їх запускати.

Перевірити: як macOS показує кілька запущених екземплярів одного `.app` з різними
`--user-data-dir` (одна іконка в Dock чи дві) і чи коректно `fyx` CLI відкриває файл у вже
запущеному екземплярі потрібного профілю [?].

## 8. Як зменшити зміни в коді Zed

Мета: уся логіка в крейтах Fyx (`terminal_ext`, `ui_ext_host`), у коді Zed — лише кілька точок
входу з позначкою `fyx:`.

| Потреба | Наївно | Мінімально | Диф у Zed |
|---|---|---|---|
| OSC-тап | Патч форку alacritty або vte | Обгортка `TeePty` у Fyx: реалізує `EventedPty` (`alacritty_terminal/src/tty/mod.rs:69-101`), делегує `register`/`writer` справжньому pty, а `type Reader = Self` з `Read`, що читає з справжнього pty і проганяє байти через маленький OSC-сканер (шукає лише `ESC ]` ... `BEL`/`ST`). `EventLoop` generic за `EventedPty`, тож підміна — один рядок у `spawn_event_loop` (`crates/terminal/src/alacritty.rs:214`) | ~5 рядків; форк alacritty не чіпаємо. [?] перевірити прототипом |
| Відповідь на запит OSC 7501 | Зміни в обробці відповідей alacritty | Сканер пише відповідь через наявний `PtySender` | 0 |
| Подія «створено/закрито термінал» | Нова подія в `Project` | `cx.observe_new::<Terminal>` і `observe_new::<TerminalView>` з крейту Fyx; закриття — через `on_release` | 0 |
| `FYX_TERMINAL_ID`, env від розширень | Зміни в кількох місцях створення | Один виклик Fyx-хука в `insert_zed_terminal_env` (`terminal.rs:656`), через який проходять усі локальні термінали | ~3 рядки |
| Статус на вкладці | Нові поля і логіка в `TerminalView` | Глобальний провайдер `TerminalDecorations` у Fyx; `tab_content` (`terminal_view.rs:1612`) лише питає «чи є статус для цього терміналу» і малює іконку/бейдж | ~15 рядків |
| Pseudo-terminal | Новий режим терміналу | Наявні display-only термінали (`terminal.rs:984`) + `write_raw_output`; ввід — через наявний шлях display-only | 0, якщо вистачить публічних методів |
| Вузол `terminal` у панелі | — | Вбудувати наявний `TerminalView` у контейнер панелі `ui_ext_host` | 0, якщо конструктор публічний (`terminal_view.rs:243`) |
| Shell integration | Зміни в запуску shell | Скрипти лежать у Fyx; підключаються через env (`ZDOTDIR`, `--rcfile`, `XDG_DATA_DIRS` для fish) у тому ж хуку env | 0 понад хук env |
| Список сесій, сповіщення | Зміни в agent panel | Окрема панель Fyx на основі `TerminalDecorations` | 0 |

Разом ~25 рядків у трьох файлах Zed замість великих змін у `terminal`, `terminal_view`, `project`
і форку alacritty.

Ще два способи:

- **Віддати загальне в upstream Zed.** OSC 7, сповіщення OSC 9/777, OSC 133 і статус на вкладці
  корисні всім користувачам Zed, тому PR-и туди мають шанс. Що приймуть, перестає бути нашим
  дифом. Лишаємо в Fyx тільки те, що стосується розширень.
- **Стежити за дифом автоматично.** Кожна точка входу позначена `fyx:` і записана в
  `tasks/reviews/upstream-diff-audit-1.md`; репетиція rebase на свіжий upstream у CI ловить
  конфлікти до того, як вони накопичаться.

## Які правила доведеться змінити

- **«Upstream edits are minimal hooks»** (`.claude/CLAUDE.md`): з підходом з розділу 7 правило,
  схоже, можна не міняти — лишається ~25 рядків у трьох файлах Zed. Міняти доведеться, лише якщо
  прототип `TeePty` не вийде і знадобиться патч форку alacritty.
- **Профілі акаунтів**: передати змінну теки в ACP-агента (`crates/agent_servers/src/acp.rs`,
  поруч із наявним скиданням `CLAUDE_CODE_OAUTH_TOKEN` на `:1453`) — ще одна точка входу.
- **0.3 заморожений** → новий світ `since_v0.4.0`.
- **«A terminal is the user's»** (`docs/fyx/wit-0.3/design.md:1363`) → «термінали користувача —
  користувача за замовчуванням; свої термінали розширення — його».
- **Рішення 21 специфікації і §7 design 0.3 («T2 при першому використанні»)**
  (`docs/fyx/platform/spec.md:145-160`) → T2 приймається при встановленні, додається T3.
- **Захищені шляхи** (`.claude/` тощо) для розширень лишаються: discovery-файли пише хост за
  оголошеним шаблоном, а `fyx_guard` має дозволити це хосту явно.

## Відкриті питання

1. Чи чекають хуки з `CLAUDE_CODE_PLUGIN_DIRS` діалогу довіри Claude.
2. Чи прийнятні постійні дифи під недокументовані IDE-протоколи (Claude, Copilot, Amp, Codex),
   чи підтримувати лише документовані (Gemini, Qwen) і OSC 7501.
3. Env у всі термінали чи лише в профільні: зручність проти «розширення змінює кожен мій shell».
   Пропозиція: обидва варіанти, вибір користувача галочкою при встановленні; за замовчуванням —
   лише профільні.
4. Віддалені (SSH) термінали: loopback з віддаленої машини недоступний без тунелю.
5. Windows: named pipe замість loopback HTTP, шлях пакета, shell integration для PowerShell.
6. Перевірити джерелом-кодом: схеми lock-файлів Copilot і Amp, формат Codex `/ide`, поширення OSC 7501.
