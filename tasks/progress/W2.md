# W2 progress (WIT and host bindings)

## Current host API for W3 (changes from the judge review `integration-1`)

`extension_host::wasm_host::fyx_ui`:

```rust
pub struct Reply<T> { pub pushed: Vec<PushedUpdate>, pub value: T }  // apply `pushed` in order, then `value`
pub struct PushedUpdate { pub surface_id: String, pub update: ui_ext::Update }

impl UiExtension {
    pub fn load(extension_id: Arc<str>, wasm_bytes: Vec<u8>, cx: &AsyncApp)
        -> Task<Result<(UiExtension, mpsc::UnboundedReceiver<PushedUpdate>)>>;
    pub async fn mount(&self, surface_id: &str) -> Result<Reply<Tree>>;                     // was Result<Tree>
    pub async fn handle_event(&self, surface_id: &str, event: UiEvent) -> Result<Reply<Update>>; // was Result<Update>
    pub async fn list_rows(&self, surface_id: &str, list_node: NodeId, start: u32, count: u32)
        -> Result<Reply<Vec<(u32, Tree)>>>;                                                // was Result<Vec<(u32, Tree)>>
}
```

- Pushes made during a call (any surface) arrive in that call's `Reply`, in emission order. The receiver
  from `load` now yields only pushes without a reply: those made during instantiation/`surfaces`, and those
  of a call that failed with an extension-reported error (forwarded so the guest's mirror stays in sync).
- New: `UiExtension::load_from_dir(extension_dir: &Path, fs: Arc<dyn Fs>, cx: &AsyncApp)
  -> Result<Option<(UiExtension, mpsc::UnboundedReceiver<PushedUpdate>)>>` reads `extension.toml`; `None` when
  it has no `[fyx_ui]` table (finding 7). Table (W4's proposal, `deny_unknown_fields`):
  `api_version = "0.1.0"` (must be supported and match the component), `component = "fyx_ui.wasm"` (relative,
  no `..`), `capabilities = ["ui:panel"]` (each panel surface needs `ui:panel`, each status item
  `ui:status-bar`). Parsed by `fyx_ui::UiManifest`; upstream's `ExtensionManifest` is untouched. The demo
  crates do not ship an `extension.toml` yet: whoever packages them (W4/W3) adds one and copies the built
  component next to it.
- `ui_ext::Tree::apply_update` / `apply_patches` / `replace` now return `BTreeSet<NodeId>`, the touched ids
  (was `bool` / `()`): `set-props` targets, inserted ids, every removed id (whole subtrees); for `replace` the
  old and new ids. Empty = unchanged. Drop cached rows of every touched id and re-request the visible range of
  those that are still list nodes (finding 5).
- A call that runs past 200 ms — busy in wasm *or* blocked in a WASI host call such as `thread::sleep` —
  fails and disables the extension (finding 1).


## 1. WIT types cannot be recursive — confirmed (2026-11-17)

The component-model Explainer (`design/mvp/Explainer.md`, section "Value types") states that value
types currently cannot be recursive; a future extension based on core-wasm `rec` groups is planned but
tied to the next canonical-ABI iteration. In WIT (`design/mvp/WIT.md`), definitions are resolved in a
topological order and the validator rejects cycles ("Interfaces linked with `use` must be acyclic";
references between items must be acyclic), so a `record node { children: list<node> }` does not
validate. The flat `list<node>` + parent-id design stays. Sources:
https://github.com/WebAssembly/component-model/blob/main/design/mvp/Explainer.md#value-types and
https://github.com/WebAssembly/component-model/blob/main/design/mvp/WIT.md

## 2. `ui_ext` tree model — done

- `crates/ui_ext/src/types.rs`: plain Rust mirror of `fyx:ui/types` (serde: externally tagged,
  kebab-case, same names as the WIT — the JSON form for a sidecar / W8).
- `crates/ui_ext/src/tree.rs`: `Tree` (forest; roots in order), `TreeLimits` (2048 nodes or patches
  per update, 16384 nodes total), `TreeError`. `from_nodes`, `from_row` (exactly one root),
  `apply_update` (returns whether anything changed), `apply_patches`, `to_nodes` (pre-order).
  Updates are atomic: a failing patch rolls back the whole batch.
- Rules: parents precede children, unique ids, only `flex` nodes may have children, `before` must be a
  sibling under the same parent, unknown ids are errors, `remove` drops the subtree.
- `cargo nextest run -p ui_ext`: 22 passed.
- New deps of `ui_ext` (workspace deps, Cargo.lock changes at merge): `serde` (+derive), `thiserror`;
  dev: `serde_json`.

## 3. Host bindings — done

- `crates/extension_host/src/wasm_host/fyx_ui.rs`: `wasmtime::component::bindgen!` (wasmtime 48.0.7, path
  `../ui_ext/wit`, world `ui-extension`, async exports, sync host imports). `From` conversions generated ->
  `ui_ext` (surface, node, props, patch, update, list rows) and `ui_ext::UiEvent` -> generated.
  `host.push-update` sends a `PushedUpdate` to an unbounded channel returned by `UiExtension::load`;
  `host.log` goes to the `log` crate (target `fyx_ui`, prefixed with the extension id).
- Public API: `UiExtension::{load, surfaces, mount -> Tree, handle_event -> Update, list_rows -> Vec<(u32, Tree)>}`.
  Guest-reported `Err(string)` is returned as an error and is not fatal.
- Upstream hook: one line in `crates/extension_host/src/wasm_host.rs` (`pub mod fyx_ui; // fyx: ...`).

## 4. Own Store / queue, shorter epoch — done

- Each UI component gets its own `Store<UiState>` and its own call queue on tokio (nothing shared with the
  `zed:extension` queue). WASI context: stderr only, no filesystem, no env.
- Separate `Engine` for UI components (shares Zed's incremental compilation cache); a dedicated
  `fyx-ui-epoch` thread ticks it every 10 ms (Zed: 100 ms). Every tick the call yields to the executor; past
  the 200 ms per-call budget (2 s for instantiate + `surfaces`) it is interrupted. Any trap disables the
  extension; later calls fail fast with "disabled after an earlier failure".

## 5. Version gating — done

- `fyx_ui::{MIN_VERSION, MAX_VERSION} = 0.1.0`, `api_version_range()` / `is_supported_api_version()` take no
  `ReleaseChannel`: the stable/preview cap at Zed's v0.6.0 does not apply.
- Version source: custom section `fyx:ui-api-version` (6 bytes, three BE u16, same as `zed:api-version`);
  fallback: version of an imported `fyx:ui/host@` / `fyx:ui/types@` interface; neither -> rejected.
- `ui_ext_sdk::register_extension!` emits the section (W4). A guest that also emits it gets a multiple of 6
  bytes after linking; the host names that case ("N copies ... emit it only via register_extension!").
