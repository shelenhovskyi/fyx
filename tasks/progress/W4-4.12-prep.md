## 1. What 4.12 delivers

| Piece | Done when |
|---|---|
| SDK builders for `image` and the `images` import | an extension builds image nodes and generated images without touching bindings |
| Down-conversion | a 0.2 or 0.1 export of the same code fails clearly on an image, as `secret` does on 0.1 today |
| Harness | records image nodes and `add-image` calls; its asset checks match the host's (§12, Tests) |
| Demo | an image gallery panel runs in Fyx and headless in `fyx-ext test` (plan 4.12) |

## 2. SDK

### 2.1 Version plumbing (the part that is not about images)

0.3 is a new package, and three 0.2 types change shape (§0.1):
- `surface-kind` gains `picker`;
- `decoration-location.path` becomes `target`;
- `ui-event` gains `orphaned`, and `host-error-code` gains `denied`.

The SDK repeats what 2.4 did for 0.1:

- `ui_ext_sdk` generates `since_v0.3.0` and re-exports its types. Its API is 0.3's.
- A new Apache crate `crates/ui_ext_sdk_v0_2` holds the 0.2 bindings in `pub mod bindings`, as
  `ui_ext_sdk_v0_1` does for 0.1. The reason is the same: both worlds are named `ui-extension`,
  so their export macros clash. This is a new crate (W0: member and workspace dependency).
- `register_extension!` gets three arms:
  - `(T)` exports 0.3;
  - `(T, v0_2)` converts down to 0.2;
  - `(T, v0_1)` converts down to 0.1. The existing 0.1 glue is kept, and fed from 0.3 values.
- Down-conversion to 0.2:
  - `decoration-target::path(p)` becomes `path`, and other targets are errors;
  - a `picker` surface is left out of `surfaces()` and logged, as a modal is for 0.1 today;
  - `orphaned` and `denied` never reach a 0.2 guest, because the host does not send them;
  - every 0.3-only import returns `unavailable`.
- `exported_api_version()` returns the version the extension was exported as, as in 2.4. One more
  shim, `__fyx_ui_*`, per new import; a 0.2 or 0.1 build still imports only its own world.
- The six demos keep building for every version through their features: `fyx-ui-0-2` stays, and
  `fyx-ui-0-3` is added. Which build is the default follows what Fyx runs then, and is the
  integrator's call.

### 2.2 Image API

```rust
// Builders; infallible, like every props builder. The rules apply in a tree.
impl ImageProps {
    pub fn asset(path: impl Into<String>, alt: impl Into<String>) -> Self; // contain, no size, no tint
    pub fn generated(image: GeneratedImage, alt: impl Into<String>) -> Self;
    pub fn size(self, width: u32, height: u32) -> Self;
    pub fn width(self, width: u32) -> Self;
    pub fn height(self, height: u32) -> Self;
    pub fn fit(self, fit: ImageFit) -> Self;
    pub fn tint(self, color: ColorToken) -> Self;
}
impl TreeBuilder<'_> { pub fn image(&mut self, props: ImageProps) -> NodeId; }
// `From<ImageProps> for Props`, as for the other eight records.

/// A handle from `add-image`. `Copy`, with no `Drop`: a handle outlives remounts, and freeing it
/// is the extension's decision (`remove`), as with decorations.
#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash)]
pub struct GeneratedImage(u32);

pub fn add_image(format: ImageFormat, bytes: &[u8]) -> Result<GeneratedImage, HostError>;
pub fn remove_image(image: GeneratedImage);
```

- **No `Drop` on `GeneratedImage`.** A `Drop` that calls the host would free images whenever a
  value is cloned into a tree builder and dropped. The decorations API has no RAII either.
- **The SDK checks nothing that only the host knows:** whether a file exists, whether it decodes,
  the 64 MiB budget. It checks the cheap rules in `SurfaceTree` (mount, insert, `set_props`), so
  an extension's own unit tests catch them off WASM:
  - alt text of 1 to 256 bytes;
  - width and height from 1 to 2048;
  - the asset path rule.

  The rules come from `ui_ext`'s validation (4.10 adds them there). They are not copied, the way
  `list_row` already uses `ui_ext::Tree::from_row`.
- **Off WASM:**
  - `add_image` returns handles 1, 2, … and records `HostEffect::AddImage { image, format, len }`;
  - `remove_image` records `HostEffect::RemoveImage(image)`.

  Neither keeps the bytes, so the record stays small. They are read back with
  `take_host_effects()`.
- **The panel-only rule** (no images in status items, modals, pickers or decorations) depends on
  the surface kind, which a `SurfaceTree` does not know today. So the SDK leaves it to the host
  and the harness. A `SurfaceTree::for_kind` is not worth it for one rule. (Decided here; an
  owner can overrule.)
- **Down-conversion:** an `image` node in a 0.2 or 0.1 export is a conversion error, "needs fyx:ui
  0.3; this extension is exported as 0.2". That fails the reply, as `secret` does for 0.1, because
  dropping a picture silently would hide a bug. `add_image` returns `unavailable`.

## 3. Harness

### 3.1 Loading with assets

Asset images need the package folder.

- `Harness::load_package(dir)` reads `extension.toml` (`api_version`, `component`,
  `capabilities`), the component, and `assets/`.
- `fyx-ext test` passes the extension folder through a second variable, `FYX_EXT_PACKAGE`, read
  by `Harness::from_env`. Today `Harness::from_env` gets only the component (`FYX_EXT_COMPONENT`).
- `Harness::load(wasm)` keeps working, with no package. Then every `asset` source fails its
  existence check, with a message that says to use `load_package`.

### 3.2 What it checks, mirroring the host

Each check below is either a host check from §12 that the harness runs the same way, or marked as
an open question.

| Check | When | Result in the harness |
|---|---|---|
| alt 1–256 bytes, width/height 1–2048 | the tree or update is applied | rejected, like the host's tree (`ui_ext` validation) |
| `image` outside a panel tree or panel list row | `push-update` at the call; replies and mounts when applied | `invalid-argument` for a push; a reply or mount is rejected |
| asset path rule (relative, `/`, no `..`, no root, no drive, no `\`) | applied | rejected (`ui_ext` validation) |
| asset exists in `assets/`, at most 2 MiB, inside the folder after canonicalizing | applied | **open: Q1.** The harness copies whatever the host does |
| asset format: PNG signature, or SVG text | applied | as Q1 |
| PNG IHDR at most 2048 × 2048 | applied, read from the header only | a `warn` log entry with the file and size, standing in for the renderer's alt text plus error icon. No decode in the harness |
| `add-image`: at most 1 MiB, at most 32 live, the format sniff matches `format` | at the call | `limit-exceeded` or `invalid-argument`, from the same code as the host's checks if 4.10 puts them in `ui_ext` |
| `remove-image` of an unknown handle | at the call | ignored, per the WIT |
| `generated(h)` for a handle that is not live | applied | **open: Q2** |

What the harness does not do: decoding, the 64 MiB LRU, the 250 ms cap, and the concurrency
limits. They are renderer behaviour with no result a test can see, other than the alt text.
They are left out, as tick timing is today.

### 3.3 API

- `HostEffect::AddImage { image: u32, format, len }` and `HostEffect::RemoveImage { image }`.
  They have the same shape as W2c's 0.3 `HostEffect`; to be checked against 4.10.
- `images() -> impl Iterator<Item = (u32, ImageFormat, usize)>`: the live generated images.
- `image_nodes(surface)`: the image nodes of a mounted surface, with their sources. This is a
  convenience; `nodes_v0_3` would cover it too.
- The `*_v0_2` methods get `*_v0_3` counterparts, or become version-neutral. **To decide with
  4.10:** the 2.4 harness shows the newest model through `_v0_2` names. A third set of suffixes
  does not scale, so the plan is to rename the newest-model methods without a suffix (`event`,
  `nodes`, `props`) and move the 0.1-typed ones to `_v0_1`. That is a breaking change for
  `fyx-ext test` users, so it goes in one release with the template update.
- Conformance: `harness_conformance` gains a 0.3 case, comparing W2c's 0.3 probe through both.

## 4. Demo: `extensions/fyx_demo_images`

A new crate, so that the gallery stays about layout primitives. W0 adds the workspace member.

- Panel `images` (right dock, "Images", needs `ui:panel` and `ui:images`):
  - **Assets, SVG.** `assets/logo.svg` drawn as is and with `tint(text-accent)`, side by side.
    The logo is a copy of `assets/fyx/icon/fyx-logo.svg`, from the same repository and licence.
  - **Assets, PNG, fit.** `assets/sample.png` (256 × 160, under 50 KiB, made with `magick` at
    implementation time) in two 120 × 120 boxes, `contain` and `cover`, with captions.
  - **Generated SVG.** A bar chart drawn as SVG text from in-memory data with `add-image`, plus a
    `Shuffle` button. The button calls `remove-image` on the old handle, then `add-image` with new
    data, then `set-props` on the node. Because of this order the live count stays at 1 or 2, and
    the 32-handle cap is never reached.
  - **Thumbnails in list rows.** 50 rows, each a 32 × 32 asset SVG (one of `assets/kinds/*.svg`)
    and a name. This exercises images in virtualized rows (Q13: allowed in panel rows).
  - **Alt text on failure.** A last box shows `assets/missing.png`, whose alt text reads "This
    file is missing on purpose". It shows what the user sees when an asset is missing. If Q1
    makes a missing asset an update error, this box is dropped.
- No image goes into a status item, modal or picker. The demo's crate doc says why.
- Tests:
  - SDK unit tests: the builders, the size and alt rules through `SurfaceTree`, and the
    `add_image` and `remove_image` effects off WASM;
  - harness, headless with `load_package`: the whole panel mounts; `Shuffle` replaces the
    handle, leaving 1 live; the rows carry images; a missing or oversized asset gives the result
    Q1 decides;
  - an `image` pushed to a status item returns `invalid-argument`, through a small fixture,
    since the demo itself never does it.
- `fyx-ext package` already ships `assets/` (`crates/fyx_ext/src/package.rs`, `ASSETS_DIR`, with
  a test). Still to add to `fyx-ext check`:
  - report an asset over 2 MiB as an error;
  - report an SVG with `<image>`, `<script>` or `<foreignObject>` as a warning, since the host
    drops those parts (§12, SVG).

## 5. Open questions for 4.10 (W2c) and the design owner (W10)

1. **Missing, oversized or non-PNG/SVG asset:** is it an update error when the tree is applied,
   or a decode failure that shows the alt text? §12 says the path is checked like `component` and
   decode failures show the alt text, but not which of the two a missing file is. The harness and
   the demo's last box follow the answer. My suggestion: path syntax at apply time (reject), and
   existence, size and format at decode (alt text plus a log line). Checking existence at apply
   time needs file I/O on the main thread.
2. **`generated(h)` with `h` not live:** alt text (renderer) or update error? The WIT says
   "nodes that still show it show their alt text" after `remove-image`, which suggests alt text
   for an unknown handle too. A test should pin the answer.
3. **Is `add-image` an effect?** It returns a handle at once. Can a push in the same call already
   reference the handle? The suggestion is yes, because the store is updated at the call, as
   `LiveIds` is. The decode starts after the call, like every effect.
4. **`tint` on a PNG:** ignored, a log line, or invalid? The WIT says "SVG only".
5. **The harness's 0.3 method names** (§3.3): rename the newest-model methods without a suffix,
   and keep the 0.1 ones as `_v0_1`, or add a `_v0_3` set?
6. **Shared checks:** will `add-image`'s byte and format checks and the asset path rule live in
   `ui_ext`, so the SDK, the harness and the host use one copy (as `LiveIds` does for 0.2)? This
   prep assumes yes.

## 6. Order of work once 4.10 lands

1. Version plumbing for 0.3: the `ui_ext_sdk_v0_2` crate, the three macro arms, and the
   down-conversions. This is the largest part, and it is not about images.
2. The image builders, `add_image` and `remove_image`, and their down-conversion errors, with
   unit tests.
3. The harness: load the 0.3 world, `load_package`, `FYX_EXT_PACKAGE` in `fyx-ext test`, the checks
   in §3.2, and the 0.3 conformance case.
4. The demo and its assets, then `fyx-ext check` for the asset caps.
5. Docs, then the generated API pages.
