## Keyboard (`crates/ui_ext_host/src/keyboard.rs`)

| Keys | Effect | Extension calls |
|---|---|---|
| Tab / Shift-Tab | focus the next / previous enabled button, input, list or table of the surface, in tree order (pre-order, children in order), wrapping; also out of an input or a list | none |
| Enter / Space on a button | `click(id)`, through the same `SurfaceView::dispatch` as the mouse (so pending typing goes first) | exactly one |
| Up / Down, Home / End, PageUp / PageDown in a list or table | move the selection (first Down selects row 0; a page is the rows that fit), scrolling it into view; highlighted with `element_selected` | none (rows are fetched as the list scrolls) |
| Enter in a list or table | `row-click(list, selected)` | exactly one |
| Enter in an input | `input-submitted` (unchanged) | exactly one |
| Escape | `workspace::FocusCenterPane`, back to the editor | none |

- **Bindings.** No key binding is added. Enter, Escape, Up, Down, Home and End already map to
  `menu::*` in the default keymap's context-free section, and the surface view handles those. Tab,
  Shift-Tab, Space and the page keys are taken by a **keystroke interceptor** that acts only while
  the context stack contains `FyxSurface` (Space only on a focused button, `FyxSurfaceButton`; page
  keys only in a list, `FyxSurfaceList`). Why: upstream binds Tab to `menu::SelectNext`, the same
  action as Down, so a list could not tell "leave the list" from "next row", and PageUp/PageDown to
  `SelectFirst`/`SelectLast`. Bindings registered from code would not work either: Zed's
  `reload_keymaps` clears every binding on a keymap change, but interceptors are not bindings.
- **Actions** in the `fyx_ui` namespace: `FocusNext`, `FocusPrevious`, `Activate`, `SelectPageUp`,
  `SelectPageDown` (plus the existing `ToggleExtensionPanel`).
- **Focus.** Each button and list has a `FocusHandle` per view, keyed by node id, so focus survives
  every patch that keeps the node; a disabled button keeps focus it already had but leaves the Tab
  order. When a patch removes the focused node, focus goes to the next node of the old Tab order
  that still exists, else the closest one before it, else the surface. The panel's
  `activation_focus_handle` (and `fyx_ui::ToggleExtensionPanel`) focuses the surface view, so Tab
  works right after opening a panel.
- **Focus ring** from theme tokens only: `border_focused` around the focused button, list, table or
  input; `border_transparent` of the same width otherwise, so focusing moves nothing.
- Tests (fake backend, real window, keystrokes through the keymap and the interceptor; the test
  setup binds the same context-free `menu::*` keys as upstream, including Tab → `SelectNext`):
  `test_tab_moves_focus_in_tree_order`, `test_enter_and_space_click_the_focused_button`,
  `test_list_selection_keys_and_enter`, `test_focus_moves_on_when_its_node_is_removed`,
  `test_escape_returns_to_the_editor`.
- Not covered: Escape inside an input reaches the surface only when the editor had nothing of its
  own to cancel (`editor::Cancel` propagating); not tested. Not tried in the running app.

## Design

`crates/ui_ext_host/src/`:

| File | What |
|---|---|
| `backend.rs` | `UiBackend` trait (mount, handle-event, list-rows as `LocalBoxFuture`s of W2's `Reply<T>`), implemented for `UiExtension`; tests use a fake. |
| `surface.rs` | `SurfaceState` entity: the retained `Tree` of one surface, shared by every view of it (one panel per window). Event queue, row cache, pushed updates, resync. |
| `view.rs` | `SurfaceView` entity: maps nodes to GPUI/`ui` elements. Owns the per-window objects: an `Editor` per input, a `Markdown` per markdown node, a `UniformListScrollHandle` per list/table. |
| `panel.rs` | `ExtensionPanel: workspace::Panel`, `ExtensionStatusItem: StatusItemView`, `SurfaceInfo`. |
| `registry.rs` | `UiExtensionRegistry` (global entity), `ui_ext_host::init`, dev loading, per-workspace registration, `fyx_ui::ToggleExtensionPanel { key }`. |

### Rules the code keeps

- **No WASM call from `render()`.** Render reads `SurfaceState` only. The `uniform_list` row callback
  calls `SurfaceState::request_rows`, which only spawns a task when rows are missing.
- **One `handle-event` per input event.** `SurfaceState::dispatch` queues events; one worker task sends
  them one at a time, in order, and applies each reply with `Tree::apply_update` before the next. A
  queued `input-changed` for the same node is replaced by the newer one (not a second call). Events
  for nodes that are no longer in the tree are dropped. `cx.notify()` only when the tree changed.
- **Pushed updates** (`host.push-update`): the registry drains the channel per wake-up and applies the
  batch to the surfaces; GPUI repaints once on the next frame.
- **Typing** is debounced 150 ms (`TYPING_DEBOUNCE`); Enter (`menu::Confirm`) sends `input-submitted`
  with the text and drops the pending change. Inputs follow integrator decision 6 (below). Our own
  `set_text` is never echoed back.
- **Lists and tables** use `uniform_list` and `list-rows`. Rows are cached per `(list node, index)`
  with row-local ids (W4 note), never merged into the surface id space. A `set-props` on a list or table
  node (or a `replace`) invalidates its rows; stale rows stay visible until replacements arrive. Rows
  the extension leaves out of an answer, and failed fetches, are not re-requested until the list
  changes, so a bad extension cannot cause a call per frame. Visible range + 8 rows overscan.
- **Invalid update** (does not fit the retained tree): the error is shown in the panel footer and the
  surface is mounted again to resync.
- **Colours** only from theme tokens: text/icon colours map to `ui::Color` (`text` → Default, `text-muted`
  → Muted, `text-accent` → Accent, `error`/`warning`/`success`), backgrounds and the remaining tokens
  to `ThemeColors` (`border`, `surface_background`, `elevated_surface_background`).

### Primitive mapping

| Node | Element |
|---|---|
| flex | `h_flex`/`v_flex`, gap/padding in px, `grow` → `flex_grow_1`, align → `items_*`, background token; the panel body scrolls vertically |
| text | `Label` (bold → `FontWeight::BOLD`, monospace → buffer font, colour token) |
| button | `ui::Button` (`IconButton` when the label is empty); default → Outlined, filled → Filled, subtle → Subtle, danger → Tinted(Error); icon by snake_case `IconName` |
| input | single-line `Editor` in a bordered box |
| list | `uniform_list` + `list-rows`; rows clickable → `row-click` |
| table | header from `columns` + `uniform_list` rows from `list-rows`; a flex row root's children become equal-width cells |
| icon | `ui::Icon`, unknown names → `Blocks` |
| markdown | `markdown::MarkdownElement` (plain label inside list rows) |
| diff-view | Zed's diff editor (d): `acp_thread::Diff::finalized` (the agent panel's and W5's review pane's diff) in a read-only `Editor` sized by its content, every hunk expanded, no gutter or scrollbars, theme colours; the language name maps to a file suffix through the language registry (`rust` → `diff.rs`, unknown → plain text). One editor per node per window, rebuilt when the props change. Inside list rows (read-only snapshots) a light line diff. Tests `test_diff_view_is_a_read_only_diff_editor`, `test_diff_view_language_from_name` |

Inside list rows, buttons do not send `click` (row-local ids would be ambiguous); the whole row sends
`row-click`. Inputs in rows are read-only, nested lists are not supported.

## Loading extensions

**Installed extensions (integration-3 finding 2).** At startup the registry scans the extension
store's `installed_dir` (`<data dir>/extensions/installed`) and loads every subdirectory whose
`extension.toml` has a `[fyx_ui]` table, with W2's `UiExtension::load_from_dir` (directories
without the table are regular Zed extensions and are skipped). Zed's "Install Dev Extension" links
the source directory into `installed/<id>`, so a dev install is found the same way, provided the
component named by `[fyx_ui].component` is already built next to the manifest
(`script/fyx-build-demos`). It rescans on the store's `ExtensionInstalled`, `ExtensionUninstalled`
and `ExtensionsUpdated` events: a new extension is loaded; a component whose modification time or
size changed is loaded again and its surfaces move to the new instance (panels and status items
stay, the surface mounts again); an uninstalled one stops its surfaces ("… was uninstalled", no
Retry); a surface a new version no longer declares stops too. Scans never overlap.
Not verified: whether Zed's dev-install build step (which compiles a crate's `Cargo.toml` as a Zed
extension) accepts a UI-extension crate; if it refuses, copying or linking the directory into
`installed/` by hand works.

**Install UX (a).** The action `fyx_ui: install dev UI extension` (command palette) asks for a
folder, reads its `extension.toml`, and confirms with the extension id, the capabilities it asks
for (`ui:panel: add dock panels`, `ui:status-bar: add status bar items`), the component and the
folder. It refuses a folder without `[fyx_ui]` or without the built component. On Install it links
the folder into the installed directory as `<id>` (as Zed links a dev extension; a previous dev
link of the same id is replaced, a regular install is left alone) and rescans, so the extension
loads at once and on every start, and a toast says what happened. Test:
`test_install_dev_ui_extension` (real fs, real component). On the extensions page, a loaded UI
extension's card shows its capability chips (`ui:panel`, `ui:status-bar`, from the surfaces it
declared) next to the card's other feature chips: `ui_ext_host::capability_chips`, called from one
`fyx:` hook in `crates/extensions_ui/src/components/extension_card.rs` (two lines) plus its
`ui_ext_host` dependency (approved by the coordinator). Test
`test_capabilities_for_the_extensions_page`.

**Hot reload (b).** Dev extensions reload by themselves: those installed as links (dev installs)
and those from `FYX_UI_DEV_EXTENSIONS` (a folder or a bare `.wasm`). The registry watches the
component file (through the link, `fs.watch` on its folder); a change to it, once writes have paused
for `HOT_RELOAD_DEBOUNCE` (300 ms), rescans the installed directory (the fingerprint check loads the
new component) or loads the dev path again, and the surfaces move to the fresh instance and remount.
Other files in the folder are ignored. Uninstalling drops the watch. Regular (non-link) installs
are not watched; Zed replaces them through its own install flow, which triggers a rescan. Test:
`test_dev_extension_hot_reloads` (real fs watcher, real component; an unrelated file does nothing,
a rebuilt component remounts).

**Extra dev paths.** The environment variable `FYX_UI_DEV_EXTENSIONS` adds paths outside that
directory: a `PATH`-style list (`;` on Windows). Each entry is either an extension directory, loaded
with `UiExtension::load_from_dir` (the id comes from the manifest), or a bare `.wasm` component (id
= file stem with `_` → `-`). An id loaded both ways ends up on whichever instance loaded last.

Demos: `script/fyx-build-demos -j 4` (W4) builds both and copies each component next to its
`extension.toml`, then prints the variable. The status-item fixture (no demo has a status item) is
`crates/ui_ext_wasm/fixtures/status_item`: its own workspace and lockfile, an `extension.toml` with
`capabilities = ["ui:status-bar"]`; build it and copy the component in:


## Known limitations

- **Names per panel (c).** `Panel::persistent_name`/`panel_key` are static functions (the dock calls
  them without a context), so a name per panel needs a type per panel: `ExtensionPanel<const SLOT>`.
  Each panel surface gets a slot for the whole process by its key, and the slot's name is
  `fyx-ui:<extension id>/<surface id>`: sizes and the restored open panel are per surface and stable
  across restarts. There are `PANEL_SLOTS` (16) slots; panels beyond that share `SHARED_SLOT` and its
  name "Extension Panel". No upstream change. The registry keeps panels as
  `Box<dyn AnyExtensionPanel>`; code that names the type writes `ExtensionPanel::<SLOT>`.
  Still: panels added after dock restoration do not restore their open state, and a panel position
  change lasts for the session only.
- **Status item priority (c).** Each side of the status bar has one `ExtensionStatusGroup` entry
  holding that side's extension status items, ordered by `priority` (higher closer to the edge,
  equal ones in load order). The group as a whole sits where the status bar appends items on that
  side; built-in items keep their places.
- **Titles (c).** The dock tooltip wants `&'static str`; titles are interned, leaked once per
  distinct title per process (slot names once per slot), no longer once per load and reload.
