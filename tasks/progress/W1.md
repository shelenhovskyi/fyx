# W1 progress (rebrand and de-cloud)

State: done and verified on Windows 11 (2026-11-17). No request leaves the machine at startup.

## Design

- **Brand and identity** come from existing knobs, so the upstream diff stays small:
  - `paths::APP_NAME = "Fyx"` (the constant upstream documents as "forks should change this"):
    `%APPDATA%\Fyx` (config), `%LOCALAPPDATA%\Fyx` (data, logs, db), `~/.config/fyx`,
    `$XDG_DATA_HOME/fyx`, `~/Library/Application Support/Fyx`, log file `Fyx.log`.
  - The `zed` crate's binary is now **`fyx`** (`crates/zed/Cargo.toml` `[[bin]]` and
    `default-run`): upstream's `main.rs` asserts at compile time that `APP_NAME` matches the
    binary name. The package is still `zed`, so `cargo build -p zed` / `script/gate.sh` are
    unchanged; the output is `target/debug/fyx.exe`.
  - `release_channel`: `display_name()` → `Fyx` / `Fyx Dev` / …, `app_id()` → `dev.fyx.Fyx`
    (`-Dev`, `-Nightly`, `-Preview` suffixes like upstream), `app_identifier()` (Windows) →
    `Fyx-Editor-<Channel>`, which names the single-instance mutex and the named pipe.
  - `crates/zed/src/main.rs` calls `cx.set_app_identity(app_id, display_name)`, so the Windows
    AppUserModelID is `dev.fyx.Fyx` (taskbar grouping, toasts) rather than one derived from the
    exe path. Upstream never called it.
  - `crates/windows_resources`: exe version info `ProductName`/`FileDescription` = `Fyx Dev`,
    `CompanyName` = `Fyx contributors`. `LegalCopyright` (Zed Industries) stays: it is a
    copyright notice, not branding.
  - Product name in `crates/zed`: app menu (`Fyx`, About/Hide/Quit Fyx), About window title,
    "Fyx failed to launch", HTTP User-Agent `Fyx/<version> (<os>; <arch>)`.
- **URL scheme `fyx://`**: `client::ZED_URL_SCHEME = "fyx"` (what macOS registers at runtime), the
  Windows installer registers `HKCU\Software\Classes\fyx` (`zed.iss`). Inside the app `zed://`
  stays the internal link namespace (mentions, schemas, settings links: ~40 call sites), so an
  incoming `fyx://…` is rewritten to `zed://…` at the two entry points: CLI args in `main.rs`
  (covers the first instance and forwarding over the pipe) and `OpenRequest::parse`
  (`open_listener.rs`, OS open-URL events). Helper: `zed::fyx_url_to_internal`.
- **De-cloud through settings, not code**: new `assets/settings/fyx.json`, layered over Zed's
  untouched `default.json` by `fyx_default_settings` in `main.rs` right after `settings::init`.
  `default.json` is not edited: it churns upstream (rebase conflicts) and upstream tests read it
  (the `extensions_ui` suggestion tests would break, for one). Contents:
  - `server_url: "http://127.0.0.1:0"`. Every zed.dev URL (`api.`, `cloud.`, `llm.`, `/rpc`,
    extension registry, telemetry, auto-update, account pages) is derived from it in
    `HttpClientWithUrl::build_*_url`; port 0 fails at `connect()` before a packet is sent.
    `ZED_SERVER_URL` still overrides it, and `"https://zed.dev"` in user settings restores Zed's
    services (their terms apply).
  - `telemetry.diagnostics/metrics: false`, `auto_update: false`.
  - `title_bar.show_sign_in/show_onboarding_banner: false`, `collaboration_panel.button: false`.
  - `edit_predictions.provider: "none"` (the `zed` provider needs a zed.dev account).
  - `auto_install_extensions.html: false`, `suggest_extensions: false` (no registry by default;
    whether Fyx may use Zed's registry is an open owner decision in `PLAN.md`).
  - Objects merge key by key, so `fyx.json` turns entries off rather than removing them.
- **`client` is neither deleted nor stubbed in code**: with `server_url` pointing nowhere it never
  connects; `project`/`workspace`/collab compile unchanged. Crash upload needs
  `ZED_MINIDUMP_ENDPOINT` (unset) and `diagnostics` (off). BYO-key providers and ACP agents are
  untouched.

## Verification (Windows 11, debug build `D:\fyx-targets\w1\debug\fyx.exe`)

Run from a scratch dir holding a `.git` marker plus `assets`/`crates` junctions to the worktree,
because debug builds read assets from the checkout found via the exe path or the cwd. The
repository itself was never opened or used as the cwd. Fresh profile: `%APPDATA%\Fyx` and
`%LOCALAPPDATA%\Fyx` did not exist before the first run.

- Exe version info: `{"ProductName":"Fyx Dev","FileDescription":"Fyx Dev","CompanyName":"Fyx contributors"}`.
- Window: class `Zed::Window`, title `empty project`; a second window opened via `fyx://settings`.
- Dirs created: `%LOCALAPPDATA%\Fyx\{db,extensions,external_agents,logs,prompts,threads,…}`,
  `%APPDATA%\Fyx\{themes,AGENTS.md}`, log `%LOCALAPPDATA%\Fyx\logs\Fyx.log`; `telemetry.log`
  is empty. `%LOCALAPPDATA%\Zed` was not touched.
- Side by side: W3's Zed-branded dev build (`D:\fyx-targets\w3\debug\zed.exe`, pid 33396) and
  Fyx (pid 31124) ran at the same time. A Zed-identity binary started meanwhile handed off to
  W3's instance, not to Fyx: separate mutex/pipe confirmed.
- `fyx.exe fyx://settings` while Fyx was running: the second process exited with code 0 and the
  running Fyx opened its Settings window (forwarding over `\\.\pipe\Fyx-Editor-Stable-Named-Pipe`).
- Network, `Get-NetTCPConnection -OwningProcess <pid and children>` polled every second for 35 s:
  - Run 1 (empty cache): `::1`/`127.0.0.1` → `:1234` and `:8080` (LM Studio and llama.cpp
    provider probes, refused locally; stay on the machine), and ~45 TLS connections to
    `172.67.170.54:443` = `cdn.agentclientprotocol.com` (registry index plus agent icons).
  - Run 2 (cache present): the same local probes plus 1 connection to `172.67.170.54:443`.
  - Nothing else: no zed.dev, no `127.0.0.1:0` attempts in the log, no telemetry.
  - Source: `project::AgentRegistryStore::init_global` called `refresh()` on every launch.
- **Fix (W0 approved):** `crates/project/src/agent_registry_store.rs` no longer refreshes in
  `init_global` (one `fyx:` edit, matching the function's own doc comment). The registry page
  (`AgentRegistryPage::new` and re-activation call `refresh`) and `refresh_if_stale` (run when
  settings contain a registry agent) still fetch on demand. The three upstream
  `registry_refresh_*` integration tests reached `refresh` through `init_global`; they now call
  it explicitly (one marked line each). New test `registry_init_makes_no_request` guards the
  fix across rebases. `cargo nextest run -p project --test integration -E 'test(/registry/)'`:
  5 passed. `cargo check -p project` and `cargo clippy -p project --all-targets -- --deny warnings`: clean.
- **After the fix** (fresh profile, 35 s): only the local `:1234`/`:8080` probes; **0
  non-loopback connections**, no `registry.json` written.
- **On demand still works** (same running instance): writing
  `{"agent_servers": {"claude-acp": {"type": "registry"}}}` to `%APPDATA%\Fyx\settings.json`
  made 1 connection to `172.67.170.54:443` within a second, wrote `registry.json` with 46
  agents (Agoragentic, Amp, Google Antigravity, …) and 46 icons, and the onboarding page's
  "Agent Setup" row went from only "Zed Agent" to Zed Agent, Claude Agent ✓, Codex, GitHub
  Copilot, Cursor (screenshot: shared notes folder, `W1-onboarding-agents-after-on-demand-fetch.png`). The test settings file was removed afterwards.
- Not seen with my own eyes: the Agent Registry page itself. Computer use cannot target the
  uninstalled dev exe, and synthetic keystrokes (`SendKeys`) did not reach GPUI. The page calls
  the same `refresh()` the configured-agent path and the tests exercise.
- Side effect: on a fresh profile the onboarding "Agent Setup" row and the agent panel's
  registry entries stay empty until the registry is fetched once (page opened or a registry
  agent configured); after that the cache fills them.
- Log excerpt (run 2): `INFO [fyx] ========== starting zed version 1.28.1+stable…`, then only
  local errors: `lmstudio.rs:135 … http://localhost:1234/api/v0/models … refused`,
  `llama_cpp.rs:346 … http://localhost:8080/v1/models … refused`.
- `cargo clippy -p zed -p client -p paths -p release_channel -p windows_resources -- --deny warnings`
  and `--all-targets` for the four small crates: clean; `cargo nextest run` on those four:
  24 passed.
